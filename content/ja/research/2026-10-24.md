### メモ

- 戻し先のバージョンは検索結果で食い違ったが、LiteLLM が挙げるのは `litellm==1.106.2` か明示したそれ以前の版で、10-24 の 01:30 UTC には PyPI と両レジストリの `latest` が 1.106.2 を配り、1.107.1 はなかった。
- LiteLLM は確認に `pip show litellm` を挙げつつ pip でもペイロードが動くとし、Flatt の `pip` と `python -c` の手順も同様で、無害な `.pth` と `sitecustomize.py` で試すと `-I`、`-E`、`-s` では動き、`-S` で止まった。
- 未確認: Claude Code が応答本文に GitHub CLI の OAuth トークンを入れうるという最初の記事の主張は、その後繰り返されも撤回もされておらず、検索しても再現や反応は見つからなかった。
- Wiz は PyPI の隔離を 13:20 UTC、イメージの取り下げを 13:53 ごろとして LiteLLM の 13:23 と 14:20 と食い違い、LiteLLM 自身の 13:51 の確認では Docker Hub のタグがまだ不正なインデックスを指していた。
- LiteLLM の時系列は Socket が見つけた 10-12 の実行に触れないが、そのコミット `1a6e3c1` (12:16 UTC、`.github/workflows/cache.yml` を追加) は `gh` でまだ取れ、LiteLLM はどのみち全トークンを失効させるとする。
- 10-24 に確かめると、GHCR の `v1.106.2` のイメージは SLSA の来歴の `vcs.source` が `https://github.com/BerriAI/litellm` だが、PyPI は 1.106.2 のどのファイルにも来歴を出していない。
- issue のコメントには、乗っ取られたワークフローが署名したので、ダイジェストでの固定も LiteLLM の鍵 ([2026-03-30](https://docs.litellm.ai/blog/ci-cd-v2-improvements)) による `cosign verify` も汚染されたイメージを通すという指摘がある。
- 10-24 に確かめると、1.107.0 が固定していた `litellm-enterprise` 0.1.78 と `litellm-proxy-extras` 0.4.110 は 10-18 のアップロードで、どちらの wheel にも `cook`、`sitecustomize`、`.pth` のファイルはない。

- 未解決: LiteLLM はプロセスの変更を来週示すとし、エンバーゴ中の脆弱性は 10-27 に開示の予定で、10-23 中と約束したリリースは 10-24 の 01:30 UTC の時点で PyPI に出ていなかった。

### 実践やアウトプットの提案

- Python を起動せずにシェルから、すべての venv、イメージ、CI のキャッシュで `cook.pth`、`sitecustomize.py`、`litellm-1.107.0.dist-info` を探し、ロックファイルに `osv-scanner` をかけて `MAL-2026-2144` を拾う。
- 1 つのサービスで uv の `--exclude-newer "7 days"` か pip の `--uploaded-prior-to P3D` によるインストールのクールダウンを試し、必要なセキュリティ修正がどれだけ遅れるかを記録する。
- LiteLLM のイメージをダイジェストで固定し、SLSA の来歴の `vcs.source` が `https://github.com/BerriAI/litellm` かをデプロイ時に確かめる検査を加えて、フォークからビルドしたイメージで試す。
- 任意のブランチに push したワークフローが読めるリポジトリと Environment のシークレット (LLM プロバイダーのキーや `DATABASE_URL` など) を洗い出し、その Environment をデプロイのブランチ規則で絞る。

### メモ

- 記事の 512K は上限で推奨は 256K、カードが記すのは 262,144 トークン (256 × 1,024) なので、両者は実用上の上限 256K で一致する。
- 4 ビットの重みは約 23 GB で Rapid-MLX はコンテキスト 1K で約 24 GB を使ったが、`rec` と NVFP4 のビルドは 48 GB を求め Wired も 48 GB で試したので、24 GB で動くと示されたのは短いコンテキストだけである。
- ベンチマークの数値はすべて Recursive のもので、独立したコーディングのベンチマークは見つからず、その SWE-bench Pro v2 は公開の SWE-Bench Pro のスコアと比べられない。
- Recursive は Flint が 25〜40B の dense モデルに匹敵するとするが、自社の表でも dense の Qwen 3.8 が 6 つのベンチマークのうち 4 つで上回り、Terminal-Bench 2.1 では 18.1 ポイント上である。
- Wired の成功は 48 GB で作った小さな単発のプログラムで、r/LocalLLaMA の失敗は複数ステップのツール利用で起き、うち 1 件は Recursive の求める 48 GB を下回る VRAM 8 GB、RAM 32 GB の環境だった。
- ツール利用の失敗が、カードが求める `reasoning_content` を落としたりチェックポイントのチャットテンプレートを使わなかったりするハーネスのせいかどうかは、どの情報源も確かめていない。
- Recursive の速度は prefill を除いた `rec` の値で、`rec` は llama.cpp の 1.4〜2.6 倍とされるのでほかのランタイムでは遅くなるおそれがあり、第三者の数値は Rapid-MLX の毎秒 131 トークンだけである。
- r/LocalLLaMA の 2 つのスレッドはこの実行で取得できず、試用者の報告は AINews の要約に頼っている。

### 実践やアウトプットの提案

- 48 GB の M4 Pro か M5 の Mac で `rec serve` を起動し、Claude Code (`ANTHROPIC_BASE_URL`) か OpenCode を向けて、自分たちのリポジトリの小さなタスクを 10〜20 件回し、成功率と速度を記録する。
- 自前のツール定義を使い `reasoning_content` を履歴に残して複数ステップのタスクを 1 つ回し直し、r/LocalLLaMA のツール利用の失敗が自分たちのハーネスでも再現するかを見る。
- Flint と Qwen3.6-35B-A3B か Qwen 3.8 27B を同じタスクとハーネスで動かし、タスクごとの推論トークンを記録して、考えすぎが Flint の速さの利点を打ち消すかを確かめる。
- 24〜32 GB のマシンで 4 ビットのビルドを読み込み、メモリが尽きるまでコンテキストを段階的に増やして、Recursive が勧める 48 GB に満たない環境にどのタスクが収まるかを知る。
- 作業を明示的なサブタスクに分けるという Recursive の助言に従い、大きなプロンプト 1 つの場合と比べて自分たちのタスクの成功率がどれだけ上がるかを測る。
