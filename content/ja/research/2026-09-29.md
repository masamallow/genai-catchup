- 2026-08-31 00:00 UTC 以降に作られたアカウントでは、`system`・`tools`・それ以前のメッセージを変えたあとに Sonnet 5.5 の思考ブロックを再送すると 400 になる。
    - `thinking-binding-controls-2026-08-01` ベータヘッダと `prefix_mismatch_behavior: "drop_block"` を使うと、エラーにせず該当ブロックを捨てる。
- 指示やツールを変えるときは、会話途中のシステムメッセージで伝えて会話を追記のみに保つのが公式のやり方で、オンデマンドの圧縮 (`compact-2026-09-04`) とメッセージ内でのツール定義 (`inline-tools-2026-09-15`) はベータで使える。
- Claude API と Google Cloud の computer use には `computer_toolset_20260801` が必要で、Amazon Bedrock は `computer_20251124` も引き続き受け付ける。
- Sonnet 5.5 が受け付ける advisor はいずれも、助言を `advisor_redacted_result` ブロックとして暗号化して返す。
- ツール呼び出しの合間のテキストは `thinking` ブロックで返り、既定の `display: "omitted"` では本文が空なので、そのテキストを流している UI はツール呼び出しの間に黙り込む。
- effort の水準は較正し直されており、まず `high`、仕様のはっきりしたエージェント型コーディングは `medium`、チャットなど遅延に敏感な用途は `medium` か `low` から始めるよう勧めている。

- キャッシュできる最小のプロンプトは 512 トークン (Sonnet 5 は 1,024) で、`temperature`・`top_p`・`top_k` に既定以外の値を入れると 400 になる。
- モデル ID は Claude API・Google Cloud・Microsoft Foundry・Claude Platform on AWS が `claude-sonnet-5-5`、Amazon Bedrock が `anthropic.claude-sonnet-5-5`。

#### [A] Docker — Introducing Cloud Sandboxes: Start on Your Laptop, Finish in the Cloud, by Timir Karia and Srini Sekaran (2026-09-24)

<https://www.docker.com/blog/introducing-cloud-sandboxes-start-on-your-laptop-finish-in-the-cloud/>

- ローカルと同じ microVM ベースのサンドボックスを Docker が管理する計算資源で動かし、1 コマンドで両者の間を移せる Cloud Sandboxes を、この日から出すと発表した。
- 今年出した Docker Sandboxes は、コーディングエージェントを手元のマシンから隔離し、独自のカーネルと Docker デーモンを持つ microVM で動かす。
- 狙いは数分ではなく数時間かかる長い作業で、ノート PC ではスリープ、電池駆動、移動中の切断で作業が途切れる。
- 隔離の仕組みも CLI も同じで、変わるのは下のマシンが常に動いていることだという。
- サンドボックスごとに専用の microVM、シークレット、ネットワークポリシーを持つ。
- `sbx move my-project --to cloud` はサンドボックスのファイルシステムを取り込んで向こう側に作り直すもので、逆向きにも使える。
- エージェント向けに組み立て済みのサンドボックスである Kit を、Claude Code、Codex、Copilot、Antigravity、Open Code、Hermes 向けに用意しており、利用者が自分で追加することもできる。
- MCP サーバー (Jira、Linear、Grafana、incident.io、または任意の streamable HTTP のエンドポイント) は 1 回つなげば、1 つのゲートウェイ経由で使える。
- キーやトークンは 1 回保存すれば Cloud Sandboxes のプロキシがリクエストごとに差し込むので、エージェントは本物のシークレットを見ない。
- ネットワークポリシーでエージェントが到達できるエンドポイントを決め、Docker AI Governance による一元的な統制は近日提供とされる。
- 料金は秒単位の従量課金で、1 時間あたり Micro (1 vCPU・2 GiB) が $0.07、既定の Small (2 vCPU・4 GiB) が $0.14、Medium (4 vCPU・8 GiB) が $0.28、Large (8 vCPU・16 GiB) が $0.56、XL (16 vCPU・32 GiB) が $1.12。
- 一時停止中のサンドボックスは無料で、ボリューム、送信トラフィック、公開イメージと Kit のホスティングも無料。
- サンドボックスは既定で 1 時間、1 セッションあたり最長 24 時間動く。
- Web コンソールか、`brew install docker/tap/sbx`、`sbx login`、`sbx --cloud run claude` で始められ、sbx 0.45.1 以降と、Docker Personal か Pro のアカウントでの従量課金プランが要る。
- ローカルのサンドボックスは引き続き無料で Docker Desktop も要らないが、ローカルとクラウドではシークレット、テンプレート、ネットワークポリシーが別々に管理される。

<https://zenn.dev/sun_asterisk/articles/e9b50f09839def>

- Planner はアプリを探索してテスト計画 (`specs/*.md`) を作り、Generator は計画の手順をブラウザで確かめながらテスト (`*.spec.ts`) を書き、Healer は失敗したテストを再実行・調査して修正する。
- 「エージェントの実体は「指示文」と「Playwright の MCP サーバー」の組み合わせです。」
- Playwright 1.56.1 が生成する Healer の指示文には、セレクタを現在の画面に合わせる更新、アサーションと期待値の修正、テストが正しいと確信できるのに失敗が続く場合の `test.fixme()` による除外が含まれる。
- これについて「対話的に使うなら便利ですが、無人で動かすと、プロダクトのバグをテストの修正で隠してしまうおそれがあります」と指摘している。
- 独自に足したのは、ツール権限を絞った CI での非対話実行 (`scripts/run-agent.mjs`)、変更できるファイルの制限と skip などの禁止 (`scripts/guard.mjs`)、既存の Page Object だけを変更できる Healer、失敗を Healer に渡すか人間に返すかの分類 (`scripts/classify.mjs`)、人間の承認。
- Gate 1 では、PR レビューを経て main にマージされた要件ファイル (`requirements/*.md`) だけをエージェントに渡す。
- Gate 2 では、生成・修復の結果を必ず Draft PR にし、人間のレビューを経てマージする。
- agent ジョブ (修復側は heal) は Copilot のトークンをエージェントのステップだけに渡し、書き込み権限を持たない。
- verify ジョブはトークンも書き込み権限も持たず、新しい環境でパッチを検査・実行し、「ここの結果を正とする」。
- `contents` と `pull-requests` の書き込み権限を持つのは pull-request ジョブだけで、検証済みのパッチから Draft PR を作り、すべてのジョブが `actions/checkout` に `ref: ${{ github.sha }}` を指定する。
- `workflow_dispatch` は選んだブランチのワークフロー定義で動くので、ワークフロー内の「main 以外なら止める」は別ブランチで消せば回避でき、「そこで、境界は GitHub の設定で守ります」として、Environment `e2e-dev` のデプロイ元を `main` に限り、main を保護して PR のレビューを必須にした。
- 2026-09-25 に確認した環境は、ランナーの Node.js 22 (Copilot CLI の npm 版は 22 以上が必要)、`.github/chatmodes/` 形式の @playwright/test 1.56.1、自動更新を切った @github/copilot 1.0.78、ガードの AST 解析用の TypeScript 5.9.3。
- `run-agent.mjs` は `.chatmode.md` を Copilot CLI のカスタムエージェント (`.github/agents/e2e-<role>.agent.md`) に変換して `-p` で動かし、非対話モードでは事前に許可していない操作は拒否される。
- 主なフラグは `--max-ai-credits` (既定 30、`E2E_AGENT_MAX_CREDITS`)、`--available-tools`、`--allow-tool=playwright-test(<tool>)`、`--deny-tool=shell`、`--no-ask-user`、`--no-auto-update`、`--disable-builtin-mcps`、`--secret-env-vars=COPILOT_GITHUB_TOKEN`。
- モデルは変数 `E2E_AGENT_MODEL` で指定し、dry-run の例は `claude-sonnet-5`。
- MCP サーバーはリポジトリのルートを `cwd` にして `playwright run-test-mcp-server --headless --config <root>/playwright.config.ts` で動かし、エージェント間の受け渡しは `specs/<name>.md` などのファイルで行う。
- ワークフローは `e2e-generate.yml` (入力 `requirement` を `^[a-z0-9-]+$` で検証する `workflow_dispatch`) と `e2e-heal.yml` (`workflow_dispatch` と、平日 10:00 JST の `cron: '0 1 * * 1-5'`) の 2 本で、どちらも `permissions: {}` と共通の `concurrency` グループを使う。
- Generator は最大 3 回試し、ガード違反かテスト失敗ログの末尾 60 行を次の回に渡し、Healer は最大 2 回で、タイムアウトは agent が 45 分、heal が 30 分。
- verify ジョブは新しいテストを `--retries=0 --repeat-each=3` で実行し、「生成したテストを 3 回連続で実行するのは、不安定なテストを見つけるためです」とする一方、成功してもアサーションの実行やテストの質は示さないと断っている。
- ガードは、Generator には `specs/*.md`、`tests/**/*.spec.ts`、`tests/pages/*.ts` の新規追加だけを、Healer には既存の `tests/pages/*.ts` の変更だけを許す。
- 禁止するのは、`test.skip`・`only`・`fixme`・`fail` の追加、`expect` や `test` の別名・再定義、Node.js の組み込みモジュール、`require()`、動的 `import()`、`eval()`、`fetch()`、`process`・`globalThis`、テストファイルでの直接のロケーター、Page Object 内の `expect`。
- 分類は終了コード、JSON レポート、トレースから pass・heal・escalate に分け、ロケーター系のエラーは Healer へ、`unexpected value`、`expected-http` 注釈で宣言していない 4xx・5xx の応答、`@no-heal` タグ付きのテスト、flaky なテストは人間へ回し、1 件でもエスカレーションがあれば全体を人間に返す。
- 2026-09-25 のサンプルの実行では、Playwright のテストが `4 passed`、ガードと分類のテストが `pass 26` / `fail 0` だった。
- 仕込んだ 5 種類の不具合のうち `renamed`、`status-role`、`bug-500`、`reworded-error` は意図どおりに分類されたが、ログアウトが消える `bug-no-logout` は Healer 行きに誤分類された。
- 実プロジェクトのローカルでの実行 (2026-09-10) では、認証まわりの高リスクな要件で Planner が計画を作らずにエスカレーションし、`process.env` を参照したテストがガードに拒否され、再生成したテストは検証環境で 3 回連続成功したが、Healer の実行は確認できていない。
- 実プロジェクトの GitHub Actions での実行 (09-10〜11) では、起動、入力と接続先の確認、固定版 CLI の起動までは成功したが、MCP サーバーがブロックされて生成は完了しなかった。
- `GITHUB_TOKEN` では CLI が「Failed to fetch MCP registry policy: 403 Forbidden.」を記録して標準以外の MCP サーバーを止めており、「Copilot Requests」権限だけの Fine-grained PAT ではローカルで動いたが、Actions 上では確かめていない。
- 「受け入れ条件のうち、③と④をエンドツーエンドで確認したことはありません」とあり、Healer による壊れたロケーターの修復と、仕込んだバグが Healer に渡らずエスカレーションされることは確かめられていない。
- ガードはテストの意味や Page Object のメソッドの動作が変わっていないことを保証せず、「HTTP エラーを伴わないバグ（ボタンが消えるなど）は、「ロケーターが見つからない失敗」と区別できません」とし、シェルを禁じても `browser_evaluate` による JavaScript の実行やブラウザ経由の通信は防げないと認めている。
- 1.0.78 に固定した CLI が以前ダウンロードされた 1.0.83 で動いていた問題は、`COPILOT_AUTO_UPDATE=false`、`--no-auto-update`、実行ごとの `COPILOT_HOME` で解決し、失敗時のスナップショットにパスワード欄の値が残ったため、テスト用アカウントは権限のない専用のものにする。
