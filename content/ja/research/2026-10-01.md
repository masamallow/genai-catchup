<https://openai.com/index/introducing-dots/>

- dots は GPT-6 Astra で動く常時稼働のエージェントで、1 つずつ専用のクラウドコンピューターを持ち、フィードバックから学び、ユーザーの目標に向けて 24 時間動く。
- プラグインのエコシステムを通じて 4,000 を超えるアプリにつながる。
- ChatGPT、Slack、Teams、音声通話から話しかけられ、テキストメッセージには今後対応する。
- 作業は dot 自身のクラウドコンピューターとブラウザで行い、ユーザーはそのコンピューターを開いて作業を確かめられ、手元のノート PC への接続は任意の権限になる。
- OpenAI 社内では、Slack に報告されたバグの調査を dots が始め、新しいデザインを動くアプリにしており、外部の早期テスターの dot は請求書の出し忘れに気づいて作成し、本人の承認後に送った。
- ユーザーと作業していないあいだ、dot は読み取り専用に制限したツールで「proactive research」を行い、メッセージの送信、アプリの内容の変更、ブラウザやコンピューターの操作はできない。
- 悪意のある指示への防御と有害な挙動の監視を組み込み、監視が安全上の懸念を検知すると dot の作業を一時停止または停止できる。
- 単独で動く場合と承認を求める場合の組み込みルールがあり、Custom Rules で特定の操作を許可・承認必須・禁止にでき、Activity View でバックグラウンドの作業を追える。
- アカウントに影響する操作や情報の共有は、ユーザーの指示・Custom Rules・安全要件と照らす auto-review を通り、パスワード変更のような操作は常にユーザー自身が行う。
- 保存済みのパスワードでのサインインは、パスワードをモデルに見せずに行う。
- Business・Enterprise・Edu のデータは既定で学習に使わず、proactive research や dot 自身のメモでも直接は学習しない。
- 専門の dot (specialist dots) は組織内の役割に合わせた固有の ID・認証情報・システムへのアクセスを持ち、調達、請求書処理、メールマーケティング、カスタマーサポート、商取引契約での社内テストをもとに、企業とのパイロットから始める。
- Microsoft と組んで、Agent 365 のガバナンスとセキュリティの仕組みで専門の dot を管理できるようにする。

#### [A] OpenAI — Codex Cloud overview and cloud environments (2026-10-01 取得時点)

<https://learn.chatgpt.com/docs/environments/cloud-environments.md>

#### [A] OpenAI Developers — MCP Events build guide (2026-10-01 取得時点)

<https://developers.openai.com/plugins/build/mcp-events>

- MCP Events により、ChatGPT は新しいメッセージ、内容の更新、状態の変化など MCP サーバーからの更新を購読し、一致するイベントが購読したチャットに届くと、ユーザーの指示どおりに動く。
- 要件は MCP 2.0 (プロトコルのバージョン `2026-07-28`)、購読の永続的な保存、コールバック URL への外向きの HTTPS、プラグインに設定したサーバー。
- ChatGPT は草案の Webhook による配信とコールバックの検証に対応し、ポーリング、ストリーミング、草案の `gap` と `terminated` の制御通知には対応しない。
- サーバーは `server/discover` で `"events": {}` を宣言し、`events/list` (`name`、`description`、`delivery`、`inputSchema`、`payloadSchema` を持つ定義)、`events/subscribe`、`events/unsubscribe` を実装する。
- 購読の際 ChatGPT はイベント名、絞り込みの `arguments`、コールバック URL、Standard Webhooks の HMAC 署名に使う `whsec_` のシークレット (24〜64 バイト) を送り、サーバーは `id`、`refreshBefore`、`cursor`、`truncated` を返す。
- 配信を有効にする前に、サーバーは使い捨ての新しいチャレンジを載せた署名付きのリクエストでコールバックを検証し、受け手はそれをそのまま返し、失敗すると `-32015` (`CallbackEndpointError`) になる。
- コールバックは HTTPS に限り、サーバーはプライベートやローカルのアドレスを遮断し、リダイレクトに従わず、DNS リバインディングを防ぐため接続時に宛先を検証する。
- イベントは `eventId`、`name`、`timestamp`、`data`、`cursor` を持ち、1 リクエストに 1 件で、`webhook-id`、`webhook-timestamp`、`webhook-signature`、`X-MCP-Subscription-Id` のヘッダーを付け、大きさは最大 256 KiB。
- 再送ではイベント ID を保ったまま署名を作り直し、`410` と `413` は再送せず、イベントは順不同で届きうるので、書き込みのツールは冪等にする。
- クライアントは `refreshBefore` の前に最後のカーソルを付けて購読を更新し、再生できるイベントはカーソルから再開し、`truncated: true` は履歴が失われたことを示す。
- ペイロードには要約を載せて全体は読み取りツールで取らせ、ユーザーが書いたテキストはデータとして扱い、モデルへの指示をペイロードに入れない。
- テストの確認項目には、取り消されたアクセス、不正な署名、重複、集中、操作が元のアプリのデータを変えるときのフィードバックループが含まれる。

#### [A] MCP Triggers and Events WG — MCP Events design sketch, by Peter Alexander (草案の日付 2026-02-19、2026-09-08 に main へマージ)

<https://github.com/modelcontextprotocol/experimental-ext-triggers-events/blob/main/docs/design-sketch-proposal.md>

- 草案は `poll` (`events/poll`)、`push` (長く開く `events/stream`)、`webhook` の 3 つの配信方式を定め、どれも必須ではない。
- 仕様と SDK の範囲がおよそ 3 倍になっても 3 方式を残したのは、サーバーレスのサーバーは push できず、NAT の内側のクライアントは Webhook を受けられず、コストを気にするクライアントはポーリングすべきでないと、展開の形が分かれるため。
- 購読の鍵は主体、コールバック URL、イベント名、正規化した JSON の引数の組で、Webhook の方式には認証された主体が要る。
- 既存の検証ライブラリがそのまま使えるよう Standard Webhooks を採り、受け手は 5 分より古いタイムスタンプを拒み、応答のタイムアウトは約 5 秒が一般的とする。
- コールバックの検証は必須で、チャレンジのやりとり、サーバーの許可リスト、事前の別経路での検証、受け手が公開する well-known の文書の 4 つの方法のいずれかを使う。
- 配信は最低 1 回で、順序や厳密に 1 回の保証はなく、v1 にフロー制御はなく、イベントを受け取っても行動する権限は生じない。
- 未解決の問いには、SDK がエージェントのフレームワークにイベントをどう見せるかや、1 つの購読で複数のイベント名を扱えるかがある。

- 今のモデルが失敗するケースを選ぶ (敵対的なサンプリング) のは、そのモデルの失敗の癖を測るだけで、アプリにとって何が難しく価値があるかを測らないとして退けている。

- いくつかのケースを採点してユーザーなら違う点を付けたかを尋ね、同じ出力を 2 回採点する、タイムアウトや切れた回答を調べる、ベースラインがすでに約 95% 以上なら警告する、の 3 つの確認を行う。
- hillclimb は目標 (性能か、同じ性能でのコスト) を聞き、ケースを学習用とテスト用にランダムに分け、評価のノイズが意味のある最小の改善より小さいかを確かめる。

- 2〜3 回改善が止まると残る失敗を原因別に仕分け、最後はテスト用で最もよい版にコードを残し、結果を信頼区間付きで報告する。

- 同梱の `feature-pipeline` は思考量 high の Claude Opus 5 で始まり、思考量 Extra high の `claude-opus-5.5` と `gpt-5.6-sol` のレビュアーを使う。
- IDE・CLI・Web の下にあるランタイムは 1 つで、Workflow はほかのエージェントの作業と同じクレジットの仕組みで課金され、複雑なものほど多くのクレジットを使う。

#### [A] Kiro docs — Workflows: overview, authoring, running and examples (2026-10-01 取得時点)

<https://kiro.dev/docs/workflows/authoring/>

- レシピは `name` と `steps`、任意の `inputs`・`modelId`・`effortLevel` を持ち、ノードは `step`、`sequence`、`repeat` (`maxIterations` と `onMaxIterations`)、`parallel` (`joinPolicy` は `all`・`allSettled`・`any`)、`watch` の 5 種類。
- 上限は step のノード 50 個と入れ子の深さ 8 で、ステップ間の出力は `{{previous.output}}` や `{{step-id.output}}` のテンプレートで渡し、ステップ間のプロンプトインジェクションに備えて区切りで包む。
- ステップは `send_message` の信号 (成功、実行を止める警告、エラー、情報) で報告し、止める条件には `containsText`、`completionSignal`、`fileCheck`、`stopWhen` がある。
- `watch` のハンドラーは GitHub のプルリクエスト (既定 60 秒ごと、最短 30 秒) やコマンドをポーリングし、モデルのターンを使わずにレビューや CI を待てる。
- Workflows を有効にすると、メインのエージェントは `invoke_sub_agent` ではなく `run_workflow` で仕事を任せ、計画はステップの境目で見直せる。
- 同時に動く実行は分離されず、Workflow は worktree もブランチも作らず、止めてもファイルの変更は戻らず、並列の分岐で時間が縮むとは限らないとドキュメントは注意している。
- 設定項目が見当たらなければ、そのアカウントではまだ使えない。
