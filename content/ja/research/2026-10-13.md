#### [A] OpenAI — Decisions guide (2026-10-06, as fetched on 2026-10-13)

<https://developers.openai.com/api/docs/guides/decisions>

- API はパブリックベータで、一般提供は今後数週間のうちの見込みとされ、モデルは `gpt-6-luna` だけで、リクエストは専用の `POST /v1/decisions` に送る。
- リクエストのフィールドは `model`、`input` (テキストの文字列か、`input_text` と `input_image` のパーツを持つユーザーメッセージで、すべての質問に共通)、`questions` の 3 つである。
    - レスポンスの `answers` 配列は、質問ごとの `name` をそのまま返す。
- `predicate` の質問は条件が真である確率 `probability` を 0〜1 で返し、`choice` の質問は渡した値の 1 つと、`probabilities` 配列、それとは別の `confidence` を返す。
- `score` の質問は 0 から数えるレベルの番号の確率加重平均を返すので、3 段階の深刻度に 0.1、0.7、0.2 の確率が付けば、2 つのレベルのあいだの 1.1 になる。
- 同じ入力についての独立した質問は 1 つの `questions` 配列にまとめて種類を混ぜられるが、前の答えに依存する判断には 2 回目のリクエストが要る。
- どの質問も型 `refusal` で返ることがあり、SDK のサンプルはそれで分岐する。
- 抽出したフィールド、文章での説明、ツール呼び出しは、Responses API の Structured Outputs か function calling に回すよう案内する。
- 画像はインラインの base64 の data URL に限り、ホストされた HTTP(S) の URL と `file_id` の入力はこのエンドポイントでは使えないとする。
- しきい値はラベル付きの例と、偽陽性と偽陰性のコストから決め、`other` のような逃げ道の選択肢を加えるよう勧める。
- 入力は 100 万トークンあたり $0.10 で、キャッシュの読み書きと出力トークンには課金しないが、リージョン処理の割増と長いコンテキストの倍率はかかり、`gpt-6-luna` へのほかのリクエストは通常のモデル料金のままである。
- 対象の顧客向けに Zero Data Retention と HIPAA に対応し、データレジデンシーとリージョン処理は米国と欧州 (EEA とスイス) で使える。
- SDK のサンプルは `client.decisions.create(...)` を呼び、Python 3.26.0、JavaScript 7.30.0、Go 3.73.0、Ruby 0.101.0、Java 4.78.0 のいずれかが要り、Playground は platform.openai.com/decisions にある。
- ガイドの見出しは型付きの答えを Responses API の約 10 倍の速さで返すとうたうが、ベンチマークは示さない。

#### [A] OpenAI — API reference: Create a decision (as fetched on 2026-10-13)

<https://developers.openai.com/api/reference/resources/decisions/methods/create>

- 1 つのリクエストに画像を最大 128 枚、base64 の data URL か公開アクセスできる HTTP(S) の URL で渡せるとしており、ガイドと食い違う。
    - ファイル ID、ほかのロールのメッセージ、関数呼び出し、ファイル、音声、item の参照は拒否され、`detail` には `low`、`high`、`auto`、`original` を指定できる。
- `choice` の質問は 2〜255 個の重複しない選択肢を取り、値は文字列か真偽値で、同じ表記の文字列と真偽値は別の値として扱う。
- 答えは質問した順に返り、拒否された質問は質問の `name` (または `null`) だけを持ち、ほかの質問にはそのまま答えが返る。
- レスポンスの `usage` は `input_tokens`、`cached_tokens`、`cache_write_tokens`、`output_tokens`、`reasoning_tokens` を報告し、例では出力トークンが 0 で、任意の `safety_identifier` (128 文字まで) でエンドユーザーを識別できる。

#### [A] SQLite — Vec1 Vector Extension (2026-10-01)

<https://sqlite.org/vec1.html>

- vec1 は SQLite の仮想テーブルのインターフェースで近似最近傍 (ANN) の検索を提供し、距離はユークリッド (L2) とコサインで、外部依存のないポータブルな C で書かれ、x86 では AVX2、ARM では NEON を使う。
- インデックスは OPQ (optimized product quantization) を使う IVFADC (inverted file with asymmetric distance computation) で、拡張全体が `vec1.c` の 1 ファイルに収まる。
- このページはいまでは SQLite の本体のドキュメントの中にあり、最終更新は後述の trunk へのチェックインと同じ分の 2026-10-01 11:21:38Z で、現在のリリースをバージョン 0.8 とし、SQLite のソースツリーの `ext/vec1/vec1.c` にリンクしている。
- 完全な SQLite のソースツリーの最上位で `./configure && make vec1.so` (macOS では `vec1.dylib`)、Windows では `nmake /F Makefile.msc vec1.dll` でビルドでき、どちらも実行時に CPU に合わせて AVX2 かスカラーのコードを選ぶ 1 つのバイナリになる。
    - `cc -g -O3 -DNDEBUG -mavx2 -mfma vec1.c -shared -fPIC -o vec1.so` のように手でビルドすると、AVX2 のバイナリは AVX2 のない x86-64 の CPU では動かず、`ext/vec1/Makefile` の `vec1multi.so` のターゲットが複数の x86-64 のレベルに対応する。
- ロードマップは日付なしで、テストと最適化の追加、IVFADC に代わるグラフベースのインデックス (HNSW か DiskANN か、その変種かと疑問形で挙げる)、速い `SELECT count(*)`、wasm での SIMD、float32 に加えて int8、int32、float16 の要素、パーティションキー、浮動小数点のバイト順が違うプラットフォームのデータベース、距離としての内積、マルチスレッドのクエリを挙げる。

#### [A] SQLite — Vec1 User Manual and Vec1 Reference Guide (2026-10-01)

<https://sqlite.org/vec1doc.html> / <https://sqlite.org/vec1ref.html>

- `CREATE VIRTUAL TABLE t USING vec1(vector, meta1, ...)` は 1 つのベクトル列と 0〜255 個の型のないメタデータ列を宣言し、クエリはテーブルを表値関数として `SELECT rowid FROM t(:v, '{K:10}')` のように使い、隠し列 `distance` を持つ。
- ベクトルはマシンのバイト順の 32 ビット IEEE 浮動小数点数の BLOB で、有限の値だけを受け付け、`vec1_from_json()` と `vec1_to_json()` が JSON の配列と変換し、次元は最初の挿入かモデルで決まる。
- モードは 3 つあり、インデックスなし (既定で、1 行に 1 ベクトル)、flat (ベクトルを大きな BLOB に詰め、全件探索が 2 倍以上速い)、学習済みのモデルが要る ANN である。
    - マニュアルは、厳密な結果が要るとき、約 5,000 ベクトル未満のとき、学習データがないか用意しにくいときは厳密 (NN) モードを勧める。
- ANN のモデルは学習用のセットに対する集約関数 `vec1_train(vector, '{nbucket:1024, quantizer:"opq", codesize:32, distance:"cos"}')` が返す BLOB で、`INSERT INTO t(cmd, arg) VALUES('rebuild', :model)` がそれを入れてインデックスを作り直し、これはデータに応じていつでも何度でも行える。
    - 学習と再構築は `vec1_config('nthread', N)` で複数のスレッドを使い、あるホストで学習したモデルは浮動小数点のバイト順が同じ別のホストでも使える。
- 推奨の設定: `nbucket` は想定行数の平方根程度 (1,000,000 ベクトルなら 1,000)、`quantizer` はニューラルネットワークの埋め込みには "opq"、SIFT のような人手で設計した記述子には "pq" とし、"bq" (二値で、既定ではランダム化した Walsh-Hadamard 変換が付く) は学習時間を最小にしたいときだけ使う。
    - `codesize` は OPQ なら 32 バイト (再現率が低すぎれば 48 か 64)、PQ と BQ なら次元数の 1/8〜1/16 で、学習用のサンプルは 100 × `nbucket` ベクトル程度でたいてい足りる。
- `nprobe` はクエリが走査するバケットの割合で、1.0 未満なら割合、1.0 以上ならバケットの数を表し、クエリごとか接続ごとに `vec1_config('nprobe', ...)` で設定でき、既定は 0.05 である。
- ANN の距離は圧縮したコードの上で計算され、vec1 は自動では再ランキングしないので、マニュアルは約 100 件の候補を取り出し、`LIMIT 10` の前に `vec1_l2_distance()` か `vec1_cos_distance()` で SQL の中で並べ直すよう求める。
    - マニュアルは、vec1 の ANN のクエリでは再ランキングがたいてい欠かせないと念を押している。
- 絞り込みの仕組みは 2 つある: `streaming:1` は SQLite が求める限り K を超えておおむね距離の昇順で行を返し続け (結合したテーブルにあるメタデータ向け)、メタデータ列への `<`、`>`、`=`、`>=`、`<=`、`IS`、`IS NULL`、`IS NOT NULL` の制約は、上位 K 件を集める前に ANN の探索の中で適用される。
- `WHERE in_stock AND price < 20000` の `in_stock` のような比較演算子のない項は取り出したあとに適用されて黙って K 件より少なくなるので、マニュアルは `in_stock = 1` と書き、結合、集約、`ORDER BY` がなく WHERE のすべての項が探索の中で適用されるクエリなら、見える `LIMIT` が K の代わりになる。
- 上限: K は 0〜33,554,432 (2^25)、`nbucket` は 2〜65,536 (0 で転置ファイルを無効化)、`codesize` は 0〜256 バイト (目安) で、`vec1_l2_distance()` はユークリッド距離の 2 乗を返し、`vec1_cos_distance()` は正規化していない入力でも 0.0〜2.0 を返す。

### メモ

- 2 つのドキュメントのサイトでバージョンが食い違う。
    - `sqlite.org/vec1.html` (10-01) は、10-06 まで 0.7 を名乗っていたコードを 0.8 とし、`sqlite.org/vec1` とそのベンチマークのページはいまも 0.7 とする。
    - 新しいロードマップは、1.0 までに要る機能はもうないという旧版の一文を削り、テストの充実を最初に置き、1.0 の日付を示さない。
    - 移動に告知はなく、3.54.0 のリリースノートは何も触れず、Nuno Cruces が 10-11 に告知を求めた。
- 3.54.0 に入ったといってもソースツリーの話である: 3.54.0 のタグは 0.8 の `ext/vec1/` を含むが、`main.mk` は amalgamation とすべての配布パッケージから外している。
    - したがって、システム、プラットフォーム、言語に同梱された SQLite を使うアプリケーションには、別にビルドした `vec1.so` と、拡張の読み込みを許す SQLite が要るが、どのプラットフォームが許すかは確かめていない。
    - 見つかったビルド済みの入手経路は APSW の PyPI の wheel (Python) と ncruces/go-sqlite3 (Go、0.7) で、APSW 3.54.0.0 (10-12) が 0.8 を同梱しているかは確かめていない。
- ローカルの RAG で効いてくる sqlite-vec との違い:
    - インデックス: vec1 には文書化された ANN の経路 (PQ、OPQ、二値のコードによる IVF) と厳密な flat の探索があり、sqlite-vec の安定版には ANN がなく、rescore、IVF、DiskANN のインデックスは 05-18 以降リリースのないアルファにある。
    - 絞り込み: どちらもメタデータの制約を探索の中で適用し (vec1 は `!=` なしで型のない列を 255 まで、sqlite-vec は型付きの列を 16 まで)、vec1 には結合したテーブル向けのストリーミングがあり、パーティションキー (sqlite-vec のドキュメントの例ではユーザーごとにシャーディング) は sqlite-vec にしかなく、vec1 はロードマップに載せている。
    - 要素の型: vec1 は float32 だけを格納してインデックスの中で圧縮し、sqlite-vec は int8 と二値のベクトルも格納する。
    - 距離: vec1 は L2 とコサインだけで内積がないが、情報源の主張ではなく推論として言えば、正規化した埋め込みならコサインは内積と同じ順位になるので、この差が効くのはおもに正規化していない埋め込みである。
    - ブラウザ: sqlite-vec はいま WASM で動き、vec1 も Nuno Cruces のようにシングルスレッドで Wasm にコンパイルできるが、Wasm の SIMD はまだなく、彼の SIMDe の経路はつなぎである。
- 増え続ける RAG のコーパスでは学習がおもな運用のコストになる: ANN のモデルには代表的なサンプル (100 × `nbucket` ベクトル程度) が要り、データの分布がずれたら学習し直して `rebuild` する必要がある。
    - Dan Kennedy は 7 月に学習の要らないオンラインのモードを次の重点としたが、10-01 のロードマップはグラフベースのインデックスしか挙げず、それで学習が要らなくなるのかは書いていない。
    - 0.7 の投稿の RaBitQ の量子化器はドキュメントにその名前では出てこず、載っているのはランダム化した Walsh-Hadamard 変換付きの二値の量子化 "bq" だけなので、"bq" がその量子化器かは確かめられていない。
- 再現率は再ランキングしだいである: agnews では、圧縮した距離での上位 10 件に本当の上位 10 件の約 62% しか入らないので、検索側は約 100 件の候補を取って SQL の中で並べ直す必要があり、マニュアルはそれを利用者に任せている。
- フットプリントは文書化されていない: ベクトルあたりのディスクやメモリを示す情報源はなく、情報源の主張ではなく推論として言えば、再ランキングは格納した `vector` の列を読むので、テーブルはコードと並べて元のベクトルも持っているとみられる。
- 頑健性: 8 月の記録はテストが不十分だという以前の注意を裏づけ、壊れたメタデータの配列や丸め誤差の修正は 10 月にも続いた。
    - 8 月の報告を誰が出したかは vec1 のフォーラムにログインしないと見えないので、Lee Butterman がエージェントで見つけたバグと結びつける根拠は時期の一致だけである。
    - SQL からたどれるメモリ安全性のバグが半ダースを超えるという数は Lee Butterman の主張で、裏づける情報源はない。
    - SQLite の[関数フラグ](https://sqlite.org/c3ref/c_deterministic.html)によれば、`SQLITE_DIRECTONLY` は関数を最上位の SQL からだけ実行できるようにしてビュー、トリガー、スキーマからは実行させないので、関数を呼ぶようにスキーマを書き換えたデータベースファイルへの守りになる。
- mattn はファイルのヘッダーから開発の始まりを 1 月ごろとみているが、ヘッダーの日付は 2026-02-04 で、Dan Kennedy の vec1 についての最初のフォーラムの投稿は 2026-02-26 である。
- 規模の目安として、agnews の実行はデスクトップの CPU の 1 スレッドで、1024 次元の 77 万ベクトルに対し再ランキング込みで毎秒約 1,300〜2,250 クエリ、再現率 0.93〜0.96 を出しており、3 月のフォーラムの利用者が sqlite-vec のフォークが動かなくなったという 10 万ベクトルを大きく超える。

    - 注目度を支えているのは日本の場で、10-13 時点ではてなブックマーク 236 users、Zenn 111 いいねだった。
- ここでの事実はどれも WebFetch だけに頼っておらず、vec1 のフォーラム <https://sqlite.org/vec1/forum> はログインが要るので読んでいない。

### 実践やアウトプットの提案

- コンパイルなしに (`pip install apsw` のあと `apsw.sqlite_extra.load(db, "vec1")`) vec1 を読み込むか、3.54.0 のソースから `vec1.so` をビルドし、チームの RAG のチャンクをいつもの埋め込みモデル (日本語なら multilingual-e5 など) で flat のテーブルと ANN のテーブル (`nbucket` は √N 程度、`quantizer:"opq"`、`codesize:32`) に入れる。
    - flat のテーブルを正解として、SQL での再ランキング付きで K を 10、50、100、nprobe を 0.02、0.05、0.1 にしたときの recall@10 と、開発者のノート PC でのレイテンシを測り、agnews の数字 (K=100 で 0.93〜0.96) が日本語のテキストでも成り立つかを見る。

- マルチテナントの RAG の使い方で絞り込みを試す: 探索の中で `tenant_id = ?` と制約する `tenant_id` のメタデータ列、黙って K を減らす `WHERE flag AND ...` の落とし穴、文書のテーブルとの JOIN を伴う `streaming:1` である。
- 1 つの SQLite のファイルで、FTS5 の BM25 と vec1 の候補を 1 つの SQL 文の中で reciprocal rank fusion によって合わせるハイブリッド検索を作り、チームの評価用の質問でベクトルだけの検索と比べる。
- 学習のあとに新しい文書を挿入して再現率の推移を追い、増え続けるコーパスでどのくらいの頻度で `vec1_train()` と `rebuild` が要るかを決める。
- Go のサービスや端末上のビルドには ncruces/go-sqlite3 の `ext/vec1` (cgo なし、vec1 0.7) を試し、Wasm の SIMD がないことでスループットがどれだけ落ちるかを測る。
- アウトプット: ローカルの RAG のための SQLite のベクトル検索を 1 ページで比べ (vec1 0.8 と、sqlite-vec 0.1.9 とその 0.1.10 のアルファ)、インデックスの種類、絞り込み、要素の型、距離、配布の経路、成熟度を、チームで測った再現率とレイテンシとともに並べる。

- 主張は、航空の規制当局が保たせているのは自動化なしで飛ぶ力ではなく自動化から引き継ぐ力であり、エンジニアも AI なしで書く力ではなく AI から引き継ぐ力を保つべきだというもので、見出しには「目的は AI なしで書けることではなく、AI から引き継げること」と掲げる。
- 論拠として、FAA SAFO 13002 (2013-01-04)、FAA の最終規則 78 FR 67800 (2013-11-12)、飛行経路管理システムについての PARC/CAST の報告書 (2013)、CAST SE-30 (2008)、SAFO 17007 (2017-05-04)、FAA AC 120-123 (2022-11-21)、EASA SIB 2013-05R1、そして ICAO Doc 9995、EASA NPA 2018-07、Opinion 08/2019 の根拠に基づく訓練 (EBT) を挙げる。
- Mermaid の図は、航空のループ (自動操縦を使う、監視する、異常を認識する、解除する、引き継ぐ、回復する) を AI 開発のループ (AI に実装させる、出力を監視する、誤った実装や判断を認識する、AI から人に切り替える、コードを読んで原因を探す、直して回復する) に対応させる。
    - 表は、自動操縦をコーディングエージェントに、飛行計画を要件と設計に、モードアウェアネスを AI が何をしているかの理解に、シミュレーター (FSTD) を障害解析とレビューの演習に、EBT を本番障害からポストモーテム、演習の教材への流れに対応させる。
- 提案する演習: Terraform や CDK に仕込んだ危険な設定を見つける、`"Action": "*"` や不要な `"Resource": "*"` のような IAM の過剰な権限を洗い出す、ALB が 502 を返す原因をアクセスログとターゲットの設定から特定する、AI が問題ないとしたコードから問題を拾う、データベースの削除につながる IaC の変更をレビューで止める、AI が書いたテストをすり抜ける障害を想定する、AI が提案した誤った修正を検証する。
- 例題: 本番と検証で共有するスタックの定義で、AI が承認した `rds.DatabaseInstance` への 2 行の差分が、`removalPolicy` を `cdk.RemovalPolicy.RETAIN` から `DESTROY` に、`deletionProtection` を `true` から `false` に変える。
    - 想定解答は本番向けにはこれを止めるというもので、`removalPolicy` は CloudFormation の `DeletionPolicy` と `UpdateReplacePolicy` の両方を決めるので、スタックの削除でも、どんな置き換え (新しいインスタンスを作ってから古いものを消す) でも本番のデータベースが消え、それを止める削除保護も残っていない。
- 日常の作業では、1 日に決まった行数を読むような一律のルールを、ノルマを避けよという SAFO 17007 の助言になぞらえて退け、AI のレビューを通ったあとでもリスクの高い差分 (IAM ポリシーの変更、データを消しうる IaC、ネットワークの構成) だけは意図して手で読むことを勧める。
- EBT からはループを借りる: 本番の障害のもとになったコードや設定を匿名化し、小さな再現環境に作り直してチームで定期的に演習し、合否を付けると課題は易しく報告は控えめになりがちなので合否は付けない。
    - AI が提案した誤った修正、AI のレビューが見逃した差分、AI が書いたテストをすり抜けた障害のような AI の時代の素材は、automation surprise の訓練教材になる。
- 認める限界: ソフトウェアの障害の多くはロールバックでき、訓練を義務づける規制はなく、1 人のエンジニアが複数のエージェントやリポジトリを見ることがあり、手動の操縦は身体技能に頼るがコードを読んで原因を特定するのは認知的な作業である。
    - そのうえで、ソフトウェアでの AI の誤りはコックピットのような警報のない、ほぼすべて静かなものなので、異常の認識が最も難しい段階であり、演習は AI が問題ないとするものから問題を見つけることを中心にすべきだと論じる。
- エージェントが操縦を担う PF (pilot flying) になれば人は監視役の PM (pilot monitoring) に回るが、航空の PM は PF として飛べる訓練を受けているので、実装の技能をゼロにしてよいわけではないとする。

#### [A] Claude Platform Docs — Multiagent orchestration (as fetched on 2026-10-13)

<https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration>

- 型 `multiagent_20261001` は 3 つの設定、つまり既定で有効の `subagents` と `workflows`、既定で無効の `advisor` をまとめる。
- サブエージェントではエージェントがターンごとに委任し、持続するスレッドに追加の指示を送れて、深さは 1 段、子のスレッドは同時に最大 25 であり、ワークフローでは Claude が自分では直接関わらずにエージェントを動かすプログラムを書くので、主スレッドはユーザーとの対話と実行の確認のために空いたままになる。
- ドキュメントは、複数のエージェントが要るたいていの作業、つまり多くの部分からなる作業、並列の作業、早く終わらせたい長い作業 (監査、移行、深い調査、照合など) にワークフローを勧める。
- 実行を始める API の呼び出しはなく、`user.message` からいつ始めるかを決めるのはエージェントで、それを誘導できるのはメッセージかシステムプロンプトだけである。
    - 許可のポリシーは実行の中のエージェントが呼ぶツールに適用され、実行を始めることには適用されない。
- 実行の中のエージェントは、ワークフローが定義するインラインのエージェント (ワークフローが書くシステムプロンプトとセッションのエージェントのモデルを使う) か、`workflows.predefined_agents` に挙げた定義済みのエージェント (最大 20 で、`subagents.predefined_agents` とは別の一覧) である。
    - 実行の一部のエージェントを別のモデルで動かすには、それをエージェントとして作ってそこに挙げる必要がある。
- 挙げたエージェントは作成か更新の時点で解決したバージョンに固定され、自身は `multiagent` を設定できず、リードのエージェントと同じ `inference_geo` をすべてが固定するか、どれも固定しないかのどちらかでなければならず、`{"type": "self"}` はエージェント自身の複製を挙げる。
- インラインのエージェントはセッションのエージェントの MCP サーバーとツールを受け継ぎ、vault の認証情報はすべてのスレッドに適用されるので、実行のアクセスを絞るには `workflows` の下で `inline_agents` を `{"type": "disabled"}` にして、より狭いエージェントを挙げる。
- すべてのエージェントがセッションのサンドボックス、ファイル、vault の認証情報を共有し、それぞれはコンテキストを分けたセッションのスレッドで働く。
- サンプルのシステムプロンプトは契約書のレビュー役に、数件を超える契約書のレビューを頼まれたら実行を始め、1〜2 件なら自分でレビューするよう指示し、追記の案として分け方 (契約書ごとに 1 エージェント、その後で全件を見直す 2 つ目のエージェント)、失敗の扱い (読めなかった契約書を対象外として挙げる)、1 時間の時間制限を示す。
- ツール名の接頭辞 `ant__` はいまでは予約されており、`ant__…` という名前のカスタムツールを持つエージェントは、ワークフローを有効にするのと同じ更新でツールの名前を変えるまで、更新も新しいセッションもすべて 400 のエラーで失敗する。
- 古い `coordinator` 型 (サブエージェントと advisor だけ) から移ると `multiagent` のブロック全体が置き換わるので、`workflows` と `subagents.inline_agents` を省くと両方が有効になり、サブエージェントの一覧を省くと空になる。
- セッションは作成時に設定を写し取り、`{"type": "disabled"}` でワークフローが止まり、既定が有効なので `null` を送ると有効に戻る。

#### [A] Claude Platform Docs — Workflow runs (as fetched on 2026-10-13)

<https://platform.claude.com/docs/en/managed-agents/workflow-runs>

- 実行は、実行、任意の名前付きのフェーズ、エージェントのスレッドの 3 層からなり、プログラムはその中でエージェントを展開し、あるエージェントの結果を別のエージェントに渡し、レビューが通るか回数が尽きるまで手順を繰り返し、失敗したエージェントを処理するか上に伝える。
    - 結果はセッションのエージェントではなくプログラムに届き、セッションのエージェントは実行が終わったときに、実行が何をしたかを読むターンを得る。
- 上限: 1 回の実行で同時に働くスレッドは 64 (API が保証する値ではない)、実行の全期間で起動するエージェントは 1,000 で、超えると実行は `thread_limit_error` で終わり、有効期間は既定で 24 時間 (エージェントが短くできる)、セッションあたりの開いた実行は既定で 10 (アイドルのものを含む) である。
    - 失敗したエージェントを新しいスレッドで再試行すると 1,000 スレッドを超えることがあり、サーバーには列挙されていないほかの上限もあり、1 つのセッションが全期間で始められる実行の数に制限はない。
- セッションのストリームのイベントは、`workflow_run.created` (`wrun_…` の ID、名前、説明、宣言した `phases` を持ち、どれもモデルが書いた文字列)、`workflow_run.status_running`、`workflow_run.status_idle`、`workflow_run.phase_started` と `workflow_run.phase_ended`、`result` を持つ `workflow_run.status_ended`、`workflow_run.error` である。
    - 実行のイベントは webhook を起動せず、実行を一覧するエンドポイントもないので、クライアントは再接続したあと、`types` のフィルターで過去のイベントを一覧して実行の状態を組み立て直す。
- 結果が `completed` でもワークフローが終わったという意味でしかなく、スレッドでの作業が失敗したりスレッドを作れなかったりしても `completed` で終わることがあり、エラーの結果は `timeout_error`、`program_error`、`thread_limit_error`、`unknown_error` である。
- 実行は入れ子にならず、実行を始められるのは主スレッドのエージェントだけで、実行のスレッドは子スレッド 25 の上限の対象外だが、エージェントはそれらに追加の指示を送れず、サーバーは実行の終わりまでに各スレッドをアーカイブする。
- ワークフローのコード、実行を始めて管理するツールの呼び出し、各スレッドがプログラムに返すものは見えず、ヒントとして、実行が終わってセッションがアイドルになってから、別の実行を始めずにワークフローを一字一句そのまま表示するようエージェントに頼むよう勧める。
- 実行を終わらせるクライアントのイベントはない: `user.interrupt` はエージェントのターンを止めるが実行は一時停止するか続くので、止めるには実行を止めるよう頼む `user.message` を送る必要があり、実行が開いているあいだにセッションをアーカイブや削除したり、その `agent` を更新したりすると、`workflow_run_open` の 400 が返ることがある。
- 実行が動いているあいだは、どのスレッドも働いていなくてもセッションは `running` のままで、作業が終わったと言えるのは、見えたすべての実行に `workflow_run.status_ended` が届き、そのあと `end_turn` の `session.status_idle` が届いたときである。
- 実行そのものに価格はなく、そのエージェントのトークンは各モデルの単価で課金されてセッションの予算に数えられ、1 つの実行の使用量はその `workflow_run_id` を持つスレッドの `usage` の合計である。
- 予算に達すると開いた実行はすべて一時停止し、働いているスレッドごとに 1 リクエストまで予算を超えうるが、一時停止中も実行の有効期間は減り続けるので、一時停止したまま放置した実行は `timeout_error` で終わることがある。
- 実行のモデルへのリクエストはほかのトラフィックとともに組織の Messages API のレート制限に数えられ、同じ作業に複数のスレッドが作られることがあるので、ドキュメントは 2 回呼ばれても安全なツールを求める。
- 例は 300 の契約書のうち支配権変更の条項を持つものを問い、フェーズ `Read the contracts` と `Reconcile the findings` を持つ実行が、41 件にあるという答えで終わる様子を示す (計測ではなく例示)。

### 実践やアウトプットの提案

- バグのテストを小さく再現する: 1 万〜2 万行のリポジトリに既知のバグを 10〜20 個仕込み、予算付きのセッションで単一のエージェントとワークフローをそれぞれ 3 回動かし、見つけたバグ、見逃したバグ、誤検知、トークン、`list_cost`、実行時間を記録する。
    - Anthropic が報告する差がチームのコードでも成り立つか、成り立つならどのくらいのコストの倍率でかを確かめられる。
- ドキュメントのサンプルをもとに最小の実行トラッカーを作る: `workflow_run.*` のイベントを追い、すべての実行が終わって `end_turn` のアイドルが続いてから作業を完了とみなし、再接続のあとは `types` のフィルターでイベントを一覧して状態を組み立て直し、スレッドの `usage` から実行ごとの費用を計算する。
    - 失敗する文書 1 つ、2 回呼ばれるツール 1 つ、割り込み 1 回、メッセージでの停止 1 回、予算による一時停止 1 回を試し、アプリケーションが実際に何を観測できるかを見る。
- どのエージェントでも有効にする前に、`workflows` を明示的に設定し (展開を望まないところ、とくに `coordinator` から移したエージェントでは無効にする)、始める条件と始めない条件の両方をシステムプロンプトに書き、Haiku 5.5 で動く定義済みのエージェントのような安いものを `workflows.predefined_agents` に挙げ、MCP のアクセスを絞るべきところでは `inline_agents` を止め、セッションは予算付きで作る。
- ルートハンドラーにまたがる認証チェックの漏れの調査のような同じ監査を、Claude Code のワークフローと Managed Agents の実行の両方で行い、スクリプトの見え方、同時実行数、承認、トークンの使用、経過時間を比べて、どの作業を開発者のマシンに置き、どれをサーバー側のジョブにするかを決める。
- アウトプット: サブエージェント、Managed Agents のワークフロー、Claude Code のワークフロー、自作の `claude -p` の呼び出しのスクリプトを、上限、課金、統制の点、実行を誰が止められるかで並べた 1 ページのチーム向けの判断表。
