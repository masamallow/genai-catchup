#### [A] Google AI for Developers — What's new in Gemini 4 Argon, Gemini 4 Argon model page and Long decode guide (2026-10-13, as fetched on 2026-10-15)

<https://ai.google.dev/gemini-api/docs/latest-model> / <https://ai.google.dev/gemini-api/docs/models/gemini-4-argon> / <https://ai.google.dev/gemini-api/docs/long-decode>

- `gemini-4-argon` は安定版のモデルで、テキスト、画像、動画、音声、PDF を受け取ってテキストを返し、入力、思考、出力で共有する 1,048,576 トークンのウィンドウを持ち、出力の上限は既定で 65,536 トークン、思考レベルは `low`、`medium` (既定)、`high` で、キャッシュは暗黙のキャッシュだけ、コンピューター操作はプレビューで、Live API には対応しない。
- Gemini API の long decode は Interactions API で `background: true` と 65,536 を超える `max_output_tokens` を指定して使い、サーバーが 64K トークンずつのホップで最大 24 時間生成して `store: true` が必須になり、バックグラウンドでないリクエストで 65,536 を超えると 400 エラーになる。
    - 代わりに GenerateContent ではクライアント側の継続が使え、1 リクエストあたり 20 分が上限で何も保存されず、Google はこれを Interactions API にも持ち込むとしている。
- ホップのたびにプロンプトとそれまでに生成したものすべてを入力として送り直すので、1,000 トークンのプロンプトから 200,000 トークンを出すと 4 ホップかかって入力は 397,216 トークンと報告され、繰り返す入力には暗黙のキャッシュの 95% 引きが効くが、思考だけのホップや、キャンセルや失敗の前に済んだ処理も課金される。
- 移行のチェックリストは、Argon は `max_output_tokens` のより多くを思考に使うので 32,768 以上に上げ、`temperature`、`top_p`、`top_k` (無視される) と明示的なキャッシュ (`cachedContents`) を外し、4,096 トークンから効く暗黙のキャッシュに頼り、クライアントのタイムアウトを 15 分以上にするよう求める。
    - Gemini Managed Agents の Antigravity のエージェント (`antigravity-preview-09-2026`) は `agent_config` のモデルとして `gemini-4-argon` を取る。

- main ブランチの履歴は 100 GB 近く、圧縮した作業コピーは 25 GB を超え、開発環境、エージェントのサンドボックス、研究のジョブを数える前に CI だけで 1 日 2,500 万回規模のチェックアウトがあり、素朴に取得すれば 1 日 600 PB を超える git のトラフィックになる。
    - Scion の前は shallow clone、sparse checkout、promisor remote、seed (blob ストレージに置いたリポジトリのスナップショット)、ピーク時には数百の社内の git のミラーに頼っており、マージが増えるにつれてどれも運用が難しくなった。
- クライアントのほぼすべてが定義上オンラインのエージェントとジョブなので、Scion は常に到達できるサーバーを前提にし、サーバーが履歴と blame に答え、コミットを作り、マージとリベースを行い、クライアントの `scn` は上限のあるローカルのオブジェクトキャッシュを持ち、作業コピーを展開し、ファイルシステムを監視する。
    - クライアントが使う問い合わせはすべて API でもあるので、自動の bisect や revert のパイプラインのような多くの CI のジョブとツールはローカルのリポジトリを必要とせず、多くの書き込みもチェックアウトを省ける。
    - 移行の初期、Scion に独自のクライアントも形式もプロトコルもなかったころは、コミットの祖先関係や blame のようなメタデータの問い合わせだけを提供していた。
    - チェックアウトは sparse (求めたディレクトリだけ) か仮想化 (ファイルを必要なときに実体化) なので、ジョブは読む分だけを負担する。
- 作業の単位は changeset で、これはサーバー上で作られる write-ahead log のエントリーであり、最初の親に対して変わったファイルを、blob ストレージの圧縮した内容へのコンテンツアドレスのポインターとともに並べるので、packfile もリポジトリの保守もなく、サーバーを含めてどこにもリポジトリを完全に展開したコピーがない。
    - ref は main とリリースのブランチ以外では勧められず、ref を動かすのは changeset の作成とは別の、Spanner の 1 行に対する compare-and-swap である。
    - 記事の図は changeset、ブランチ、ツリーを Spanner に、ファイルの内容を Cloud Storage に置き、ツリーは changeset に保存するのではなくサーバーが導出する。
- Anthropic は blame、パスの履歴、コミットグラフのスキップリストのように changeset から計算するものをすべて派生データ (derived data) と呼び、ある型の changeset に対する値を親の値から即時か遅延で求める 1 つの汎用の仕組みで計算し、クライアントからは隠して自由に最適化できるようにしている。
    - システムが育つにつれて、コピーの検出やパスによるファイル検索のインデックスのような新しい型が加わった。
- `scn` の取得のプロトコルは、クライアントが何を持っているかをサーバーに伝えず、クライアントがルートのツリーから下へたどって足りないツリーと blob を順に要求し、どれもどのキャッシュからでも返せる不変のオブジェクトなので、転送は再開でき、数 GB の packfile も要らない。
    - CI とクラスターのジョブは、定期的なスナップショットから種を入れたノードごとの `scion-daemon` を通り、ミスすると地域の `scion-cache` に尋ね、`scion-cache` はデーモンのディスクの形式でメモリからオブジェクトを流し、開発者のマシンには直接応え、自身がミスすると Spanner か Cloud Storage を読む権威ある `scion-server` の群に尋ねる。
    - 3 つの層はどれも同じ RPC に答え、地域のキャッシュが落ちてもサーバーを圧倒しないよう、階層は厳密に守られている。
- どの層もキャッシュのヒット率は 99% を超え、基盤が要る CPU とメモリは置き換えた git のミラーの 200 分の 1 で、CI と研究のジョブのチェックアウトは 2 桁速くなり (分ではなく秒)、CI は CPU の容量を 25% 取り戻した。
    - 記事のグラフは git と `scn` の中央値を比べ、開発環境では Pull latest が 87 s 対 3.5 s (×25)、Checkout が 15 s 対 1.1 s (×14)、Rebase が 13 s 対 2.7 s (×4.8)、Status が 3.9 s 対 19 ms (×207)、Commit が 1.4 s 対 1.1 s (×1.3)、Diff が 407 ms 対 67 ms (×6.1) である。
    - エージェントの環境では New worktree が 7.1 min 対 5.1 s (×84)、Pull latest が 3.0 min 対 9.0 s (×20)、Commit が 18 s 対 761 ms (×24)、Status が 4.3 s 対 0.2 s 未満 (×20 超) で、変更要求 1 件あたりのソース管理の時間は 34 min 対 3.7 min (×9.2、1 日約 11,000 エージェント時間) である。
    - CI と計算のジョブでは、CI のジョブでのチェックアウトが 31 s 対 3.5 s (×8.8、1 日約 195,000 マシン時間)、計算のジョブの開始時が 175 s 対 22 s (×8.0、1 日約 85,000 マシン時間) である。
- 7 人のチームが、Scion、コードレビューのツール Antique、コード検索、ソース管理の IAM のシステムなどの関連システムを作り、1 日のマージが 10 倍に増えるあいだの 5 か月でそれらに完全に移行した。
    - 2 つめのグラフは、1 月以降の `scm/` と `antique/` のディレクトリへの変更を 12,257 件、表示された最後の週で 1,500 件超と数える。
    - Claude Mythos Preview の初期の社内のスナップショットに、ほぼ手書きの git から Scion への取り込みのプロトタイプをほかに指示を与えず書き直させると、取り込みの順序とデータ構造の不変条件を保ったまま、メモリが 20 分の 1 で 4 倍速い版ができた。
- プロジェクトのエンジニアは全員がいまや Claude を自分より優れたコードの書き手とみているが、システムの設計とトレードオフはエンジニアが担い、エンジニアの役割は多くの場合 Claude にノーと言うことだったと記す。
    - その例として、コードレビューのツールに尋ねる代わりにコミットのログを先頭から読んで変更がいつマージされたかを割り出すシステムや、視野の狭い敵対的なレビューのあとで加えられた過剰な検証を挙げる。
    - このシステムへの変更要求はいまも人がすべてレビューするが、行ごとではなく意図を見ており、Claude が書ける量のおかげで、自明でない基盤とソース管理のやり取りすべての密閉したシミュレーション、ファジング、レート制限、インデックスを使えていなかった祖先関係の問い合わせのアルゴリズム上の修正にまで手が回った。
- Anthropic がスーパーファンと呼ぶ Claude は、それぞれ Claude Tag を通じて Slack のチャンネルにいて、1 つのコンポーネント (`scion-daemon`、`scion-cache`、Antique のマージキュー) に専念してテレメトリーとログを見られ、従来のアラートでは拾えない微妙で新しい問題を捉える。
    - Scion はリポジトリごととディレクトリごとのアクセス制御に対応し、Antique はたとえばコメントだけの変更とセンシティブなロジックの変更を見分ける承認のルールを書ける。
- この速さではマージキューに業界で一般的なリポジトリ全体のロックを再現できなかったので、Anthropic はマージ後とデプロイ前の自動テストに頼り、同時の変更が衝突しうることを受け入れており、その衝突はたいてい人が気づくより速く Claude が直す。
- Anthropic は Scion を git の一般的な代わりではなく、数万人のエンジニアやエージェントの群れを抱える巨大なモノレポでだけ意味があるものとし、公開も発表しておらず、導入する側はライフサイクル全体を移行し、専用のコードレビュー、コード検索、CI が要り、誰もが満足するように作った公開版はあまり役に立たないだろうとする。
    - 社内でのトークンの支出は、ほかの企業が現実に使う額をはるかに超えるとも付け加える。
    - この種の問題は 6〜12 か月のうちにありふれたものになるとみて、代わりに git に向けた案として、クライアントとは違うサーバーのアーキテクチャ、フォージが git のクライアント向けに標準化しうる網羅的なサーバー側の RPC、別のネゴシエーションのプロトコル、組み合わせられる sparse と shallow の機能を示し、GitHub、GitLab、OSS のコミュニティと進めるとする。

#### [A] Linus Torvalds — mm: read from the page cache without folio references, the empty cover-letter commit on noref-filemap-read-with-llm (2026-10-10)

- 問題は、多数のスレッドから 1 つのファイルを小さく読むと folio の参照カウントで競合することで、`filemap_get_read_batch()` が参照を取り `filemap_read()` がそれを手放すため、読み取りのたびに `struct page` のキャッシュラインに 2 回書き込むことになり、Matthew Wilcox が 2024 年に顧客のワークロードからこれを提起していた。
    - Torvalds のノート PC (i7-8565U、4 コア 8 スレッド) では、8 スレッドが 1 ページから 16 バイトずつ `pread()` すると、ロードの HITM の 99.92% がそのキャッシュラインに集中した。
- 考え方は、ページキャッシュから外した folio を RCU の猶予期間のあとでしかページアロケーターに返さない (フラグ `PG_rcu_free`) ことで、そうすれば `filemap_read()` は `rcu_read_lock()` のもとで見つけたページから、ページフォールトを無効にしたまま、参照もバウンスバッファも seqcount もなしにユーザーのバッファへ直接コピーできる。
    - 以前の試み (Torvalds の 2024 年の草案と Kiryl Shutsemau の fast short reads) はスタックのバッファにコピーしてからあとで検証する方式で、検証では見えない場合に行き当たって止まっていたが、解放を遅らせればそうした場合を検出するのではなく、なくしてしまえる。
- 解放を待つページは `kfree_rcu()` のバッチ処理と同じ形で CPU ごとに並び、1 つの CPU で 1024 ページを超えると作業項目が `synchronize_rcu_expedited()` を呼び (パッチ 7)、パッチ 8 はページキャッシュから外すループに CPU を譲らせて、この作業が次のティックの前に走るようにする。
- 数字はすべてノート PC のもので、ext4、緩和策なし、`CONFIG_HARDENED_USERCOPY` なしで測り、ノート PC は温度で速度を落とすので読み取りあたりのコストで比べている。
    - 1 つのファイルを 8 スレッドで読むと、読み取りあたりのカーネルのサイクルは 2937-2975 から 725-726 に減って毎秒の読み取りは 9.9-10.4 M から 30-33 M に増え、1 スレッドでは 452-454 から 408-409 サイクルになり、ロードの HITM (perf c2c、8 スレッド) は 30538 から 101 に減った。

- 猶予期間を待つメモリは、Torvalds によればシリーズで最も解決できていない部分である。
    - パッチ 1-6 では、スワップなしの 2 GiB の VM で Kiryl Shutsemau の再現手順が 4 CPU と 8 CPU で OOM killer を招き、パッチ 1-8 では最後まで走ったが、穴あけ (hole punching) をする 16 のプロセスでは平均 177 MiB、ピークで 870 MiB が解放待ちのまま残った。

### 実践やアウトプットの提案

- チームが持つ追いにくいレガシーなモジュール 1 つで assoc_array のやり方を試し、コーディングエージェントに振る舞いを変えない小さなコミットで大きな関数を分けさせ、そのあと影のモデル、ランダムな操作、アロケーションの失敗の注入、AddressSanitizer と UBSan を備えたホスト側のハーネスを作らせる。
    - 見つかった本当の欠陥の数を、同じモジュールでこのコードのバグを監査せよと直接頼んだ場合と比べ、まず読みやすくしてハーネスを作るほうがバグを直接尋ねるより勝るかを確かめる。
- エージェントの助けを借りたプルリクエストに 10-10 のカバーレターの形を写し、エージェントが何をし、誰が計測を走らせたかを書く Tools の節と、証明していない論証と試していない構成を並べる既知の問題と見てほしい点の一覧を付ける。
    - そのうえで、レビュー役の指摘のうちいくつがその一覧の範囲に入るかを確かめる (Shutsemau の競合状態は既知の問題 6 の範囲に入った)。
- Torvalds のセッションの終わりの片付け (コードをコメントに合わせることなど) を、いくつかの実際のタスクでエージェントの最後の手順としてスクリプトにし、そのトークンのコストと捕まえたものを記録する。
- エージェントが見つけたバグについてのカーネルの手順をチームのルールとして取り入れ、報告の前に再現手順を作り、それで確かめた修正を用意し、バグを持ち込んだ変更を参照し、テストできなかったことを明記する。
    - 修正なしで失敗し修正ありで通る Sakkinen の影のモデルのテストは、再現手順のひな形になる。
