#### [A] Microsoft — MXC SDK v1.0.0 release notes and the repository's release history (2026-10-07)

<https://github.com/microsoft/mxc/releases/tag/v1.0.0> / <https://github.com/microsoft/mxc/releases>

- 2026-10-07 05:54 UTC に出た v1.0.0 は、Rust、.NET、Node.js 向けの SDK の最初の安定版で、プロジェクトの GitHub のリリースとしても初めてプレリリースの印が付いていない。
    - それまでのリリースは v0.6.1 (2026-06-02)、v0.7.0-rc1 (2026-06-13、題は MXC SDK v0.7.0)、v0.8.0 (2026-08-22)、v0.9.0 (2026-09-29) で、どれもプレリリースの扱いであり、v0.9.0 のノートは自らをリリース候補とは呼んでいない。
- 公開 API はバージョン付きの入口 `mxc_sdk::v1`、`Microsoft.Mxc.Sdk.V1`、`@microsoft/mxc-sdk/v1` だけに置かれ、3 つの言語で同じ操作のモデルとポリシーの概念を共有する。
- 1.x の系列では V1 が互換性の境界になり、今後の変更は semver 2.0 に従う。
- 実行のモデルは 3 つある: 完了まで走らせて stdout、stderr、警告、メタデータ、型付きの結果を受け取るもの、SDK が持つプロセスのハンドルの上で stdin、stdout、stderr を別々のパイプにして起動するもの、初期のサイズを渡して実行中にリサイズできる PTY 付きで起動するもの (バックエンドが端末のセマンティクスを出せる場合だけ)。
- ライフサイクルの API はコンテナをプロビジョニングして不透明な `ContainerId` を返し、その後の開始、停止、プロビジョニングの解除を受け持ち、バックエンドが対応していればその中でプロセスを実行したり、起動したり、PTY を開いたりする。
- 型付きの API はほかに、能力付きのバックエンドの発見、発見したホストのツール、ユーザープロファイル、一時ディレクトリから組み立てるファイルシステムのポリシー、テレメトリの同意を扱い、テレメトリは Windows だけ、オプトインで、管理者による制限を受ける。
- 移行の手順: V1 の入口から import し、従来のサンドボックスのリクエストとライフサイクルの型を `ContainerRequest`、`ProvisionRequest`、`ExecutionRequest`、`ContainerId` に置き換え、1.0 のパッケージに対してビルドし直す。
- 変更履歴には、v0.9 より前のスキーマの契約の廃止 (#1382)、FFI の設定の入力をバージョンを厳密に指定した JSON だけにしてバインディング用のリクエストの FFI のエクスポートを削ったこと (#1349〜#1352)、Rust の SDK のクレートを公開できる 1 つのパッケージにまとめたこと (#1390) も並ぶ。
- セキュリティ関連の項目は、ingress の既定の拒否を文書化して固定したこと (#1363)、ポリシーによる拒否を `policy_validation` のコード付きの終了コード 1 で返すこと (#1364)、IsolationSession が `inheritDefaultEnv` なしの `process.env` を拒むこと (#1339)、公開された CVE に対応する依存関係の更新 (#1124) である。
- 署名付きのバイナリが `mxc-release-binaries.zip` として付き、ノートはテストに便利だと説明する。

#### [A] Microsoft — microsoft/mxc README, schema guide, backend guides and V1 SDK reference (as fetched on 2026-10-10)

<https://github.com/microsoft/mxc>

- 2026-02-06 に MIT ライセンスで作られたリポジトリは、取得時点でスター 2.4k、フォーク 120 で、MXC を呼び出し側のアプリケーションに組み込む SDK の依存関係と説明し、コンテナの種類、封じ込めのルール、実行するコマンドはそのアプリケーションが選ぶ。
- 既定のバックエンドは Windows 11 の x64 と ARM64 では `processcontainer`、Linux の x64 と ARM64 では `bubblewrap`、macOS では `seatbelt` で、Windows にはほかに `wslc` と `isolation_session`、Linux には `lxc` がある。
    - `windows_sandbox`、`microvm` (Nanvix)、`hyperlight` は実験的で、README は Windows の行でしかそう示さないが、Nanvix と Hyperlight のガイドは Linux でも `--experimental` を求める。
    - Seatbelt は macOS 15 以降で動き、生成したプロファイルを、macOS 10.8 からヘッダーで非推奨とされながらいまも提供される API `sandbox_init()` で適用し、Bubblewrap には bwrap 0.5.0 以降が、LXC にはポリシーがネットワークなしを求めない限り root が要る。
- `processcontainer` は実行時に、ホストの対応に応じて、新しい OS のサンドボックス API である BaseContainer か、従来の AppContainer の経路のどちらかに解決される。
    - プロセスの分離には Windows 11 24H2 のビルド 26100.9278 か 25H2 のビルド 26200.9278 (2026 年 8 月の更新 KB5120998) が、セッションの分離にはビルド 26100.9550 か 26200.9550 (9 月の更新 KB5124010) が要り、26H1 ではそれぞれ 28000.2804 と 28000.3086 が要る。
    - BaseContainer も OS のファイルシステムのブローカーも使えないときは、既定で `true` の `fallback.allowDaclMutation` によって、MXC がホストの DACL に ACE を書き込み、終了時に元に戻す。
- V1 の型付きの作成は `process` (OS ごとに解決)、`processcontainer`、`bubblewrap`、`seatbelt`、`lxc`、`wslc`、`isolation_session` を受け付けるが、ライフサイクルの操作が受け付けるのは `isolation_session` と `wslc` だけである。
    - Bubblewrap と Seatbelt は作成と実行を一度に行う形しか取れず、発見の API は V1 の作成の API を持たないバックエンドも報告することがある。
    - README の Node の例は、`@microsoft/mxc-sdk/v1` の `spawn()` を `command`、`network: { egress: { default: 'deny' } }`、`timeoutMs: 30_000` で呼ぶ。
- ポリシーは読み取り専用、読み書き、拒否のパスの一覧と、向きを分けた `network.egress` と `network.ingress` (`hostLoopback` 付き)、`runtimeConfig.networkProxy` からなり、どれも既定で拒否する。
    - 直接の egress のルールは数値の CIDR とポートで書き (例: `{"to": [{"cidr": "140.82.112.0/20"}], "ports": [{"protocol": "tcp", "port": 443}]}`)、以前のスキーマのホストの一覧は拒否される。
    - LXC、Bubblewrap、WSLC のバックエンドでは、複数のパスからたどれる 1 つのオブジェクトにはいちばん厳しい許可が当てはまり、拒否が読み取り専用に、読み取り専用が読み書きに優先する。
- `ui` の節 (既定は `disable` が true、`clipboard` が `"none"`、`injection` が false) を強制するのは、Win32k のシステムコールの緩和策とジョブオブジェクトの UI の制限を使う ProcessContainer と、Seatbelt だけで、IsolationSession と WSLc は `ui` を渡すと拒否し、ほかのバックエンドは何も適用しない。
- ネットワークの粒度はバックエンドで違う: ProcessContainer は BaseContainer の経路で WFP によりコンテナごとに IP の範囲、プロトコル、ポートで egress を絞り、Bubblewrap はサンドボックス自身の名前空間の中で IP と CIDR で絞って IPv6 の宛先には届かないままにし、Seatbelt は外向きを全部許すか全部止めるかとループバックのポートしか選べず、ホスト名、IP、CIDR、ポート、プロトコルのルールを拒否する。
    - ホスト名のルールを受け付けるバックエンドはなく、ホスト名のポリシーは呼び出し側が管理するプロキシに置き、プロキシ経由だけの egress はそのプロキシを通じて強制されるが、Seatbelt と Bubblewrap では実際にプロキシを使うかどうかはプロセスの協力に任される。
- バックエンドは強制できないポリシーを黙って弱めずに起動前に拒否し、README は `--audit` が解析するワークロードのサンドボックスのセキュリティをすべて切ると警告する。
- Bubblewrap は名前空間だけで分離し、2026 年 6 月の Linux のロードマップは seccomp の対応を未完とし、`io_uring_setup`、`keyctl`、`bpf`、`userfaultfd` を含むシステムコールの全体がさらされたままだと記す。
- JSON の契約のバージョンは製品のバージョンとも、実行時に調べるホストの能力とも切り離されており、サポートする最小の契約は `0.9.0-alpha`、安定版は `1.0.0`、開発中のものは `1.1.0-alpha` である。
    - v1 の系列では別名 `appcontainer`、`appContainer`、`macos_sandbox` がなくなり、将来スキーマに破壊的な系列ができるときは、V1 を置き換えずに V2 の名前空間を横に並べて足す。
- Windows の ProcessContainer には、強制を続けながら止めたアクセスを記録する Learning Mode の拒否の捕捉と、許したうえで記録する `permissiveLearningMode` があり、テレメトリは実行、Windows のユーザー、管理者のポリシー、アプリケーションのすべてがオプトインしない限りオフで、Windows の外では何もしない。

### 実践やアウトプットの提案

- V1 のサンプル `dryrun-check-containment-support` と `run-with-containment-of-network` を Windows 11、macOS、Linux のマシン 1 台ずつで動かし、`getAvailableBackends()` と `probe()` が何を返すかを記録する。
    - チームのマシンに 2026 年 8 月と 9 月の Windows の更新が当たっていて、AppContainer へのフォールバックではなく BaseContainer が使われるかがわかる。
- 社内のエージェントのハーネスのツール実行の 1 段 (`pytest` や `npm test` の呼び出しなど) を `@microsoft/mxc-sdk/v1` の `run` で包み、読み書きできるパスはリポジトリだけ、`network.egress.default` は `deny` にして、OS ごとに 1 回あたりのレイテンシと誤った拒否を測る。
    - macOS では、MXC の下の Seatbelt にはないドメインの許可リストを持つ Anthropic の sandbox-runtime と比べる。
- 使い捨てのリポジトリで各 OS の Copilot CLI の `/sandbox` をオンにし、`~/.ssh` と `~/.aws` の読み取り、作業ディレクトリの外への書き込み、プロキシを無視するクライアントでの接続、PowerShell 7 が `PATH` にある Windows では許可の外の読み取り (issue #1455) を試す。
    - GitHub が文書に書いた Windows のプロキシと Linux のローカルネットワークの注意点を、チームのマシンで確かめられる。
- Windows では `run-with-logging-access-denied` のサンプルの拒否の捕捉でコーディングエージェントが止められたアクセスを記録し、そのレポートから最小権限のポリシーを下書きして、チームのいつものタスクが通るポリシーにたどり着くまでの時間を測る。
- アウトプット: OS ごとのローカルのエージェント向けサンドボックス (Copilot の下の MXC、Codex の Windows のバックエンド、Unsloth Studio、sandbox-runtime) を、ファイルシステムのルール、ネットワークの粒度、カーネルの共有、エンタープライズでの強制、それぞれが固定する MXC のバージョンで比べる 1 ページの表。

### メモ

- 生成 AI のチームが作るものへの影響: 本文は、11 の高リスクの分野の製品 (レビューの関門、判断の対象者への開示)、ハードウェアを動かすエージェント (停止の手段、切断時の安全な状態、モデルの外の限界)、エージェントの運用者 (ツールとブラウザの操作への責任)、消費者向けのサブスクリプションを使うハーネス、海外にいる職員や対象外の地域から所有される企業によるアクセスについて、設計の要件を変える。
- 発表は高リスクの要件を変わらないとするが、2026 年の本文は 2025 年の本文と比べて要件を両方向に動かしている。
    - 広がった点: 2025 年の企業間の除外がなくなり、ルールは High-risk AI Recommendation を出すすべての人に当てはまり、開示は出力を見せられた人だけでなく判断の対象者にも及び、レビューは実質的でなければならず、法が求める場合は免許が要る。
    - 狭まった点: 自動で公開するメディアや報道の内容はもう高リスクの分野ではなく、新しい除外と、全面的に有利な判断の免除で外れる用途がある。
    - 最大の未解決の問いは、顧客の採用チームに売る候補者の選別のような B2B の製品がいまは要件に入るのかで、本文は出力が特定の個人について助言するか判断するかを鍵にしている。
- 発表は本文のいくつかの条項に触れていない: 消費者向けのサブスクリプションを通じたリクエストの送信やクライアントの偽装、支払いの回避、AI の答えの情報源への仕込み、同意のない性的な画像のためのツール、doxxing、セキュリティの調査の例外、製品のインターフェイスでの開示、エージェントの行動に対する作り手の責任、Software Directory Policy。
- The Verge はハードウェアの操作者が人間でなければならないのかを問うが、ポリシーの本文は qualified individual と書き、The Register はそれを資格のある人間の操作者と言い換えている。
- The Verge は兵器の変更を禁止の拡大として示すが、Anthropic は兵器と監視の文言は既存の執行を反映したものとし、The Register もそう伝えており、脅威の報告の事例 (誘導のソフトウェア、射撃管制、ドローンの群れ、監視の基盤) は新しい条項と一致する。

    - Claude は Claude.ai (2025 年 8 月から) と Claude Code (2026 年 7 月 18 日の EndConversation のツールで、ジェイルブレイクの試みも対象) で会話を終えられるが、API のリリースノートにはそうした仕組みの記述がなく、一方でポリシーは API の顧客とその製品のエンドユーザーにも及ぶ。

### 実践やアウトプットの提案

- 11 月 12 日までに、Claude を使う機能を 11 の High-risk Areas と除外に照らして洗い出し、対象になる機能ごとに、資格のあるレビュー担当者、届ける前のどこにレビューの関門を置くか、影響を受ける本人に AI の利用をどう伝えるかを記録する。
- MCP や MHS で機器を動かすエージェントがあれば、ハードウェアの要件を作業台で試す: 人の手が届く停止の手段、API の接続が切れるかタイムアウトしたときの安全な状態、プロンプトインジェクションの試みの下も含め、モデルが範囲外のコマンドを送ったときにファームウェアか別の制御装置で強制される限界。
- チャットボットとエージェントの開示 (セッションの初めか、インターフェイスに常に出す通知) を確かめ、エージェントのツールとブラウザの操作の監査ログを、ポリシーの区分に照らしてレビューできる形で残す。
- ツールが Claude にどう届くかを監査する: Pro や Max のサブスクリプションを通るハーネスは API キーに移し、クラウドのプラットフォーム経由のアクセスも含め、所有関係と職員の渡航を Supported Regions の文言に照らす。
- 監視では `stop_reason: "refusal"` を違反ではなくセーフガードのブロックとして扱い、`stop_details.category` を記録して、どの機能がリアルタイムのセーフガードに当たるかを見る。
- レッドチームと虐待への対処の評価では、テストの目的を記録し、ジェイルブレイクのテストに Anthropic の事前の許可が要るかを確かめる。
- アウトプット: チームの製品に関わる 2025 年と 2026 年の条項の 1 ページの差分で、設計レビューのチェックリストとして使う。
