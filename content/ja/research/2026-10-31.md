#### [A] Cursor — Security notice: malicious version of Anthropic.claude-code (2.1.312 and 2.1.313) identified in the Cursor VS Code Extension Marketplace (2026-10-29, updated 2026-10-30)

<https://cursor.com/blog/claude-code-extension-security-notice>

- `Anthropic.claude-code` 2.1.312 と 2.1.313 (macOS、Windows) は 10-29 の午前 2:27 から午後 1:35 ごろ (PT) まで Cursor の VS Code 拡張機能マーケットプレイスにあり、Cursor は Anthropic の開発ではないとする。
- 10-30 の午前 11:30 (PT) 付けの追記で、Cursor は侵害の痕跡 (IoC) を改め、影響を受けるバージョンを明確にした。
- 悪意あるコードは、ホスト名、ユーザー名、OS、アーキテクチャ、ホームのパス、環境変数の名前、作業ディレクトリ、Git のメールアドレス、パブリック IP を攻撃者に送る。
- `svc-telemetry` というラベルの付いた攻撃者の SSH 鍵を `authorized_keys` に書き足し、ローカルの SSH サービスの有効化とリバース SSH トンネルの確立を試みる。
- 永続化には macOS では LaunchAgent を、Windows では SYSTEM での実行を狙うスケジュールタスク (失敗すればスタートアップのスクリプト) を使い、バックグラウンドのスクリプトが約 60 秒ごとにトンネルをつなぎ直す。
- SSH の有効化に要る管理者権限をほとんどのホストで拡張機能は持たないので、Cursor の日本語版の告知は「攻撃者がトンネル経由でログインできた可能性はありません」とするが、鍵の追加、永続化、ホスト情報の送信は実行された。
- Cursor は該当バージョンを取り下げてマーケットプレイス全体を止め、アクセスを監査して他の拡張機能に改ざんがないことを確かめ、鍵をローテーションしてマーケットプレイスを再構築した。
- クラウドプロバイダーと連携して攻撃者のサーバーを落としたので、リバースシェルもホスト情報の POST ももう機能しない。
- 確認手順は `~/.ssh/authorized_keys` (Windows では `C:\ProgramData\ssh\administrators_authorized_keys` も) から `svc-telemetry` を探すもので、見つかればそのマシンは影響を受けている。
- アンインストールだけでは足りない場合があるとして、Cursor は `remediate-macos.sh` と `remediate-windows.ps1` を公開し、ホストの隔離、再構築の検討、信頼できるシステムからの認証情報のローテーションを求める。

#### [A] Cursor Docs — Extensions (as fetched on 2026-10-31)

<https://cursor.com/help/customization/extensions>

- Cursor は自社のプロキシ `marketplace.cursorapi.com` を通して Open VSX を使い、拡張機能を表示または配信する前にマルウェアとサプライチェーンの自動解析をかけるとしている。
- チームの管理者は短命な悪意あるアップロードへの緩衝として Marketplace Install Cooldown を時間単位で設定でき、既定は `0` (無効) で、ユーザーごとの `extensions.installCooldownHours` より優先される。
- チームはインストールを承認済みの発行元や拡張機能 ID に絞れ (`AllowedExtensions`)、Enterprise のチームは有効な Open VSX の拡張機能署名を必須にできる。
- 認証バッジが確かめるのは発行元の身元で、ページはこれを防御の 1 層にすぎず、本番のコードや認証情報に触れる拡張機能では許可リストとクールダウンの代わりにならないとする。

#### [B] Phorion — Official Claude Code Extension Compromise: Security Advisory, by Calum Hall (2026-10-30, updated 2026-10-31)

<https://phorion.io/blog/offical-claude-code-vsx-compromise/>

- 発見者の Phorion によれば、`extension.js` の先頭に足された IIFE は Node がファイルを読み込んだ時点で `activate` コールバックより先に動くので、ユーザーが拡張機能に触らなくても実行される。
- macOS では管理者権限のない `systemsetup -getremotelogin` がエラーを出して終了コード 0 で終わるので、`/Off/i` の判定を通らず、`sudo -n systemsetup -setremotelogin on` は実行されない。
- リモートログインがすでに有効か後で有効にされた Mac には攻撃者がそのまま入れると Phorion は警告し、Windows の SSH のセットアップは `/bin/sh` を決め打ちした補助処理のせいで失敗するとする。
- ビーコンが送るのは `KEY|TOKEN|SECRET|PASS|AWS|GCP` に一致する環境変数の名前を最大 40 個で値は含まず、攻撃者がログインすれば SSH のログに `svc-telemetry` 鍵による `localhost` のログインとして残るはずである。

### メモ

- どこが破られたのか: Beaumont の見出しは Anthropic とするが、Anthropic は否定して Cursor のマーケットプレイスを指し、Cursor は鍵のローテーションと再構築はしたものの侵害されたシステムを名指ししていない。
- Beaumont は 2.1.313 が黙って削除されたと読むが、Dworken は公開されたことがないとしており、10-31 に GitHub のリリース、npm、Visual Studio Marketplace と Open VSX の API を見てもどこにも 2.1.313 はなかった。
- 対象バージョンは一度動いた: Cursor の最初の告知、DoublePulsar、The Hacker News は 2.1.313 だけを挙げ、Cursor が 10-30 に 2.1.312 を加えて Phorion も 10-31 に続いたので、範囲はまた動くかもしれない。
- プラットフォーム: Phorion の Linux の経路はペイロードの中のコードで、Cursor が改ざんを挙げるのはリリースごとの公式ビルド 8 種のうち `darwin-arm64` と `win32-x64` だけであり、Linux の確認手順もない。

### メモ

- Fowler の記事に測定はなく、書かれているのは彼の反応、1 つの逸話、サイトの方針だけで、この実行の検索でも人が編集した LLM の下書きについての読者研究は見つからなかったので、彼の主張にとどまる。
- [Armin Ronacher の試み (2026-09-14)](https://lucumr.pocoo.org/2026/9/14/interpreting-pangram/) は 1 例だが、編集については Fowler を支持し、アウトラインの許容は崩しており、Opus 5 の文章の構成を保って手で書き直しても Pangram の判定は 100% AI だった。
- [Russell らの研究 (ACL 2025)](https://arxiv.org/abs/2501.15654) では、LLM をよく使う 5 人の多数決の誤りは言い換えや人間らしくする加工があっても 300 本中 1 本だけで、ただしこれは訓練された読み手についての測定である。
- [Karr らの研究 (2026)](https://arxiv.org/abs/2608.11256) はツールへの疑いを支持し、検出器が AI と判定する率は人の要旨に LLM が軽く手を入れたもので 38〜80%、手を加えていない 2023〜2025 年の要旨で 9〜15%、人間らしく書き直したものでは 4% 未満だった。
- Fowler が触れない害は濡れ衣で、[Liang らの研究 (2023)](https://arxiv.org/abs/2304.02819) は検出器が非ネイティブの英語を AI と誤判定することを示し、HN には AI だと疑われてエムダッシュをやめた人もいる。
- 翻訳ではスレッドの意見が割れ、Fowler ほど抵抗がないという人、ブロークンな英語のまま投稿せよという人、一律の拒否は特権だという人、LLM の口調では嫌なやつに聞こえるという非ネイティブの書き手がいる。
- [azukiazusa (2026-08-22)](https://azukiazusa.dev/blog/what-i-learned-writing-technical-blog-posts-with-ai/) は異を唱え、下書きしてから編集する流れでも学びの大半は残り、読者が気づいた AI の記事だけを数えると判断が偏るという。
- [Simon Willison の方針 (2026-03-01)](https://simonwillison.net/2026/Mar/1/ai-writing/) の線はもっと緩く、LLM に校正や README を任せても、意見や一人称の入る文章は自分で書くとするのに対し、Fowler は言い換えの受け入れさえ危険とする。
- Fowler の開示の規則には測定された代償があり、[Schilke と Reimann (2025)](https://news.arizona.edu/employee-news/being-honest-about-using-ai-work-makes-people-trust-you-less-research-finds) は 13 の実験で AI の利用を開示すると信頼が下がり、他人に暴かれるともっと下がると報告する。
- HN のあるコメントは学習データではなく instruction tuning のせいだとし、[Reinhart らの研究 (2025)](https://arxiv.org/abs/2410.16107) は instruction tuning したモデルで文体の差が大きいと測っており、Clark の Olmo の結果と合う。

### 実践やアウトプットの提案

- Fowler と Willison をもとに 3 段階のチームの規則を作り、意見と根拠は人が書き、リリースノートと定型文は LLM の下書きでよいとし、謝辞で開示して、四半期後に見直す。
- 社内文書 20 本 (半分は LLM の下書きを編集したもの) でブラインドテストを行い、レビュアーに判別と信頼性の評価をしてもらって、Fowler の主張がチームの文章に当てはまるかを見る。
- 名詞の積み重ねや無生物主語と有生の動詞の組み合わせなど Clark の特徴を LLM の下書きの編集前後で数え、編集でどれだけ消えるかを測る。
- 日本人エンジニアの実際のメッセージで、本人の英語、LLM の翻訳、LLM の推敲を海外のレビュアーに評価してもらい、不格好でも人の文章がよいという Fowler の好みを確かめる。
- Fowler の Say Your Writing の勧めどおり設計文書を 1 本レビュー前に声に出して読み、LLM はファクトチェックにだけ使い、書きながら考えが変わった点を書き留める。
