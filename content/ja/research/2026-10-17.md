#### [A] Meta AI Research — Introducing Muse Spark Open, The Most Capable US Open-Weight Model to Date (2026-10-15)

<https://research.meta.ai/blog/muse-spark-open>

- Meta は 10 月 15 日、総パラメータ 816B、アクティブ 42B、100 万トークンのコンテキストを持つネイティブのマルチモーダルモデルの重みを公開し、コーディングとエージェントの作業向けに作ったとする。
- Meta はこれまでで最も高性能な米国製のオープンウェイトモデルと位置づけ、長い時間のかかるタスク、複雑なソフトウェアエンジニアリング、多段階の推論に強いとする。
- 公開時にホストされた API を出すのは Baseten、Fireworks AI、Groq、Modal、Nebius、OpenRouter、Together AI である。
- 重みは Hugging Face、Amazon SageMaker AI、Google Cloud Model Garden、Microsoft Foundry Models から入手できる。
- SGLang、vLLM、TensorRT-LLM、Hugging Face Transformers、Apple MLX、llama.cpp、Unsloth で動き、AMD、Apple、Intel、NVIDIA のチップ向けの最適化もある。
- Meta はこのクラスで初めてデスクトップで動くモデルだとし、それぞれ最大 512GB のユニファイドメモリと 1.2 TB/s の帯域を持つ M5 Ultra の Mac Studio 2 台で、最新の MLX を使って動かす。
- Meta はデバイス上のテストで、このモデルの上で Muse Code を動かして iOS アプリ Ice Cubes にバグ修正と機能を出荷し、DaVinci Resolve をエンドツーエンドで操作させた。
- SGLang には自動調整できる Helion の GPU カーネルが入り、NVIDIA と AMD の GPU でカーネル単位で 1.03〜3.95 倍、AMD MI350 ではエンドツーエンドで 3% 速くなる。
- オープン版は安全性の事後学習を追加で受けて Meta Superintelligence Scaling Framework の公開の基準を満たしたとされ、完全な評価レポートは近日公開と予告されている。
- Meta は、Muse Model License の商用の条件は限定的で、多くの開発者が無料で使えると説明する。

#### [A] Air Security — Plugin4Shell - Zero Click RCE Vulnerability found in top 4 most popular coding agents, millions of agents affected, by Or Nevo, Dor Granat and Niv Hoffman (2026-09-17)

<https://www.air.security/blog-posts/plugin4shell>

- 4 つのエージェントはどれもマーケットプレイスが固定したコミットをチェックアウトするが、HEAD が本当にそこに来たかを確かめないので、エージェントが固定の SHA を報告したまま別のコードが入る。
- Claude Code、Codex、Copilot は `git clone` と `git checkout <40-hex sha>` を実行し、git は ref でもオブジェクト ID でもある名前を ref として解決して、`refname is ambiguous` と警告するだけである。
- 攻撃者が固定された SHA と同じ名前のブランチをリポジトリの既定にすると clone でそのブランチがローカルに作られ、既定でないブランチならリモート追跡の ref として届くだけなのでコミットが勝つ。
- GitHub は 40 桁の 16 進のブランチ名を拒むが、Bitbucket やセルフホストの git サーバーは受け付け、Anthropic のドキュメントはどちらもマーケットプレイスの対応ホストに挙げている。
- Gemini CLI は `git clone --depth 1`、`git fetch origin <sha>`、`git checkout FETCH_HEAD` を実行するので、`FETCH_HEAD` という名の既定のブランチがあるとチェックアウトがそちらに取られ、取得したコミットは捨てられる。
- AIR のいうゼロクリックでは、マーケットプレイスがプラグインを新しい無害なコミットに固定し直したとき、攻撃者がその名の既定のブランチを悪意のあるコードに向けると、自動更新が確認なしにそれを入れる。
- AIR は、自動更新は Claude Code と Codex で既定で有効で、攻撃者に要るのはプラグインのリポジトリだけ (無害なプラグインを公開するか、信頼されたものを乗っ取る) だとする。
- 修正はエージェントの中の 1 つのアサーション `test "$(git rev-parse HEAD)" = "<pinned-sha>" || abort` で、要求した ref ではなく解決した HEAD を確かめるもので、マーケットプレイスの側からは強制できない。
- AIR は 2026 年 5 月に欠陥を見つけて 4 つのエージェントすべてへの PoC を作り、6 月に開示し、Anthropic は 06-17 に 2.1.179 での修正を確認し、Codex 0.146.0 は 08-12 に修正済みと確かめられた。
- Microsoft は Copilot の修正を出しておらず、Google は 08-04 に非推奨の Gemini CLI は直さないと答えて Antigravity を勧め、Antigravity にはすり抜けられるようなプラグインの SHA 固定がない。

#### [B] DevelopersIO (Classmethod) — Checking Claude Code's CVE-2026-86063 locally: git checkout prefers a same-name branch over a commit SHA, by 西村祐二 (2026-10-17, in Japanese)

<https://dev.classmethod.jp/articles/claude-code-plugin-sha-pin-bypass/>

- macOS 26.6.1 の git 2.55.0 でコミット X と同じ名前のローカルのブランチを Y に向けると、`git rev-parse $X` は X を返したが、`git checkout $X`、`checkout --detach $X`、`switch --detach $X` は Y に解決された。
- 取り出しで X になったのは `git checkout --detach $X^{commit}` だけで、`refname '...' is ambiguous` の警告は標準エラーに出るだけで終了コードは 0 なので、終了コードで成否を判定するツールは見落とす。
- 同名のブランチを `file://` のリモートにだけ置くと `git checkout $X` は X を detached HEAD で取り出し、筆者は、ローカルのブランチができた経緯をアドバイザリが書いていないと指摘する。
- スクリプトと CI には `<SHA>^{commit}` か、`git fetch origin <SHA>` に続く `git checkout --detach FETCH_HEAD` を勧め、どちらでも最後に `test "$(git rev-parse HEAD)" = "$PINNED"` で照合するよう求める。

- AIR の記事は、クラスメソッドが「実際の導入処理で、どのような経緯でローカルブランチができる状態になっていたかは、アドバイザリに書かれていません」と残した疑問に答えており、SHA の名のブランチは `git clone` がローカルに作るよう既定でなければならず、クラスメソッドのリモートだけの検証は既定でないブランチを使っていたので、AIR のリモート追跡の ref の説明と合う。
    - この実行で git 2.56.0 を使って確かめた結果も一致し、SHA の名のブランチをベアリポジトリの HEAD にすると、普通の clone と `git checkout <sha>` は終了コード 0 で別のコミットに行き、既定でないブランチにすると固定したコミットに行った。
- 食い違い: クラスメソッドの 2 つ目の取り出し方 (`git fetch origin <SHA>` のあと `git checkout --detach FETCH_HEAD`) は、AIR が示す、Gemini CLI が `FETCH_HEAD` という名の既定のブランチに負けるのと同じ形であり、クラスメソッド自身の表も `--detach` ではブランチ優先の解決が止まらないことを示している。
    - この実行の確認 (git 2.56.0) では、既定のブランチが `FETCH_HEAD` のリポジトリを `git clone --depth 1` したあと、`git checkout FETCH_HEAD` も `git checkout --detach FETCH_HEAD` も同じあいまいさの警告を出してブランチの先端に行った。
    - したがってこの方法が安全なのは、クラスメソッドが最後に置く `git rev-parse HEAD` の照合があるときか、攻撃者の既定のブランチから clone していないリポジトリでだけである。
- git のこの振る舞いは git のホストには知られていた (背景) もので、2020 年の GitLab への HackerOne の報告 ([issue 202690](https://gitlab.com/gitlab-org/gitlab/-/issues/202690)) が同じハッシュよりブランチを優先するチェックアウトを説明し、[CVE-2020-13293](https://nvd.nist.gov/vuln/detail/CVE-2020-13293) として GitLab 13.0.12、13.1.6、13.2.3 で修正された。
    - その issue は GitHub のように 40 桁の 16 進のブランチ名を拒むよう GitLab に求めており、AIR のいうあらゆるセルフホストの git サーバーという言い方は、いまの GitLab には広すぎるかもしれないが、GitLab がいまそれを拒むことは検索結果でしか確かめていない。
- AIR には商売上の利害があり、Air Marketplace と Air Filter を売っていてその利用者は影響を受けなかったとし、これまでの乗っ取りについての数字 (仕込んだ 1 つのスキルで 26,000 のエージェント、乗っ取った 925 のスキルが 134,000 のエージェントに届いた) は自社の調査によるもので、独立に確かめられていない。

- ここに WebFetch だけに拠る事実はなく、NVD のページは中身が薄かったので、その日付、状態 (Awaiting Analysis)、ベクトルは NVD の API から取った。

### 実践やアウトプットの提案

- すべての開発者のマシンと CI のイメージでバージョン (Claude Code は 2.1.179 以降、Codex は 0.146.0 以降) を確かめ、`DISABLE_AUTOUPDATER=1` を設定したインストールや固定したコンテナイメージから動かしているものを先に見る。
- 使っているマーケットプレイスとプラグインのソース (Claude Code の `/plugin` の Marketplaces タブと `extraKnownMarketplaces`、Copilot CLI の `extraKnownMarketplaces`、Gemini CLI の拡張) をすべて洗い出し、GitHub 以外のホストにあるプラグインと自動更新が有効なマーケットプレイスに印を付ける。
- 固定を信じる前に各プラグインのリポジトリを `git ls-remote <url> | grep -E 'refs/heads/([0-9a-f]{40}|FETCH_HEAD)$'` で調べ、クラスメソッドの 40 桁の 16 進の確認を Gemini CLI の手口にも広げる。
- Copilot CLI か Gemini CLI が修正を文書化するまでは、それらのプラグインを GitHub 上のリポジトリに限り、利用者が追加したマーケットプレイスの `autoUpdate` をオフのままにし、CSA のノートの勧めどおり、各プラグインが解決したコミットをエージェント自身の報告とは別に記録する。
- チーム自身のスクリプトと CI を直し、クラスメソッドの `git grep -nE 'checkout .*[0-9a-f]{40}'` と `git grep -nE 'git (checkout|switch)'` で SHA のチェックアウトを探して、`git checkout --detach "${SHA}^{commit}"` と `git rev-parse HEAD` のアサーションに書き換える。
- Codex の PR #34644 にあるような回帰テストを加え、既定のブランチが別のコミットの SHA の名を持つフィクスチャのリポジトリと、既定のブランチが `FETCH_HEAD` のものを 1 つずつ用意して、インストーラーやスクリプトが両方を拒むことを確かめる。
- Gemini CLI を使う企業のチームは、Google が AIR に修正は出さないと伝えている以上、Antigravity CLI への移行か、拡張をレビュー済みの社内リポジトリに限ることを検討できる。
- GitHub 以外のプラグインのソースが自動更新されていた環境では、CSO Online が引くアナリストが指す場所である EDR、Git、CI/CD、クラウドの IAM、認証のログで、予期しないプラグインのファイルや認証情報の使用を調べる。
- アウトプット: 2 つの手口 (SHA の名の既定のブランチと `FETCH_HEAD` の既定のブランチ) をそれぞれ数行で再現して 1 行の `rev-parse` の照合を示す、クラスメソッドの記事を広げる短い日本語の記事。

### 実践やアウトプットの提案

- 最小の試行はサンドボックスのワークスペースで 1 時間ほどで済み、ポート 443 の HTTPS の背後にあるバックエンドに Custom の送信先を加え、Test を押して `anthropic.test` を確かめ、Playground からリクエストを送り、`service.name` = `claude-platform` で絞り込む。
    - セルフホストの Collector には 443 番の TLS か、既定の OTLP/HTTP のポート 4318 の前に置くプロキシが要る。
    - Platform は `localhost` に届かないので、[MLflow 3.17.1 以降](https://mlflow.org/blog/claude-otel-tracing)をインターネットから届くようにすれば、登録の要らないバックエンドとして使える。
- エンドツーエンドのトレースを見るには、トレーサーのプロバイダーを登録して自分のスパンの中で SDK を呼び、SDK の `CLIENT` のスパンが API の `SERVER` のスパンを含むことを確かめ、自分の HTTP スタックを通した `traceparent` の伝播を検証する。
    - Node では `@opentelemetry/instrumentation-undici` を読み込んでいるとき、そこでのバグが `traceparent` ヘッダーを二重にするので `propagation: false` を設定し、同じクライアントに OpenInference のような 2 つ目のインストルメンターを動かさない。
- 送信先の作成を、ドキュメントの例どおり `ant auth login --profile admin --scope "org:admin"` と `ant --profile admin beta:organization:telemetry-destinations create` でスクリプトにし、`claude-api` スキルもいまはこの手順を説明している。
    - ガイドには、設定のための Claude Code 向けのプロンプト `Set up OpenTelemetry tracing with the Claude API and Claude SDK` もある。
- トークンと費用のパネルでは、API のスパン、つまり種類が `SERVER` の `anthropic.messages.create` かその子の `anthropic.model_request` に `anthropic.compaction` を加えたものだけを合計し、トレースとスパンの ID で重複を除き、1 週間の合計を Usage API と比べてベストエフォートの欠けを測る。
    - Managed Agents のセッションでは、代わりに `anthropic.model_request` と `anthropic.session.outcome_evaluation` のスパンを合計する。
- 内容の方針をワークスペースごとに決め、既定はメタデータだけ、ステージングのワークスペースでは Full content にし、長いコンテキストのエージェントでは `anthropic.content.truncated` を確かめる (100 万トークンのコンテキストには既定の 0.75 MB に対して約 4 MB が要る)。
    - Full content にする前にバックエンドの保持期間とリージョンを確かめ、New Relic のプリセットには JP のリージョンがある。
- Full content を社内にとどめるには、自前の Collector に送り、スパンのリファレンスが Content のタグを付ける属性 (`gen_ai.input.messages`、`gen_ai.output.messages`、`gen_ai.tool.call.arguments` など) をベンダーに届く前に取り除く。
- Managed Agents では、スパンを `gen_ai.conversation.id` でまとめてスレッドの記録を、`anthropic.session.id` でまとめてセッション全体を組み立て直し、`anthropic.tool.evaluated_permission` (`allow` か `ask`) と `anthropic.session.outcome_evaluation.result` をグラフにする。
- アウトプット: Bedrock と Vertex AI のワークロードには SDK のスパンしかなく、OpenAI 互換の呼び出しには API のスパンがないことを書いたチーム向けの 1 ページのカバー範囲のメモと、Platform のエージェントをチームの Claude Code のトレースと 1 つのバックエンドに並べるダッシュボード。
