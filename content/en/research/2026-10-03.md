#### [A] Anthropic — Customize Claude Code with mods (2026-10-01)

<https://claude.com/blog/claude-code-mods>

- "Today we're introducing mods, small TypeScript functions that change how Claude Code works."
- "A mod can rewrite a prompt, add new UI, replace a built-in feature, or add entirely new functionality."
- A mod can be written by hand or by Claude Code, ships inside a plugin, and works in the Claude Code CLI and the desktop app.
- "Mods run with the same access to your machine as Claude Code itself."
    - "They aren't sandboxed, and you should only install mods from sources you trust, the same way you'd install any code on your computer."
- Why: "Hooks helped give users some of this control, but hooks can't rewrite events, draw new UI, or replace features."
- Anthropic "shared the design for mods on GitHub" (issue #91870) before launch to get feedback from developers.
- Each time Claude Code does something it emits an event, such as calling a tool, asking for permission or drawing part of the screen, and a mod can run before the event, after it, instead of it, or wrap it.
- With one function, a mod can rewrite a prompt before it reaches the model, block, rewrite or retry a tool call, approve or deny a permission request, and redact secrets from tool output before Claude reads it.
- A mod can edit or replace parts of the interface, such as a tool result or a question from Claude, and add buttons and inputs that other mods can respond to; it can target the terminal, the desktop app or both.
- "When several mods hook the same event, they run in the order they load."
    - "The first mod to load sees the event first and the result last."
- Claude can write the TypeScript of a mod, install it and hot reload it in the session.
- The built-in `/diff` is now a mod that can be turned off in `/plugin` or replaced.
    - "We plan to move more built-in features to mods over time, so you can pare Claude Code down to a small core and add back only what you want."
- Existing plugin controls apply to mods: Team and Enterprise owners allow or block marketplaces in the admin console, and admins on Claude API and third-party API plans push managed settings.
- On Team and Enterprise plans and on any machine with managed settings, a built-in mod called `sec-default` ("security default") loads first.
    - "It stops mods that users install from doing risky things, like overriding your permission deny rules."
    - Admins can load their own mods first instead, and should then add `sec-default` to their list to keep its restrictions.
- Team examples: a CI/CD status pane, a confirmation before any command touches production config, and an audit-logging mod that loads first and records every call that every other mod makes.
- Mods install from the Claude directory or `/plugin`, and can be shared by submitting a plugin to the directory.

#### [A] Anthropic (claude.dev) — Getting started with Claude Code mods, by Addy Osmani (2026-10-01)

<https://claude.dev/blog/getting-started-with-claude-code-mods/>

- "A mod is a small JavaScript or TypeScript file that runs inside your Claude Code session."
- To try one, run `claude`, describe the mod, allow hot reload when asked, and "the mod shows up when the turn ends".
- "Under the hood, mods are hooks that ship inside plugins, and each one sees every event in your session as it happens."
- Layout: a normal plugin with `.claude-plugin/plugin.json`, a `hooks/hooks.json` that names one module under `modules`, and a module that exports `register(on, options)`, in which `on(event, matcher?, hook)` adds a hook.
- Every hook has the shape `($, e, next)`: `$` is the mods API, `e` the event's input as plain data, and `next` passes `e` to the other plugins and then to Claude Code's own behavior.
- Three moves: Observe (`const r = await next(e); /* look */ return r`), Rewrite (`return next({ ...e, command: safer })`) and Answer (`return { deny: "…" }` without calling `next`).
- The events cover tool calls, the prompt as submitted, turns starting and finishing, the session starting and ending, slash commands, and `ui.render` for every piece of the interface as it is drawn.
- "The module runs in a sandbox of its own, with no DOM and no Node, so everything outside it goes through `$`."
- A settings hook runs a shell command per event with JSON over stdin and stdout, while a mod is loaded once, stays in the session, keeps state, draws UI that updates as events happen, and calls back into Claude Code.
- The tutorial builds Token Weather, "about 80 lines", which draws one line above the prompt with a weather icon, the percentage and tokens of the context window used, a chart of recent turns and what the last turn added.
- Its thresholds are under 25% Clear, 25–49% Cloudy, 50–74% Showers, 75–89% Storm and 90% and up Compact soon, shown at 18%, 67% and 81% of a 200k window.
- A mod Claude writes "loads only in this session, and its folder is cleaned up later", so it has to be copied out and installed like a plugin to keep it.
- Prerequisite: Claude Code 2.1.287 or later, "Mods are on by default", and "The API can change between releases".
    - The type declarations Claude Code writes into `.claude-plugin/types/` "are the authority for your version".
- Sharing: a folder with `.claude-plugin/marketplace.json`, then `claude plugin marketplace add ./my-mods` and `claude plugin install token-weather@my-mods --scope user`, or `/plugin marketplace add your-org/my-mods`, `/plugin install token-weather@my-mods` and `/reload-plugins` from a GitHub repository.
- "A mod is code that runs inside Claude Code on your machine, with the same access Claude Code has, and it's written by its publisher, not Anthropic."
- Blast Radius holds a Bash call with `rm -rf`, `git reset --hard`, `git clean`, a force push or a database migration and opens a pane with Proceed and Cancel; in the figure it holds `rm -rf build` and lists the 9 files (1.1 MB) it would delete.
- Replay Theater records every Edit and Write call in a turn, and `r` or `/replay` steps through the diffs in a pane with Prev, Next and Close, shown on a 5-edit rename across 3 files.
- Four habits: rely on the generated types, read props from `e.props`, keep data in `$.state` because every save runs `register` and `session.start` again, and run `claude --debug` when a drawing does not show.
- Suggested mods: a cost or rate-limit meter from `$.session.usage()`, a `prompt.submit` hook that adds team conventions, a pane of the files Claude read, a focus timer with `$.ui.toast`, and a `tool.call` guard for production kubectl contexts or `terraform apply`.

#### [A] Claude Code Docs — Mods overview (as fetched on 2026-10-03)

<https://code.claude.com/docs/en/plugins/mods/overview>

- "A mod is a plugin that changes how Claude Code looks and behaves."
- It is made of JavaScript or TypeScript event handlers that Claude Code calls on a tool call, a submitted prompt or a part of the interface being drawn, and "the handler can watch the event, change it, or take it over".
- On these pages "hook" means a mod's handler, and the settings-file kind is a "settings hook".
- What a mod can do that settings hooks, skills, status lines and MCP servers cannot: draw a pane beside the transcript or a band above the prompt, redraw Claude Code's own interface, step into a tool call or a request, run a `/command` "with no Claude turn, even while Claude is working", and share data between hooks.
- Stepping in includes holding a tool call while asking the user, answering it without running the tool, or sending one request to a different model.
- Install: `/plugin install token-chart@your-org` in a session or `claude plugin install token-chart@your-org` in the shell, then `/reload-plugins` if a session is open.
- Sample mods `token-weather`, `blast-radius` and `replay-theater` live in `anthropics/claude-code-playground`, shared "as they are, without support".
- Once loaded, a mod can act on the machine as the user, read secrets ("environment variables and settings files, including an API key you keep in either"), see every prompt and tool call, change the session, approve a tool call before the user is asked, and spend the user's usage.
- "Mods aren't sandboxed."
    - With sandboxing on, the sandbox isolates the Bash commands Claude runs, "and a process that a mod starts runs outside it".
- A mod that approves tool calls can approve one that an `ask` rule would prompt for, or that one of the user's own `PreToolUse` hooks blocked.
- "A mod can restyle much of Claude Code's interface, but not the permission prompt."
- `claude plugin validate ./some-mod` lists, without running the mod, the events it handles (`hooks:`) and what it asks Claude Code to do (`calls:`).
- "Mods require Claude Code v2.1.287 or later, and they're on by default."
- To turn mods off: disable or uninstall one plugin in `/plugin`, start with `--safe-mode` for one session (which also disables other customizations), or set `"disableAllHooks": true` in `~/.claude/settings.json`, which also stops settings hooks and the custom status line while organization-managed ones keep running.
- `disableAllHooks` and `allowManagedModsOnly` stop a mod but leave its plugin's skills, commands, agents and MCP servers loading.
- "If you set `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS` during early access, remove it."
    - v2.1.287 and later ignore it, "so setting it to `0` doesn't keep mods off".
- `/plugin` shows a dim line such as `1 mod active · first-mod`.
- A small mod has three files: `.claude-plugin/plugin.json`, `hooks/hooks.json` and the hooks module `register.js`.
- A hook can Observe, Rewrite or Answer, and anything outside its own code goes through the mods API, "which is why Claude Code can list what a mod does before you install it".
- Where hooks run and where drawing appears: the terminal (including editor terminals and the JetBrains plugin) runs and draws, the Desktop Code tab runs and draws except terminal-only elements, a WSL session in Desktop does neither, the VS Code chat panel, `claude -p` and the Agent SDK run hooks without drawing, Remote Control runs and draws on the user's machine, and a cloud session runs hooks for a plugin that reaches it without drawing.
- Comparison: a mod is "Functions in a plugin that Claude Code calls in its own process" and can change "Tool calls, prompts, commands, turns, and what the interface draws"; only mods can draw.
- Built-in mods listed in `/plugin`: `cc-plugin-agents-md`, `cc-plugin-diff`, `cc-plugin-plugin-authoring` (a skill, no mod code), `cc-plugin-sec-default` (cannot be turned off), `cc-plugin-telemetry` and `cc-plugin-you-should-know`.
- `cc-plugin-you-should-know` "Runs a side agent that watches your back while Claude works on longer tasks."
    - "When it finds something worth knowing that you might miss, it shows you a note above the prompt."
    - It is "Disabled by default" and listed under `/plugin` -> Installed -> Show disabled "if available for your org".

#### [A] Claude Code Docs — React to events with a mod (as fetched on 2026-10-03)

<https://code.claude.com/docs/en/plugins/mods/events>

- The handlers for an event form a middleware chain, and "the last `next` reaches Claude Code's own behavior".
- "The first mod is outermost: it sees the event before the others and the result after them, and it decides whether the others run at all."
- Chain order: the built-in guard, mods in `prependPlugins` and other organization mods, then mods the user installs, then `appendPlugins`, then other built-in mods; within one module, hooks run in the order `register` called `on`.
- Matchers compare fields by value, array or regular expression, such as `{ tool: /^mcp__github__/ }`, and `'*'` matches every event except telemetry.
- `tool.call` fires for subagents' calls and MCP tools; a hook that answers without calling `next` means "the command never runs" and no permission prompt appears.
- A hook can hold a risky Bash command with `$.ui.ask` until the user picks an answer; waiting inside a mods API call does not count against the time limit, and "Claude Code skips a hook that times out, so the held command would run".
- `tool.check` fires after the permission rules and settings hooks have decided, so it can deny a call a rule allows, or approve one that a `PreToolUse` hook outside managed settings blocked.
- A `prompt.submit` hook can rewrite the text, add text only Claude reads, or drop the prompt, and text that changes between requests "invalidates the prompt cache".
- A `turn.step` hook is an async generator that can read each request's token usage or send it to another model with `next({ ...e, model })`.
- `PreToolUse` hooks from managed settings run before the first mod's `tool.call` hook, and their block is final; other settings files' and plugins' `PreToolUse` hooks run after the last mod calls `next`, so a mod that answers keeps them from running.
- A hook that throws, times out or returns the wrong shape before calling `next` is skipped and the next handler runs, so a guard fails open unless it has a `.catch` handler that answers with `{ deny }`.

#### [A] Claude Code Docs — Use the mods API (as fetched on 2026-10-03)

<https://code.claude.com/docs/en/plugins/mods/api>

- `$.command.register` in `session.start` adds a command; `immediate: true` lets it run while Claude is working, and a taken name throws.
- `$.tool.register` adds a tool Claude sees as `mcp__` plus the plugin name, two underscores and the tool name.

- Default with no mod settings: mods are on, from any marketplace the plugin settings allow or from `--plugin-dir`.
- The built-in guard loads "ahead of every mod a user installs" when the machine has managed settings or the user is signed in with a Team or Enterprise plan.
    - "A user who authenticates with an API key, or through Amazon Bedrock, Google Cloud's Agent Platform, or Microsoft Foundry, gets the guard only on a machine that has managed settings."
- The guard keeps users' mods from changing what managed hooks receive or decide, the system prompt, managed `CLAUDE.md` and instructions, what any mod reads as settings, and the tools and descriptions of managed MCP servers.
- "Everything else is allowed."
    - A user's mod can still read and write files, start processes, make network requests, rewrite tool calls and prompts, deny or approve tool calls, and draw, all with that user's permissions.

    - Neither applies to a mod's own `$.fs` and `$.process` calls: "with `Read(.env)` denied, a mod can still read that file with `$.fs.read` or start a program that does".
- "In auto mode, a call the mod approves runs without a classifier check."
- Settings hooks "run as before, alongside mods", and "Nothing about them is deprecated".
- Managed `PreToolUse` hooks run again on a call a mod rewrote, so their block still applies.
- Network policy refuses a `$.http.fetch` when web fetching or nonessential traffic is off, but "doesn't cover a program the mod starts with `$.process.run`".
- `strictKnownMarketplaces` and other plugin controls decide whether a mod can be installed, the permission prompt cannot be changed, no mod loads before the trust prompt is answered, and `--safe-mode` turns installed mods off, the organization's included.
- "None of these controls sandboxes a mod."

- Hooks to look for: `tool.call` and `prompt.submit` (every tool call and prompt), `session.append` (rewrites stored rows), `ui.render{component=AskUserQuestion}` and `tool.check`.

- `allowManagedHooksOnly` also blocks hooks in users' own settings files, and `disableAllHooks` in managed settings stops every installed plugin's mods and every settings hook, including managed `PreToolUse` hooks.
- `disableSideloadFlags` rejects `--plugin-dir` and `--plugin-url` at startup, keeps mods Claude writes from loading, and also rejects `--agents` and `--mcp-config`.
- A mod counts as the organization's only when managed `enabledPlugins` enables it, managed settings name its marketplace as a directory on the machine by absolute path, and the marketplace lists it by relative path so it loads in place.
    - The directory should be writable only by an administrator, because "Anyone who can write there can rewrite your mod".
    - A plugin copied from a GitHub, git, URL or npm source counts as a user's even when managed `enabledPlugins` enables it.
- When `prependPlugins` is set, it replaces the default, so it must name `sec-default@builtin` to keep the guard; repositories cannot set `prependPlugins` or `appendPlugins`.
- The guard's options are read only from managed settings, and "The guard fails closed": it refuses every user's mod if it cannot read managed settings, and refuses a call if it cannot check the deny rules.
- `allowModsToOverrideDenyRules` lets a user's mod approve a call that a `deny` rule refuses.
- A policy-mod example (`acme-guard`) refuses user-tier mods whose code calls `process.run` or `process.spawn` in `plugin.register`, and writes an audit line for each `tool.call` and each `fs.write` another mod makes.
- "If your `plugin.register` hook throws or exceeds its time limit, Claude Code skips the hook, so the check fails open", unless a `.catch` handler returns the refusal.
- If the worker thread that runs installed mods crashes three times, Claude Code unloads every mod that is not built in, the organization's included, until `/reload-plugins` or a new session.
- Debug-log checks: `tier prepend` for the organization's mod, `refused by cc-plugin-sec-default: mods are limited to your organization's by policy (allowManagedModsOnly)` for a user's mod, and `--plugin-dir is disabled by your organization's managed settings (disableSideloadFlags)` at startup.

### Notes

- The documentation says mods need v2.1.287, but the Qiita measurement had them working on 2.1.286 (3/3 runs) and not on 2.1.285, and Desktop builds bundling 2.1.286 already ran community mods.
- "On by default" has exceptions: Anthropic can turn installed mods off remotely, a gateway user without an Anthropic account found the rollout switch (`tengu_plugin_hooks_modules`) served off and cached, and the npm `stable` tag was still 2.1.285 on 2026-10-03.
    - 2.1.288's fix for `claude plugin test` reading an out-of-date saved setting may address part of the gateway report; whether gateway users now get mods is unconfirmed.
- The claude.dev guide says the module "runs in a sandbox of its own, with no DOM and no Node", while the documentation, the blog and Bromure say mods are not sandboxed.
    - The first refers to the JavaScript runtime, which reaches the outside only through `$`; the second to permissions, since `$` acts with the user's full access and installed mods share one worker thread inside the Claude Code process.
    - Pluto draws the same line on v2.1.274: the worker had no ambient fetch, require or import and no way around `$`, while `$` itself read the credentials and history files and reached the network.
- Dash Security claims that mods draw in VS Code and on mobile, which contradicts the documentation table (no drawing in the VS Code chat panel; Remote Control draws in the terminal on the user's machine); Dash wrote against the v2.1.277 preview.
- Whether a cloned repository can ship a mod under `.claude/skills/<name>/` that loads after the workspace trust dialog is not settled: Dash says it can, the loading reference lists trust-time restrictions only for MCP servers, bundles and monitors, and no page says hooks modules are excluded.
- `claude plugin validate` lists hooks and `$` calls only, so a mod that changes behaviour purely by rewriting what it passes to `next()` shows no calls at all (Dash's wallet swap, Pluto's falsified transcript).
    - Its `hooks:` line would still name the `tool.call` and `ui.render` hooks such a mod registers, which the review guidance in the documentation tells administrators to look for (inference from the documented output, not tested here).
- The built-in guard loads only on machines with managed settings or for Team and Enterprise sign-ins; Pro, Max, API-key and cloud-provider users without managed settings get no guard, and even where it loads deny rules do not cover a mod's own `$.fs` and `$.process` calls.
- A policy mod's `plugin.register` check fails open on a throw or timeout unless it has a `.catch` handler, and three crashes of the shared hooks worker unload the organization's mods too.
- Pluto tested the v2.1.274 pre-release behind the environment-variable gate, and the 2.1.287 documentation settles some of its findings but not others.
    - Settled or changed: mods are now on by default and the variable is ignored, the permission prompt is still not a render site, and the band, `Input`, `AskUserQuestion`, `$.http.fetch` and `$.process.run` are all still documented, so the capabilities behind the fake prompt, the dialog rewrite and fetch-then-run remain.
    - Open: whether `plugin details` still reports Hooks (0) for a mod, whether installation still shows no capabilities and prompts nothing, whether the content scan still runs only on the claude.ai channel, and whether the model's option labels are still restored; no 2.1.287 page or changelog item addresses any of these.
    - The 2.1.287 interface page now requires a tree that replaces `AskUserQuestion` to hold Claude Code's own dialog exactly once with the mod's elements above it, while props can still be changed through `next`, so whether the question text can still be swapped as on v2.1.274 is not stated.
    - Pluto's administrator advice predates `allowManagedModsOnly`, which the 2.1.287 documentation adds as a narrower switch that leaves users' settings hooks running.
- `bareElicitationCapability` appears only in the changelog, and the MCP page does not mention it; since the 2025-11-25 specification makes an empty `elicitation` object mean form mode only, the key plausibly makes Claude Code send that bare object to servers that reject the new `url` capability (inference, not stated by Anthropic).
- The Monitoring page does not list `prompt_text` yet; the reason for the copy is issue #70763, in which `prompt.id` overwrote `prompt` on backends that nest dotted keys.
- `$.ui.selection()` matches a community request of 2026-09-28 on issue #91870, and the reference page, written as of v2.1.287, does not list it yet.
- 2.1.288's change to the background command time limit reverses, for terminal, desktop and VS Code sessions, the 30-minute default that 2.1.285 introduced (topic 11 of 2026-10-01).
- Timing: npm published 2.1.287 at 16:59 UTC on October 1 and the GitHub release followed at 18:00 UTC (03:00 on October 2 in JST); 2.1.288 reached npm at 18:30 UTC on October 2.
- No page says which model the You should know side agent uses, what it costs, or what it sends; it needs telemetry on and first-party sessions, is off by default, may not be available for every organization, and its source is not in the public `mods` directory.
- The view count of the ClaudeDevs post differs by date: 685,000 within a day according to Bromure, 3.7M on the page fetched on 2026-10-03.
- The Qiita measurement article shows a posting date of 2026-10-01 but states a measurement date of 2026-10-02.
- Classmethod's interactive step is written from the documentation, not from an observed run; its `-p` run and validate output are its own.
- The New Stack discloses that its owner is an investor in Anthropic, and Bromure, Dash and Pluto sell security or isolation products.

### Ideas for practice and output

- Before the `stable` channel moves past 2.1.285, decide the team's mod policy and deploy it to one managed test machine: `allowManagedModsOnly` under `cc-plugin-sec-default@builtin`, `disableSideloadFlags`, and a marketplace allowlist, then confirm the refusal lines with `claude --debug` and `claude --plugin-dir ./first-mod`.

#### [A] Earendil Engineering — Pi Durable (2026-10-01)

<https://earendil.com/posts/pi-durable/>

- The post is signed "Earendil Engineering"; the Pi 1.0 post says Mario Zechner wrote it.
- Pi Durable "was built specifically for long-running, durable, and malleable agents that can run anywhere".
- The Pi coding agent is built "to run on your (remote) machine, inside a terminal, driven by one person", and that focus "is not changing".
- The goal is a harness that "runs anywhere, can be reached from different surfaces, supports infinitely long conversations, survives catastrophic internal and external failures, and lets multiple humans steer the same agents".
- "It does not replace the Pi coding agent."
    - "It is a framework for building any agentic application, coding agents included."
    - It shares code with the coding agent, such as pi-ai, and the principles "minimalism and malleability".
- Lessons from Pi Durable "will flow back into Pi the coding agent as they prove themselves valuable".
- "A harness is storage plus the machinery needed to run one or more conversations with large language models in parallel."
    - It provides the tools the models call and the execution environments the tools run in.
- An agent is the model with its settings, such as the thinking level, and the tools it can call.
- "Everything the harness runs, from calling the model to executing a tool, is a task."
- "The entire source code, without tests, is about 15,000 lines, which comes out to about 150,000 tokens with GPT and about 250,000 with Claude."
    - The storage backends alone are 3,000 lines that an agent can usually skip.
- Agents should run for a long time and anywhere, "where anywhere currently means anywhere there is a JavaScript runtime".
- A harness opens over a storage backend; Pi Durable ships memory, SQLite and JSONL storage, "plus a conformance suite and benchmarks for your own backend".
- "The SQLite and JSONL storage code uses no Node APIs, so with a small adapter it runs on Bun or inside a Cloudflare Durable Object."
- The storage interface is small enough to implement on a key-value store or Postgres, and "One process owns a storage at a time, and other clients attach to that process."
- On SQLite only the working set stays in memory (active transcripts, live tasks and pending submissions), so "even a conversation with tens of thousands of messages fits snugly into memory".
- Pi Durable ships a Node execution environment with access to local files; the interface lets tools run on another machine than the harness.
    - An `env` function builds the environment for every tool call from the conversation's working directory.
- The setup example opens `Harness.open(await openNodeSqliteStorage("./agent.sqlite"), { models, registry, env }, context)` with `CodingTools` (read, write, edit, bash) and a root conversation on `{ provider: "openai", modelId: "gpt-6.1-sol" }`.
- "In Pi Durable, every step of a run is a task that stores a checkpoint before it moves on."
    - A new process opens the same storage, finds the unfinished tasks and continues each from its last checkpoint.
- A model request that was cut off is sent again, and the partial answer stays in the transcript marked as aborted.
- A tool call that was cut off reruns if it is safe to; otherwise the model is told it was interrupted.
- "Pi Durable has no built-in subagents, but they take a few lines of code to build."
    - A subagent runs in a conversation of its own, so it also continues where it left off.
- "A `requestId` makes a submission exactly-once, so a client that retries after a crash gets the original submission back instead of asking twice."
- One harness runs many conversations concurrently, "all with the same guarantees".
    - A conversation starts fresh or forks another at any point of its transcript and sees the parent's history up to that point without copying it.
    - The example is a Slack channel as one conversation and a thread as a fork of it, neither blocking the other.
- Each conversation stores its own agent: model, thinking level, selected extensions and active tools, extra instructions and working directory.
    - "A reviewer next to the main agent can use a cheaper model, read-only tools, and its own checkout."
- An extension is "a named bundle of system prompt sections, tools, hooks, and tasks", and conversations store only their names.
- The system prompt is rebuilt from the extensions' sections before every request, and each change is recorded in the transcript "so a restart or a fork sees exactly what the model saw".
    - On models that accept mid-conversation changes, only the change is sent, "so the prompt cache stays valid".
- "Every tool call runs as its own durable task, and its intent is stored before it runs."
    - A tool marked `replay: "safe"` reruns after a crash; any other tool returns an interruption with the output stored so far.
    - The `deploy` example declares no replay, so a deploy interrupted by a crash is reported to the model and never repeated.
- Tool sets can differ per conversation: the Slack thread "may search, but not deploy" through `thread.configure({ tools: { remove: [deploy] } }, context)`.
- A tool gets the harness API: it can commit entries and documents, start tasks and conversations, and talk to other conversations.
    - The `triage` example creates a subagent on `gpt-6-luna` with no tools, owned by the tool call, so aborting the call aborts the subagent.
- A later extension's tool with the same name replaces the earlier one, and `wrapTool` decorates whichever tool won, for example to time every bash call.
- Hooks step into the built-in tasks for a model response, a tool invocation and compaction; they can rewrite a request, block or rewrite a tool call, replace a result, keep a run going or write a summary.
- "A hook can run again after a crash, so a hook that makes a decision stores it in a memo: a small value stored with the task, where the first write wins."
    - The approval example asks in Slack once before `deploy`; after a restart it finds the stored answer.
- Hooks of several extensions run as a chain: `beforeTool` passes rewritten arguments on and stops at the first block, `afterTool` passes the result on, `onYield` stops at the first hook that keeps the run going, and observers like `afterResponse` always run them all.
    - A hook that throws is reported and the chain continues, "except in `beforeTool`, where a throw blocks the call".
- Built-in tasks are one per model request, one per tool call and one for compaction; extension tasks get "a checkpoint after every step, timers that survive restarts, and waiting on other tasks".
- The checkout example charges several cards as child tasks with an idempotency key (`payment-${task.id}`), waits on them with `policy: "failFast"`, and refunds in `abort` when one card is declined.
- "Tasks and conversations form one ownership tree."
    - Aborting a task aborts what it owns bottom-up, and a task finishes only once the work it owns has finished.
- Foreground tasks are part of the conversation's current work, so Esc aborts them; a background task lets the conversation go idle and survives an ordinary abort, for "a subagent that should outlive the turn that started it, or a reminder that fires tomorrow".
- Compaction is a task that runs while the conversation keeps going: near the context limit a background compaction summarises older messages and places the summary at the next turn boundary.
    - The conversation waits only when the next request would not fit, and a request the provider rejects as too long is compacted and retried once.
    - Manual compaction takes instructions, and "The older messages always stay in storage."
    - The example settings are `reserveTokens: 16384` and `backgroundTokens: 32768`.
- `reset()` starts a new context, optionally from a handoff note, and a tool can ask for it with `control: { handoff }`; a `search_history` tool can still search everything before the handoff.
- Application state such as a todo list, a plan, a ticket or the sandbox "lives in documents": typed JSON stored next to the transcript and changed in the same atomic commits, "so the state never disagrees with the transcript that produced it".
    - Each document says what a fork starts with: the parent's value at the fork point, its current value, or a fresh one.
- The registry can change while conversations run: installing an extension under an installed name replaces it in one step, a running tool call finishes on its old code, and the next call uses the new code.
- Any number of clients can attach to a conversation: a client first gets the current view (transcript, streamed answer, running tools and output, queued messages, agent and usage), then only changes, and any client can steer or queue a follow-up.
    - `thread.watch()` delivers the exact operations of every commit; `watchEvents()` turns them into the coding agent's events "at the cost of more bytes on the wire".
- "Pi Durable is experimental, and the API might still change."
- The post points to the README, over thirty examples, a small coding agent on Pi Durable and a vacation planning agent of "about 1,300 lines of TypeScript, most of them the TUI".
- In the vacation demo a subagent runs three searches in parallel as durable tasks; the process dies with weather and museums done, and after the restart "`search` is safe to rerun: only trains runs again".
- Coming weeks: "small agentic tools we build with it to help us work, like a Slack bot or a GitHub triage bot".
- FAQ, "Why TypeScript again?": "Because it is the easiest way to bootstrap this."
    - Rust or assembler are not ruled out, "but at the moment we are focusing on TypeScript".

#### [A] Pi documentation — Virtual Models and Codemode (as fetched on 2026-10-03)

<https://pi.dev/docs/latest/virtual-models>

- "A virtual model is a selectable model that picks a physical model for each request."
    - It is registered from an extension and appears in `/model`, `--model` and settings like any other model.
- The footer shows the routed model next to the selection, for example `auto • high → gpt-5.6-luna • medium`, and `/session` lists the cost for each physical model.
- `route(request, ctx)` runs before every request with a `reason` of `user`, `continuation`, `retry` or `direct`.
- "Returning `previous` for `continuation` and `failed` for `retry` keeps prompt caches and thinking signatures valid."
    - "Switching models between turns is allowed but loses the prompt cache."
- A router can return JSON state, which Pi stores on the session branch; it follows forks and `/tree` navigation and survives compaction.
- Routers can call a classifier through `ctx.modelRegistry.classify()`, and "The call adds latency before the first token of the turn."
- `jev-router.ts` "plans on a strong OpenAI Codex model chosen by the Jev classifier, lets that model make the first edit, and then switches once to a cheaper model, accepting a single prompt-cache miss".
- A virtual model cannot route to another virtual model, and a resumed session whose virtual model is gone falls back to the physical model that answered last.
- Codemode scripts run in a QuickJS sandbox with "no Node APIs, file system, network, or timers"; they reach the outside only through tools and `models`.
- Script output is capped by `max_output_tokens` (default 10000), and `timeout_ms` is unset by default.
- `store()` keeps at most 262144 characters of JSON per value and 1048576 in total, and is written to the session only when the script succeeds.
- At most four `classify()` or `generateImages()` calls run at once per script, and their usage counts toward the session cost.
- Tool declarations listed in the `codemode` description share a budget of 3000 estimated tokens (`codemode.inlineBudget`); `codemode.mode` is `on` by default or `only`, which hides the other tools from the model.
- Inside scripts `bash` resolves to `{ output, truncated, full_output_path?, exit_code, wall_time_seconds }` with up to 1 MiB of output, while the model sees 2000 lines or 50KB.

#### [A] Earendil (GitHub and npm) — pi-durable README, Pico5 specification, package metadata and the harness removal commit (as fetched on 2026-10-03)

<https://github.com/earendil-works/pi/blob/main/packages/durable/README.md>

- The README opens with an experimental warning: "The API changes without notice between releases."
- "Conversations, model turns, tool calls, and your own state are committed to storage before anything is shown."
- The package is built on `@earendil-works/pi-ai` for model access and `@earendil-works/chord` for document state; chord 1.0.0 describes itself as an "Application composition runtime for services, replicated state, RPC, and plugins".
- Harness: "All changes go through one line of atomic commits, and nothing is shown before its commit is stored."
- Built-in entries include `pi.user`, `pi.assistant`, `pi.tool-result`, `pi.system` and `pi.reset`; built-in documents hold each conversation's agent (`pi.agent`), running work (`pi.live`), queued submissions (`pi.inbox`) and spend (`pi.usage`).
- The `pi.generation` task calls the model and owns the `pi.tool` tasks of its tool calls.
- Submitting to a busy conversation queues the input: steers join after the current tool round, follow-ups start the next run, writes append an entry without asking the model, and `whenBusy: "reject"` throws `ConversationBusy`.
- "A slow watch keeps at most 100 undelivered frames", after which the pending frames are replaced by one frame with the newest view.
- "Partial answers and tool output are committed at most every 100 ms, so a crash loses at most that window."
- SQLite storage runs in "WAL mode with `synchronous = NORMAL`: commits survive process crashes; the newest may be lost on power or host failure."
- JSONL storage is append-only files in one directory, with `{ fsync: true }` to flush before each commit marker.
- "One process owns a storage at a time; there is no cross-process locking."
- The portable SQLite and JSONL cores run without Node APIs, "for example on Bun or in Cloudflare Durable Objects", given an asynchronous `SqliteDatabase` facade or a `FileSystem`.
- Custom backends run the shared conformance suite (`registerStorageConformance`) with any Vitest- or Jest-compatible runner.
- The built-in tools are `read`, `write`, `edit` and `bash`, and "Reading images is not supported yet."
- Usage is kept per `provider/model` and per tool, and failed and aborted attempts count too.
- Loading TypeBox for argument validation "costs about 23 MB of peak RSS unbundled, about 4 MB in a tree-shaken bundle".
- The examples include persistent background subagents (23), a checkout with four payments and a restart (24), background compaction (25), a read-only plan mode as an extension (27), a reviewer conversation (28) and a sandbox per conversation (29).
- The normative `docs/spec.md` is titled "Pico5 specification", and its core rule is "A Session atomically commits immutable entries, full task records, and Chord-tracked documents."
    - "Only committed state is observable."
- Its invariants include "All visible progress is durable." and "External effects do not run inside the Session mutation transaction."
- The spec's effect sandwich (section 5.2) is: commit intent phase, perform external effect, commit outcome or next phase.
    - "Reopening in an intent phase means the effect may have happened."
    - The phase handler then "retries safely, polls an external handle, or records interruption".
- Non-goals include CRDT or offline multi-writer merge, an automatic checkpoint heuristic, and "forced termination of non-cooperative extension code inside one process".
- On npm, `@earendil-works/pi-durable` 1.0.0 was published at 2026-10-01T19:11Z, after versions from 0.86.0 (2026-09-19) onward in step with Pi.

#### [A] GitHub Docs — About computer use in GitHub Copilot (as fetched on 2026-10-03)

<https://docs.github.com/en/copilot/concepts/agents/computer-use>

- Copilot reads accessible application content and visual context "through your operating system's accessibility tree or screenshots when visual context is needed", and the agent selects these tools as it works, with tool activity reviewable in the session.
- Example tasks: reviewing and summarizing information in a legacy desktop application, updating content in a presentation, entering or updating information in GUI-only software and moving information between applications in a multi-step workflow.
- "If an API, MCP server, terminal command, filesystem tool, or dedicated browser tool can complete the task directly, that tool typically provides more structured information and predictable results."
- Computer use is disabled by default and must be enabled before an agent can use its tools.
- It follows the tool permission settings of the Copilot surface running the session, which decide whether Copilot asks for approval before controlling a desktop application.
- An approval prompt offers access for the current session, a saved approval for future sessions, or denial.
- "Always allow" for an application is stored locally and applies to both Copilot CLI and the Copilot app on the same computer.
- Removing an application in the app deletes its saved approval in both the app and the CLI, but "It does not revoke access already granted in a running session."
- "Permission rules that deny a tool take precedence over automatic or saved approvals."
- Enterprise administrators can disable computer use through managed settings, and "Enabling computer use locally does not override an enterprise policy."
- Esc twice interrupts an active operation in the CLI, and Stop or Esc does so in the app.
- On macOS, computer use guides the user through Accessibility permission (to interact with application controls) and Screen Recording permission (to inspect application windows when visual context is needed).
- Interfaces change between application versions, operating systems and window states, and computer use "can select the wrong control, enter text in the wrong location, or have difficulty with non-standard or dynamic controls and complex workflows".
- Changes in timing or window state can produce different results, make computer use repeat an action or stop it from continuing.
- The warning says ambiguous instructions or unexpected on-screen content "may cause unintended actions that affect your device, data, or connected accounts, including access to personal, financial, or enterprise systems", and "Computer use is not a substitute for human judgment."
- Application windows may display sensitive information, including information about other people, so computer use should only be used where the visible content is acceptable as context for Copilot.
- With "Always allow", later computer-use actions can control the application without asking again, so it should be avoided for applications that contain sensitive information or support high-impact actions.

#### [A] GitHub Changelog — Dynamic workflows in Copilot CLI and the Copilot app (2026-10-01)

<https://github.blog/changelog/2026-10-01-dynamic-workflows-in-copilot-cli-and-the-copilot-app>

- Dynamic workflows are now available in Copilot CLI, the GitHub Copilot app and the GitHub Copilot SDK, to "define an orchestration in code to get the reliability and observability that complex, multi-agent work demands".
- A dynamic workflow is "a program that defines how a task is carried out", combining automated steps with the work of one or more agents, run one after another, in parallel, or both.
- The steps, when to involve agents and how to use their results are defined in code, while agents handle the parts that need analysis or judgment.
- The program lives inside a GitHub Copilot extension, "which means it has access to Copilot's powerful extensibility APIs".
- Worked example: investigate a service incident by collecting logs and telemetry, assigning independent agents to analyze different systems and combining their structured findings into a timeline and root-cause report, where "The same steps run every time".
- Listed capabilities: run commands, use tools or call other services; divide a goal into tasks and run independent tasks in parallel; pass structured results from one stage to the next; have subagents verify each other's findings; ask the user for input if the client supports it; pause at a checkpoint for review and resume later.
- Unlike `/fleet`, where Copilot delegates work to subagents and coordinates them in parallel, a dynamic workflow carries out a process defined in code.
- Users can author workflows themselves or have Copilot write them, with built-in authoring guidance as for extensions.
- Suggested uses: release checks where one agent assesses failures and the run pauses for review; reviewing many changed files of a pull request in parallel; finding unresolved review comments on merged pull requests and asking two models whether they still matter, reporting only when both agree; sweeping a large codebase for a pattern such as missing tests or usages of an API being removed; researching, planning and then making a change; a long, potentially expensive run to pause and resume later.
- "For a quick answer or a simple change, a normal prompt in the standard chat mode is usually sufficient."
- Dynamic workflows are available on all Copilot plans.
- In the Copilot app they are always available with no setup; in the latest Copilot CLI they need experimental features (`--experimental` or `/experimental on`), and `/update` updates the CLI.
- Users can ask "What dynamic workflows are available?" to list their workflows and send feedback with `/feedback`.
- The feature is in public preview and subject to change.

#### [A] GitHub Docs — Dynamic workflows (as fetched on 2026-10-03)

<https://docs.github.com/en/copilot/concepts/agents/dynamic-workflows>

- The concept page describes dynamic workflows as a way to "orchestrate work on complex tasks, potentially combining deterministic operations, agents, tools, API calls, and user interactions", suited to tasks repeated "with a deterministic set of actions carried out every time".
- Beyond the changelog's list, a workflow can "Combine results into a single answer", and it can ask agents to return results in a specified format, with Copilot asking an agent to correct the format if needed.
- Workflows are defined in Copilot extensions and can be authored by Copilot, written by the user with the built-in guidance, or shared, becoming available once the extension is loaded.
- A workflow is started by asking for it by name, for example `Run the java-security-review dynamic workflow on the java files in the current directory.`, and Copilot runs it in the background and reports back while the session continues.
- "Your chat agent only creates or runs a dynamic workflow when you explicitly ask it to, or when a skill or slash command instructs it to do so."
- In Copilot CLI, `copilot workflow run WORKFLOW-NAME` runs a workflow from the terminal without an interactive chat and waits for the run to finish or stop, for repeated inputs, saved results, scripts and CI/CD pipelines.
- A workflow can also be started from an extension's slash command, custom tool or programmatic hook, from other code that uses the Copilot SDK, or from a canvas (a custom interface) that an extension provides in the Copilot app.
- The comparison table: autopilot lets Copilot keep working autonomously and decide the next steps; `/fleet` encourages Copilot to delegate to subagents and decide how to divide and coordinate the work; in a dynamic workflow the author defines "the steps, conditions, and handoffs", run sequentially, in parallel or both, with one agent or many.
- "Reusing a workflow means reusing its steps and rules", while the path through those steps can change with the inputs or findings and agents can give different answers on different runs.
- A workflow's subagents use the CLI's permission system and inherit the permission grants of the session that started them.
- A subagent request that is not yet permitted surfaces as a normal permission prompt in the interactive session, and that subagent waits for the answer.
- A permission granted for the session to one subagent applies to all subagents that need the same permission.
- `copilot workflow run` displays no permission approval prompts, so the needed permissions must be granted before the run starts.
- "An extension can also run its own code directly, outside these permission prompts."
- By default Copilot creates the workflow's extension for the current session, and it can instead create a personal or project extension.
- A first run is typically tested on a limited scope, such as two or three files, before asking Copilot to revise the workflow.
- Revisions are requested in natural language (for example `Update the check-python-style dynamic workflow to use no more than 10 subagents in total.`) and saved to the extension, apply to new runs after the extension reloads, do not replace saved results of a paused run, and reach teammates only after they pull the repository and reload their extensions.
- Copying the extension to the personal extensions directory or a repository's extensions directory shares the definition, "not the original session's run history or saved progress", and wider distribution goes through a plugin.
- Four limits can be set: the maximum number of workflow-owned agents active at the same time, the maximum launched in total over a run, the maximum active running time (paused time does not count), and an approximate maximum of AI credits for the workflow's agents and their subagents.
- The credit limit is "an approximate maximum, not a hard ceiling": usage is reported after it occurs, so work already underway can take the total past the limit.
- Limits come from the prompt (for example `with a timeout of 1 hour`), from the workflow code or from personal settings, in that order of priority.
- The CLI's personal default keys are `workflows.defaultLimits.maxConcurrentSubagents`, `workflows.defaultLimits.maxTotalSubagents`, `workflows.defaultLimits.timeoutSeconds` (in seconds) and `workflows.defaultLimits.maxAiCredits`, set with `/settings`, for example `/settings workflows.defaultLimits.timeoutSeconds 3600`.
- Reaching the concurrency limit only makes extra subagents wait, while the other limits stop the run but keep its status and saved results.
- A run resumed after a limit needs a higher limit, and "The new limit is a total for the run, including usage before it stopped, not a fresh allowance".
- A workflow that launches many subagents "can take a long time to complete and consume a large number of AI credits", so the page advises a small-scale test, a check of the actual credit usage, and then a credit limit for the large run.
- `/workflows` in the CLI and the Workflows button in the app list current and past runs with AI credit usage, phases, progress messages and subagents, and let the user cancel, pause or resume a run.
- A resumed run can reuse saved results from completed steps and subagents, while "Work that was not saved may need to run again".

#### [A] GitHub Docs — Using dynamic workflows (as fetched on 2026-10-03)

<https://docs.github.com/en/copilot/how-tos/use-copilot-agents/use-dynamic-workflows>

- In Copilot CLI the prerequisite is experimental features, through `--experimental` or `/experimental on`.
- Users can ask which workflows are available, ask Copilot to describe one, and run one by its registered name with its required inputs, for example `Run the java-security-checks dynamic workflow on the java files in the current directory, with an AI credit limit of 500.`
- Setting limits is "optional but recommended, as it helps control resource usage and prevent excessive consumption of AI credits".
- Depending on the permission approval settings, Copilot asks the user to approve the run before it starts.
- `copilot workflow run WORKFLOW-NAME [OPTIONS]` needs the workflow in a personal extension, a project extension or an installed plugin, so a workflow created in a chat session must first be made available outside that session.
- `--args` supplies inputs as JSON, or as a file path prefixed with `@`.
- The command shows no permission approval prompts even in a terminal, so permissions are granted up front with `--allow-tool` or `--allow-url`, and "Requests that cannot be approved automatically are denied."
- Example: `copilot workflow run java-security-checks --args '{"directories":["java/src","java/tests"]}' --allow-tool=read`.
- The command shows the phases and progress messages, prints the result and exits on completion, reports the status and run ID when the run pauses or stops, and is interrupted with Ctrl+C.
- The workflow's configured limits and the user's personal default limits still apply to these runs.
- `--result-file` writes only the returned value to a JSON file, only when the run completes successfully and returns a result, and replaces an existing file only after the new result has been written; a paused, failed or interrupted run leaves the file unchanged.
- For scripts and CI/CD pipelines, authentication can come from an environment variable such as `COPILOT_GITHUB_TOKEN`.
- `GITHUB_COPILOT_PROMPT_MODE_EXTENSIONS=true` loads a project extension when the working directory has not already been trusted, which "allows repository extension code to run" and is meant only for trusted code.
- `--silent` suppresses progress output, and `--output-format json` returns a JSON record with the workflow name, run ID, status and any returned result.
- An authoring prompt such as `Create a dynamic workflow named review-changed that lists changed files, asks an agent to review them, and summarizes the findings.` produces a workflow, and Copilot chooses a name when none is given.
- Copilot may ask for approvals while it creates and registers the workflow, and "Creating and registering a workflow does not start a run".
- `Show me the guidance for writing dynamic workflows.` shows the built-in guidance for writing the extension by hand.
- A session-scoped workflow lives at a path such as `/Users/yourname/.copilot/session-state/d58ba0bf-78fa-4172-b277-c18ba400e7c6/extensions/java-security-checks/extension.mjs`.
- Copying the directory that contains `extension.mjs` into `~/.copilot/extensions/` makes the workflow available in all of a user's sessions, and copying it into `.github/extensions/` of a repository shares it with everyone once the change is merged and teammates update and reload.
- Workflows can also be packaged in a plugin and published on a plugin marketplace for others to discover and install.
- In the CLI, `/workflows` lists running and recently completed runs with their active time, current phase, active and total subagents and AI credits used, with `P` to pause, `X` to cancel and `R` to resume.
- In the Copilot app, a Workflows button above the prompt box lists active runs, runs "Ready to resume" and finished runs, with Cancel, Pause, Resume and "Resume with limit…" actions.
- In the app, run monitoring is only available for local sessions.
- With OpenTelemetry enabled, a workflow creates an `invoke_workflow` span each time it runs or resumes, with its agents' activity linked to it.
- When resuming a run that reached a limit, the higher total includes the usage before the stop, and "Canceled runs cannot be resumed."
- A run can be scheduled in a CLI session with `/every` or `/after`, for example `/every 1d run the changed-files-report dynamic workflow on the 'main' branch, limiting it to 200 AI credits`.

#### [A] GitHub — copilot-sdk Node.js reference: Dynamic Workflows (added 2026-09-22, updated 2026-09-27)

<https://github.com/github/copilot-sdk/blob/main/nodejs/docs/workflows.md>

- Dynamic workflows are "extension-authored, session-scoped workflows that coordinate subagents and durable steps", and the API is experimental.
- A workflow is declared with `defineWorkflow` from `@github/copilot-sdk/extension` and registered by passing it to `joinSession({ workflows: [...] })`.
- Its metadata holds a stable `name`, a human-readable `description`, declared `phases` (each a `title` and an optional `detail`), an optional `argsSchema` and optional `limits`.
- `argsSchema` enforces structure (types, required properties, enum or const values) but only records finer constraints such as `minLength`, `pattern` or `additionalProperties`.
- A declaration outside the accepted schema subset is rejected at registration, and arguments passed by an extension through `session.workflow.run(...)` are not validated against `argsSchema`.
- `run(context)` returns a JSON value or nothing, and other non-JSON values are rejected.
- The context provides `ctx.runId` (stable across resumed attempts), `ctx.args`, `ctx.agent`, `ctx.parallel`, `ctx.pipeline`, `ctx.phase`, `ctx.log`, `ctx.step`, `ctx.pause`, `ctx.session`, `ctx.signal` and `ctx.workflow`, which always rejects because nested workflows are not supported.
- `ctx.agent(prompt, options?)` spawns one workflow-scoped subagent with the options `label`, `schema`, `model`, `agent`, `reasoningEffort` and `contextTier`, and resolves to its final text, or to parsed JSON when a schema is given.
- "Identical calls are memoized into one subagent": each call is journaled by its prompt and options including `label`, so N independent subagents need a unique `label` each or different prompts.
- "An ordinary failure resolves to `null` — it does not throw", including output that still fails the schema after its one retry, while cancellation and hard runtime failures (a reached limit, a durable-state failure) reject and abort the run.
- `schema` is "a structural subset of JSON Schema, not a validator": `additionalProperties`, `pattern`, `minLength`/`maxLength`, `format` and numeric ranges are ignored, and `oneOf` is treated as `anyOf`.
- A schema call retries once on a parse or match failure, so it may spawn twice, and both spawns count toward `maxTotalSubagents`.
- `ctx.parallel(thunks)` runs thunks concurrently behind a barrier, `ctx.pipeline(items, ...stages)` moves each item through the stages without a barrier, both turn a failed item into `null`, and both reject above 4096 items.
- The guide prefers `pipeline` for multi-stage work and a barrier only when a stage needs every prior result at once, because "if the slowest of N subagents takes three times the fastest, a barrier wastes the rest of the pool's time".
- `ctx.phase(title)` sets one run-global progress phase, so it should be called at run-level transitions, not inside concurrent stages.
- `ctx.step(key, producer)` journals the producer's JSON result under a key so that a resume replays it without running the producer again.
- The key is "the *sole* identity" of a step, so it should be versioned (`"scan-v2"`) whenever its inputs or meaning change.
- Journaled producers are "best-effort at-least-once" and may run again across crashes or concurrent same-key callers, "so keep side effects idempotent".
- `ctx.pause(key)` records a durable, one-shot checkpoint and pauses the run; on resume the workflow starts again from the beginning, replays the journaled steps and returns from the checkpoint.
- `ctx.pause` may be called only from the main workflow flow, not inside `ctx.parallel()` or `ctx.pipeline()`.
- Workflow-owned subagents are intentionally hidden from `read_agent` and `write_agent`, and the workflow observability APIs are used instead.
- Limits can be declared in `meta.limits` and overridden per invocation, and an omitted limit leaves that dimension unbounded, except that an omitted `maxConcurrentSubagents` falls back to `maxTotalSubagents`.
- `maxConcurrentSubagents` queues extra subagents without failing the run, and `maxTotalSubagents` caps cumulative admissions.
- `timeoutSeconds` measures accumulated active-execution time across attempts, including the extension body, subprocess waits, queued-agent waits and sleeps, is capped at `2_147_483.647`, and is soft because running work may take time to stop.
- `maxAiCredits` is a budget for the run's whole subagent subtree, "a soft, post-paid ceiling", and its accounting is fail-closed: an accounting failure stops a budgeted run.
- "A guessed ceiling does not make a run safer": it stops a healthy run partway with `workflow_limit_reached` after credits are spent, so a ceiling should come from a known cost or from the user.
- A limit breach ends the attempt with status `error` and `failure.type` `workflow_limit_reached`, and the run keeps its ID, arguments, journal and accounting for a resume with a raised limit, where earlier consumption still counts.
- `session.workflow.run(name, { args, limits, notifyOnComplete, logPhaseNames })` and `session.workflow.resume(runId, …)` resolve with a `WorkflowRunResult` envelope for every outcome: `completed`, `error`, `halted`, `paused` or `cancelled`.
- "SDK-initiated `run` and `resume` do not request permission", and an SDK-initiated run is refused only when the session already has its maximum number of active top-level runs.
- Pre-execution resume failures throw `WorkflowResumeError` with codes such as `not_found`, `non_resumable`, `already_active`, `workflow_limits_invalid`, `workflow_storage_unavailable` and `workflow_storage_corrupt`.
- The calling session can `pause`, `cancel`, `getRun`, `listRuns` (paged), `getRunDetail`, `getRunProgress` and `waitForRun`, and listen for the ephemeral `workflow.run_updated` event with a `{ runId, revision }` payload.
- Workflow prompts are never exposed by these APIs, and a run is visible only through the session that owns it.
- The file first appeared in the repository on 2026-09-22 in the SDK snapshot for Copilot CLI 1.0.88-2 and was updated on 2026-09-27 for 1.0.89-5.

#### [A] LangChain — How to Build a Model Router in the Harness, by Sydney Runkle and Eugene Yurtsev (2026-10-01)

<https://www.langchain.com/blog/how-to-build-a-model-router-in-the-harness>

- Key takeaway: "In our experiments, model routing cut median cost per coding task by 64% compared with the baseline, with no noticeable change in quality."
- Key takeaway: "An effective model router belongs in the harness, not a generic gateway."
    - "Choosing the right model requires domain and task context that the harness already assembles, and a gateway typically lacks."
- Key takeaway: "Effective router design is rooted in observability and evals."
- The post quotes Anthropic's model guide: "for many applications, starting with a faster, more cost-effective model like Claude Haiku 4.5 can be the optimal approach."
- "Past a certain point, you hit diminishing returns: a more capable model adds little quality while cost and latency keep climbing."
- The trigger: "our monthly coding agent spend started to climb rapidly", and customers raised the same concern.
- Against the previous baseline "of always using a top-tier frontier model, it cut median cost per thread by 64% with no measurable change in quality".
- The test bed is Open SWE, LangChain's open-source coding agent, which its engineers use from Slack and a web UI to ask about codebases and request code changes.
- Step 1, understand the tasks: thread-level LangSmith trace data (request kinds, cost and turn count of each thread) explored in LangSmith Custom Apps.
- A week of interactive threads was labelled by task type with an LLM classifier: "new features (22%) and bug fixes (17%) were the two largest groups, followed by test or no-op runs (16%)".
    - The categories are heuristics based on each thread's title and metadata, and the chart covers Aug 29 to Sep 5.
- Feature-work investigations ran longer, with higher cost and median turn count; testing and release procedures were short and inexpensive.
- Complexity was judged by total cost and invocation count; a high invocation count can mean a harder task or a model that needed follow-ups.
- "At the time of data collection, all of the Open SWE threads were being routed through a top-tier frontier model."
- The hypothesis: "a router could infer a task's type and difficulty from the initial request and send it to a cheaper or faster model without degrading outcomes".
- Step 2, understand the models: the Artificial Analysis Intelligence Index plots intelligence against cost per task, and "The Pareto frontier is the set of models that are the cheapest and smartest."
    - The chart data is as of Sep 9, 2026.
- The three tiers: "Fast: GLM-5.3-Flash (xhigh)", "Balanced: GPT-5.6 Sol (medium)" and "Performance: GPT-6 Astra (low)".
- "We selected models from different providers, and the fast tier is an open model."
    - GLM-5.3-Flash "sits on the Pareto frontier next to closed models".
- With LangChain's model interface, swapping in a better model "is a one-line change to the router".
- Step 3, build the router in the harness: the decision fits in LangChain middleware, which "can swap the model an agent calls without changing anything else about the agent" (dynamic model selection).
- The Open SWE router runs on the thread's first human message and has three parts.
    - "A base prompt: tells the classifier its job: pick the least expensive model likely to complete the task."
    - "Criteria per tier: a short, plain-language description of the work each tier should take."
    - "A classifier model: reads the request and picks a tier according to the criteria and prompt."
- "A general benchmark is only a starting point."
    - The tier criteria came from the task breakdown and from the provider guides for GPT-5.6 Sol, GPT-6 Astra and GLM-5.3-Flash.
- "Those criteria are written for Open SWE's task set, so the router is deeply coupled to the tasks Open SWE handles."
    - That is why it belongs in the harness, which has "the agent's task-specific context (its prompt, tools, and domain knowledge) that a generic gateway lacks".
- "Our first version used an LLM with structured output, prompted with the user's request."
    - "The classifier now runs on Jev, a newly released decision model, which made classification almost 50× faster."
- "The router picks a model once, at the start of each thread, and that model is used for the whole thread."
    - Mid-thread changes are "not addressed in this naive router design".
- Step 4, track task outcomes: "The value in a router is lower cost, but only if quality doesn't regress."
- Offline evals compare router versions safely and repeatably, but for a coding agent the dataset must judge "PR quality and reviewability, which are hard to grade offline".
- An A/B test uses live traffic as a representative dataset, with the downside that "users are subjected to a potentially non-optimal router".
- Outcome signals: Open SWE now records every PR it opens and whether it is merged or closed, and "Merged PRs per thread became our main success metric."
- Thumbs up and down were added to every thread and logged as feedback on the LangSmith trace; "Merged PRs were the stronger signal."
    - "Feedback was sparse, since only a small share of threads get rated, but it's where we heard about routing mistakes".
- The first A/B test: "half of threads went through the router, and half always used GPT-6 Astra, across 973 threads in total."
- "Quality didn't measurably change."
    - "29.2% of routed threads ended in a merged PR vs. 27.3% of control (p = 0.49)."
    - "PR open rates were also flat (38.9% vs. 39.6%, p = 0.82)."
- "The median routed thread cost $0.94 vs. $2.61 on control, 64% less."
    - "The mean dropped 42% and the p90 dropped 37%, so the savings weren't just a few cheap outliers."
- "Of routed threads, 56% went to balanced, 34% to fast, and only 10% to performance."
- "The cost ladder between tiers is steep: the median thread cost $0.097 on fast, $1.50 on balanced, and $2.88 on performance, a 30× spread."
- The cost chart covers "LLM cost per thread, Sep 16 to 22 (log scale)".
- Engineers flagged overspend on GPT-6 Astra with comments like "pretty expensive for this query" and "this request should not have been routed to the performance model."
- "This result isn't surprising, given the control was our most expensive model."
    - "But it's a change a lot of agents would benefit from: many over-rotate on quality and end up overspending."
- The second A/B test put the router against always using the fast model, and "We ended this test within a day, before it could produce statistically meaningful results."
    - "Engineers flagged problems with the fast-only arm almost immediately, and it was disrupting their productivity due to low output quality."
- What's next: benchmarking the router on DeepSWE or other coding benchmarks instead of relying on production A/B tests alone.
- What's next: model selection for subagents, since "Right now subagents pick their model independently of the router."
- What's next: re-routing mid-thread, at the cost of the prompt cache, though "For async agents that cost is often negligible, since the cache often expires anyways between human turns when the TTL is short (like 5 minutes)."
- What's next: refining the criteria with signals such as user frustration mined from traces, "which can mean the task needed a stronger model".
- Getting started: understand the tasks, understand the models, build the router in the harness, and track task outcomes.
    - "Treat routing as context engineering, analogous to classical feature engineering".
    - "If building an eval dataset is too costly or difficult, an A/B test on live traffic works well."
- "To add routing to your own agent, you can add our newly released model routing middleware."
    - "Give it your base prompt, model tiers, and the criteria for each, and it picks a model at the start of every thread."

#### [A] LangChain (GitHub) — Open SWE router code: model_selection.py, the tier prompts, the Jev helper and server.py (main, as fetched on 2026-10-03)

<https://github.com/langchain-ai/open-swe/blob/main/agent/middleware/model_selection.py>

- Open SWE is "An Open-Source Asynchronous Coding Agent", MIT-licensed, in Python, with 10,789 stars when fetched.
- `model_selection.py` (165 lines) defines the routes `fast`, `balanced` and `performance` and a `ModelSelectionMiddleware` that also holds a `default` model.
- `select_route` checks in order: a model the user requested in the opening message, routing switched off (`default`), a `model_route` already stored in state, `fast` mode, and otherwise Jev.
- Jev receives the latest human request, cut to its last 8,000 characters; injected context blocks such as sender metadata are skipped because they arrive as later `HumanMessage`s.
- `abefore_model` stores the route as `model_route` in agent state, and `awrap_model_call` swaps the model with `request.override(model=model)`.
- It streams a `model_routed` event so the UI can show the routed model next to `Auto`: "Routing display is cosmetic; never fail a run over it."
- `agent/utils/jev.py` calls `TypeSafeClassifier` with model `jev-1.13.0`, or `typesafe/jev-1.13.0` through the LangSmith gateway, under `JEV_TIMEOUT_SECONDS = 3.0`.
- An answer is accepted only when its confidence is between 0.6 and 1.0.
    - Missing credentials, errors, low confidence or a choice outside the criteria return no route, and the middleware uses its `default` model.
- The base prompt (`model-selection/instructions.md`): "Choose one fixed model profile for this Open SWE turn."
    - "Use the least expensive profile likely to complete the whole turn safely."
    - "Explicit targets, clear acceptance criteria, reversibility, and strong tests lower the required capability."
    - "Ambiguous requirements, weak verification, architectural tradeoffs, broad scope, consequential security or data work, and conflicting assumptions raise it."
    - "Prompt length and eventual runtime are not difficulty signals."
- Fast tier criteria: "Use for direct lookup, extraction, status checks, test or log collection, mechanical PR or release operations, and localized changes with explicit targets and strong verification."
- Balanced tier criteria: "Use for ordinary bug fixes, bounded investigations, multi-file implementation, research synthesis, semantic PR maintenance, and partially specified localized work."
- Performance tier criteria: "Use for architecture or design, requirements disambiguation, subtle semantic review, novel root-cause reasoning, conflicting evidence, cross-component or multi-repository judgment, and high-stakes decisions."
- In `server.py` the tier models come from workspace settings (`agent_routing_models`) and can be overridden per thread.
- When Auto routing is on, the default model becomes the fast tier: "Auto never falls back outside its tiers: an uncertain route uses Fast."
- A `/oswe` question in Slack never routes adaptively: "one question gets one answer, so there is nothing to route."
- `_MODEL_ROUTING_SPLIT = 0.5` still assigns each routed thread, by a SHA-256 hash of its thread id, to `auto` or to `fast` mode.

#### [A] Zenn (tksfjt1024) — How is Claude Code's usage counted? The weights measured on Max 20x differed from the API price list (2026-10-01, in Japanese)

<https://zenn.dev/tksfjt1024/articles/25c0ab111c277c>

- On Pro and Max plans Claude Code draws on two limits, the "5時間のセッション制限" that resets every five hours and the "週間使用制限" that resets weekly (the Help Center's terms), and the author measured under controlled conditions what moves each of them to derive a formula for usage.
- Headline results: cache reads count toward usage, but one cache-read token weighs 1/40 (0.025x) of an input token.
- Headless use (`claude -p` or the Agent SDK) drains the 5-hour window twice as fast as interactive mode for the same tokens, 2.86x during the peak hours (weekdays 21:00 to 03:00 JST), and the weekly window 1.25x as fast at any time.
- The model weights are Haiku 4.5 : Sonnet : Opus 5.5 : Opus 5 : Fable 5.1 = 1 : 1.5 : 2.2 : 2.75 : 10, unlike the ratio of API input prices (1 : 2 : 4 : 5 : 10).
- The counting method changed without notice in mid-September 2026, and the 20% increase in the 5-hour window that Anthropic announced afterwards measured as 1.11x.
- Requests can still go through while `/usage` shows 100%.
- The formula: usage of one request = model weight × (input + cache write × 1.25 + output × 5 + cache read × 0.025), where each term is a token count.
- 5-hour utilization = (sum of interactive usage + sum of headless usage × 2) ÷ 300 million × 100%, and weekly utilization = (sum of interactive usage + sum of headless usage × 1.25) ÷ 1.13 billion × 100%, each summed since that window's reset.
- 300 million (3億) and 1.13 billion (11.3億) are the sizes of the Max 20x 5-hour and weekly windows expressed in Haiku 4.5 input tokens.
- The headless × 2 on the 5-hour window becomes × 2.86 in the weekday peak hours, while the weekly × 1.25 does not vary with the time of day.
- The formula also predicted a workload dominated by tool calls and cache reads, the auto mode test in the appendix, to within 0.002 points of the actual utilization.
- Coefficient table (2026-09-29 version), token types: input 1 (excluding cache writes and reads), cache write 1.25 whether the cache TTL is 5 minutes or 1 hour, output 5 including thinking with no surcharge by effort, and cache read 0.025 regardless of model (measured on Opus 5, Opus 5.5 and Sonnet 5.5).
- Model weights: Haiku 4.5 1, Sonnet 5 1.5, Sonnet 5.5 1.5, Opus 5.5 2.2, Opus 5 2.75 and Fable 5.1 10.
- The window sizes are Max 20x values and differ by plan.
- From the ratio of the two windows, interactive use alone fills the weekly window after about 3.8 full 5-hour windows (1.13 billion ÷ 300 million; about 4.2 before the 20% increase of 09-23), headless use alone after about 6 ((1.13 billion ÷ 1.25) ÷ (300 million ÷ 2)), and after about 8.6 in the weekday peak hours.
- Worked example: an interactive Opus 5 request with input 2,000, cache write 3,000, output 1,000 and cache read 100,000 tokens weighs 2,000 + 3,750 + 5,000 + 2,500 = 13,250, and 2.75 × 13,250 = 36,437.5, about 0.012% of the 5-hour window and 0.0032% of the weekly window.
- About 82 such requests make 1% of the 5-hour window, and the cache reads are 94% of the tokens but count 2,500, half of what the output counts.
- The model weights come from the input tokens that move the headless 5-hour window by 1% outside the peak hours, measured on 2026-09-24 (Sonnet 5.5 on 09-29): Haiku 4.5 1.486 to 1.490 million, Sonnet 5 987,000 to 992,000, Sonnet 5.5 996,000, Opus 5.5 675,000 to 680,000, Opus 5 544,000 and Fable 5.1 150,000 to 155,000.
- Multiplied by the weights, every model lands within one request's error of about 1.49 million (Fable 5.1 takes 30 to 31 requests per 1%, so one request makes a spread of about 3%).
- Against the API price list, the token-type weights match for input (1), output (5) and the 5-minute cache write (1.25), but the 1-hour cache write counts 1.25 against 2 on the API.
- Cache reads count 0.025 against API ratios of 0.1 for Haiku 4.5, Sonnet 5, Sonnet 5.5 and Opus 5, 0.05 for Opus 5.5 and 0.025 for Fable 5.1.
- Claude Code on a subscription uses a 1-hour cache TTL (the author quotes Addy Osmani's post), so its cache writes would cost 2x input on the API but count 1.25x against the limits.
- With Opus 5 = 1, the limit weights are Haiku 4.5 0.36, Sonnet 5 and Sonnet 5.5 0.55, Opus 5.5 0.8 and Fable 5.1 3.64, against API input prices of $1, $2, $2, $4 and $10 per million (0.2, 0.4, 0.4, 0.8 and 2 relative to Opus 5's $5).
- Sonnet and Opus weigh less than their price ratios and only Fable 5.1 equals its price ratio of 10, so Fable 5.1 costs 2x Opus 5 on the API but drains the limits 3.64x as fast.
- Switching from Opus 5 to Opus 5.5 lowers the API-equivalent cost of the same tokens to 0.8x for input and output and 0.4x for cache reads, but the limit usage only to 0.8x, cache reads included.
- So limit consumption per API-equivalent dollar rises on Opus 5.5 by a factor set by the cache-read share of the Opus 5 API-equivalent cost (not of the tokens): 1.43x at 0.6, 1.67x at 0.8 and at most 2x when everything is cache reads.
- A report on Max 20x saw weekly consumption per API-equivalent dollar rise 1.3 to 2.5x between the weeks before and after switching the main model from Opus 5 to Opus 5.5 (a comment on anthropics/claude-code #97398), up to 2x of which this mechanism may explain.
- Claude Code sends a `cc_entrypoint` value with each request (`cli` for interactive mode, `sdk-cli` for headless), and the same tokens drain the windows at different rates by it.
- Only the headless 5-hour window speeds up in the peak hours; neither the interactive 5-hour window nor the weekly window varied with the time of day.
- The peak hours (weekdays 21:00 to 03:00 JST) match, under daylight saving time, the peak hours Anthropic announced in March 2026 (weekdays 5 to 11am PT), so if they are set in Pacific time they will move one hour later in JST when daylight saving ends in November.
- Every difference in the multiplier table is explained if neither the 05-06 announcements (the doubled 5-hour window and the end of the peak-hours reduction) nor the weekly +25% from 09-14 apply to headless use, while the 20% increase of 09-23 did apply to it.
- GitHub issue #97074 found headless drawing the 5-hour window about 1.8x as fast on Max with Opus 5 and narrowed the two requests' differences to `cc_entrypoint`, the User-Agent and one beta header, and a reproduction in the same issue on Pro with Opus 5.5 found about 2.0x (1.8 to 2.2x with the 1% reading error), matching the author's × 2.
- Timeline (JST): on 05-06 Anthropic doubled Claude Code's 5-hour window and removed the peak-hours reduction for Pro and Max, from 05-13 to 09-13 the weekly window ran at +50% as a promotion, and from 09-14 it stood at +25% over the pre-promotion level (announced on 08-30).
- In mid-September (09-17 to 09-18 on the author's account) the counting switched to a new method without an announcement, its per-type weights were posted to r/ClaudeCode on 09-18, and at 01:44 on 09-23 Anthropic announced "5-hour session limits increase 20% today" and that Opus 5.5 "goes 25% further within limits" with the release of Opus 5.5.
- Formula until early September: input 1, cache write 1, output 8, cache read 0, a 5-hour window of 186 million and headless × 2, with the same model weights as now.
- Right after the change (09-18): input 1, cache write 1.25, output 5, cache read 0.025, a 5-hour window of about 267 million and headless × 2; now the same weights with a 5-hour window of 300 million.
- The author infers a gradual switch-over in mid-September, since there was no announcement.
- The window sizes moved twice: about 1.45x for both windows with the counting change, then 1.11x for the 5-hour window only after the 09-23 announcement, so today's 300 million is about 1.6x the 186 million of early September (1.45 × 1.11 ≈ 1.6).
- In the author's interactive use, the same work consumed about 0.66x as much of the 5-hour window after the change (until the 09-23 announcement), but usage with extremely many cache reads relative to cache writes and output became heavier.
- Announcements checked against measurements: the weekly +25% from 09-14 over the pre-promotion level matched for interactive use (the measured change agreed with 150 → 125 within error) but not for headless use, whose weekly multiplier is still × 1.25.
- The claim that Opus 5.5 goes about 25% further within the limits matched (weight 0.8x of Opus 5), and so did the claim that the extra cache-read cut is an API price change (cache reads weigh 0.025 on both Opus 5 and Opus 5.5).
- "5-hour session limits increase 20%" did not match: the 5-hour window grew 1.11x and the weekly window 1.001x, and as of 09-29 Anthropic had not stated a baseline.
- Measured headless, outside the peak hours, on Opus 5: 1% of the 5-hour window took 492,000 input tokens before the announcement (09-18) and 544,000 after (1.11x), while 1% of the weekly window took 3,296,000 and 3,299,000 (1.001x), and remeasuring days later gave the same values.
- In interactive use too, the ratio of the 5-hour and weekly windows derived from everyday logs shifted by 1.12x across the announcement.
- Other baselines do not fit either: a +20% with the weekly window cut at the same time would have shrunk the weekly window (it stayed at 1.001x), the pre-change window would give 1.2x (measured about 1.6x), the ratio to the weekly window would shift by 1.2x (measured 1.12x), a daily average including the peak would change the peak multiplier (× 2.86 unchanged), and a phased rollout would keep moving (it did not for days).
- The remaining explanations are a rollout over a longer period, a rate that differs by plan (20% on Pro and others), or an announced figure that differs from the actual change, and which one holds is unknown.
- Precedent: the weekly 25% increase from 09-14 was relative to the pre-promotion window, which made it about 17% smaller than in the +50% period (125/150), as Anthropic said in a follow-up post, so Anthropic's percentages are not always relative to the window just before.
- The status line's `rate_limits` `used_percentage` is built from the response headers `anthropic-ratelimit-unified-5h-utilization` and `anthropic-ratelimit-unified-7d-utilization` (checked in the code of Claude Code 2.1.283), whose values are a 0 to 1 fraction rounded to 0.01.
- The integer percentage on the `/usage` screen comes from an API that Claude Code calls for that display, and it is 0 below 0.5% and otherwise rounded up.
- So with a header value of 0.99 the status line can show 99 while `/usage` shows 100, requests still pass and are counted, and they are refused with a 429 once the unrounded value reaches 1.0 (both observed on the weekly window).
- Implications for use: over 96 five-hour cycles of the author's normal interactive use in September, the median share of cache reads in tokens was 96%, so counting cache reads as 0 like the old method underestimates cache-heavy use.
- Headless runs in the peak hours drain the 5-hour window 2.86x as fast as interactive use.
- Thinking counts as output at 5x, and xhigh and low effort on Opus 5.5 showed no surcharge, so effort affects usage only through the number of output tokens, thinking included.
- Opus 5.5 uses 0.8x the usage of Opus 5 for the same tokens.
- The auto mode classifier runs server-side by default and was not counted toward the windows; only with `CLAUDE_CODE_AUTO_MODE_SERVER=0` does it run locally, as separate Sonnet 5 requests counted by the formula, at about 0.0008% of the 5-hour window per check in interactive mode.
- Prior reports checked: shellac (2026-01-25) derived from unrounded claude.ai values that cache reads were not counted, cache writes weighed the same as input and output 5x, which matches the author's pre-September formula on cache reads 0 and cache writes 1.
- skipbit (2026-08-12) found tokens per 1% of the weekly window swinging 1.8x within a week, which the author calls natural for totals that include cache reads while they were not counted.
- Classmethod's DevelopersIO (中島健雄, 2026-08-20) found cache-read weights of 0 to 0.12x the API cache-read price consistent with its observations, a range that contains the author's pre-September 0.
- An r/ClaudeCode post (flobernd, 2026-09-18) published new-method weights on Opus 5 of cache read 0.027±0.005, 1-hour cache write 1.21±0.06 and output 4.49±0.48, broadly matching the author's, except a provisional 1.00 for the 5-minute cache write.
- claude-usage-tracker (jonathanavis96) estimated from everyday logs by regression, with Opus = 1, Sonnet 0.406, Opus 5.5 0.687 and Fable 2.159 (2026-09-29 version) and treats cache reads as 0 (2026-09-28 analysis), while the author's equivalent ratios of 0.545, 0.8 and 3.64 all exceed the upper bounds of its 80% intervals.
- An r/ClaudeCode post (BobMcFizzington, 2026-09-27) on Opus 5.5 and Max 20x gives tokens per weekly 1% that imply a cache-read weight of 0.018 to 0.064, a range that contains 0.025.
- As far as the author found (as of 2026-09-29), no other report measured six model weights under the same conditions or checked the 20% increase with a before-and-after comparison under the same conditions.
- Caveats: the coefficients were derived on Max 20x and not checked on Pro or Max 5x, except the headless-to-interactive ratio, which the Pro reproduction in #97074 also showed.
- The cache write weight of 1.25 was measured on headless Opus 5 only, and output 5 and cache read 0.025 on Opus 5, Opus 5.5 and Sonnet 5.5.
- The 5-hour window size (300 million) was measured with interactive requests of over 140,000 tokens each, so one request's error is about 14% of 1% of the window.
- The peak-hours difference was measured on weekdays, not on weekends.
- Utilization reads only in 1% steps, so the usage of arbitrary work cannot be predicted as precisely as in the appendix's check.
- The model weight ratios and the headless × 2 on the 5-hour window did not change across the September change, but the window sizes moved with the counting change and the announcement, so they should be read with the measurement dates.
- Fable 5.1 usage also counts toward a separate model-specific limit of up to 50% of the weekly window, which the article does not cover.
- Utilization also moves for reasons outside the formula: resets of both windows for all users on 09-02 and of Max weekly windows on 09-05 as announced, a reset to use any time until 10-22 granted with the 09-23 announcement, and many Reddit reports of weekly utilization dropping to about 0.69x on 09-16 with no official explanation found.
- Use that leaves no local logs, such as GitHub Actions' claude-code-action running on subscription authentication, also counts toward the same windows.
- Method: a proxy that forwards requests unchanged, set through `ANTHROPIC_BASE_URL`, recorded each response's usage by token type and the utilization headers.
- Because utilization reads in 1% steps, each weight was derived from what was sent while utilization moved by 1%: first the input-only amount per 1%, then requests rich in the measured type, giving weight = (input-only amount per 1% − the other types weighted) ÷ tokens of the measured type.
- Interactive values were measured in a session running under tmux, sending large inputs with caching disabled.
- For the auto mode test, 20 instructions that each made Claude Code run Bash 10 times (headless, outside the peak hours, Opus 5, 220 requests in all) were run with classification server-side (the default), off and local, comparing utilization computed from the proxy log with the actual figure: 2.574% against 2.576%, 2.233% against 2.235%, and 2.523% against 2.521% (local, including 200 Sonnet 5 classifier requests).
- Server-side classification sends no separate requests, so the computed value left it out and still matched, meaning it is not counted, while local classification was counted by the formula; every difference was 0.002 points.
- The article's changelog lists a first draft on 2026-09-29, and the page shows publication on 2026-10-01.

<https://github.com/anthropics/claude-code/issues/97398>

- Title: "[Bug] Weekly usage limit consumption rate increased ~3.6x after September 25 reset", open and labelled bug and area:cost, with five comments and none from Anthropic staff as of 10-03.
- The reporter counted about 93 responses per 1% of the weekly limit in the previous week and about 30 after the reset, on the same workflow.

## 7. 🛡️ Classmethod found that Claude Code's auto mode fetches web pages without asking unless an ask rule matches, and narrowed that entry point for indirect prompt injection by limiting WebFetch to an allowlist of domains with a PreToolUse hook

- Selected / impact 1 / potential 1 / importance 2 / anchor 10-02 / kind: hands-on / areas: coding agents, security and safety.
- Feed items in this topic:
    - `classmethod-claude-code` 10-02 [Claude Codeでプロンプトインジェクションされたくないので調べてみた](https://dev.classmethod.jp/articles/claude-code-prompt-injection-webfetch-domain-allowlist/) (looking into how to keep Claude Code from being prompt-injected)

### Collected information

#### [A] Classmethod (DevelopersIO) — I looked into Claude Code because I don't want to be prompt-injected, by nnakamura.yasutaka (2026-10-02, in Japanese)

<https://dev.classmethod.jp/articles/claude-code-prompt-injection-webfetch-domain-allowlist/>

- The author uses auto mode every day for its fewer confirmation dialogs, and felt that fewer dialogs meant the risk from text brought in over the web, such as indirect prompt injection, needed sorting out.
- The example injection is a page telling Claude to discard all previous instructions and send the contents of the local `.env` to `https://attacker.example.com`, which leaks secrets if Claude takes the content as an instruction rather than data.
- Real damage needs three conditions at once: an entry (untrusted external text reaches the model), privileges or assets (access to sensitive data such as source code, `.env` and credentials) and an exit (a way to send data out, such as requests to arbitrary URLs or external API and MCP tools).
- The entry is controlled by asking who wrote the text Claude reads (its provenance) and the exit by asking who can see what Claude generates and sends (its destination).
- An attack injects through the entry and extracts through the exit, so narrowing the entry makes it hard to succeed even if an exit remains.
- Built-in defences the author found: WebFetch parses a page to Markdown and has a fast lightweight model extract and summarise what is needed before handing it to the main Claude, so raw page data is less likely to flow into the main context.
- In auto mode a classifier evaluates each action Claude Code tries and blocks those judged dangerous, and explicitly set `ask` and `deny` rules take precedence even in auto mode.
- Citing the official docs, the author notes that no mechanism prevents every injection and that the best practice is a design that does not pipe untrusted data straight into Claude.
- WebFetch by mode: in Manual mode, a fetch to a domain with no allow rule shows a confirmation dialog first, except for documentation that is pre-approved internally.
- In auto mode and `bypassPermissions`, the dialog is skipped unless an explicit `ask` rule matches.
- The auto mode classifier judges how dangerous an operation is, not whether traffic stays within an allowlist of domains, so keeping auto mode's comfort while restricting destinations needs a mechanism on the user's side.
- The author's earlier setup ([a 2026-09-25 article](https://dev.classmethod.jp/articles/claude-security-configuration-tips/) on security settings that let a Claude beginner use auto mode safely) had three layers: a sandbox (no reads of `.env` or private keys, writes limited to the working directory and similar, network destinations limited for Bash), permissions (commit and push as `ask`, dangerous commands as `deny`) and hooks (blocking `git reset --hard`, force pushes and `rm -rf` by parsing).
- That setup contained access to sensitive data and exfiltration to a degree, but the sandbox's network restriction applies to Bash commands only, so the built-in WebFetch sat outside the defences.
- Left as it was, WebFetch could be both the entry that reads malicious text and an exit that carries data out in query parameters.
- Four approaches were rated (◎ sufficient, ○ mostly good, △ has issues, ✕ insufficient) on certainty of defence, setup and maintenance cost, developer experience and ease of judging extensions: (1) detecting content ✕ ○ ◎ △, (2) a dedicated subagent ○ △ ○ △, (3) blocking exits △ ✕ △ ✕, and (4) narrowing the entry ◎ ◎ ○ ◎.
- (1) Detecting content, rejected: scanning fetched HTML or Markdown with regular expressions or heuristics for suspicious phrases, such as telling the model to ignore its instructions, is possible by replacing content with a PostToolUse hook's `updatedToolOutput`, but it is weak against rewording, other languages and obfuscation.
- (2) A dedicated subagent, rejected: a subagent with only WebFetch and WebSearch that returns summaries isolates to a degree, but agent definitions and anti-impersonation hooks bloat operations, and injected text can still propagate through the summary.
- (3) Blocking exits, rejected: putting `ask` on every action that can trigger sending data (navigation by browser-automation MCP servers, external API calls, posting issues) means enumerating every route and adding rules for each new MCP server or plugin.
- (4) Narrowing the entry, adopted: an allowlist that limits the data sources Claude Code can fetch to trusted publishers.
- Trusted sources are places only the company or the project's stakeholders can write to (internal repositories, internal Notion or wiki, tech blogs written by employees) and primary official documentation hosted by cloud vendors and framework developers, and publicly editable sites and forums are excluded in principle.
- The deciding factor is a security criterion that fits in one line: text Claude Code reads is limited to what people inside the company or project stakeholders wrote, or official documentation.
- The same question, who wrote the text a tool feeds in, then decides whether to allow a new tool or MCP server.
- WebSearch stays allowed, because it returns only the titles and URLs of results without bodies, and fetching a body calls WebFetch, where the domain restriction applies.
- Research that needs Qiita, Zenn or Stack Overflow is done in claude.ai, and a human passes the summary to Claude Code.
- Implementation: a PreToolUse hook with matcher `WebFetch` in `~/.claude/settings.json` runs `/usr/bin/python3 ~/.claude/hooks/webfetch-domain-allowlist.py` with `"timeout": 5`, checks the destination domain before the fetch and blocks domains not on the list.
- A hook is used instead of `permissions` because `permissions` alone cannot cleanly express blocking everything except specific domains (default deny).
- The script matches a host exactly or as a subdomain with `host.endswith("." + d)`, which rejects spoofs such as `code.claude.com.attacker.com` and `fakecode.claude.com`.
- Fail-closed: a hook script that ends abnormally on an exception can be treated as a non-blocking error that lets the action proceed, so the script wraps everything in `try-except` and on any error still prints `deny` as JSON and exits with 0.
- The `permissionDecisionReason` asks Claude to tell the user to research in claude.ai, so that Claude can propose a next step after a denial.
- In case Claude turns to a browser-automation MCP server when WebFetch is blocked, `ask` rules cover opening pages and navigating to URLs, so those prompt every time.
- Unit tests with edge cases: `https://code.claude.com/docs/en/hooks` allowed (exact match), `https://docs.aws.amazon.com/lambda/` allowed (a subdomain of a listed domain), `https://code.claude.com.evil.io/x` denied (suffix spoof), `https://evil.io\@code.claude.com/` denied (the `@` that confuses parsers), `http://code.claude.com/` denied (plain http) and `https://192.168.1.1/` denied (an IP address).
- In a live auto mode session, a URL outside the list returned the hook's reason to Claude, which pointed the user to claude.ai; the reason read that example.com is not an allowed domain and that Claude should tell the user to do research beyond official documentation in a claude.ai chat.
- claude.ai chats cannot reach local files, so injected instructions on a page cannot touch `.env` or the repository; the Claude Code feature inside the desktop app touches local files and is excluded, and connectors should be off in research chats.
- The research flow: search and summarise in claude.ai (asking for key points and code snippets only), have a human review the summary for stray instructions, and paste only the needed conclusions into Claude Code, never raw page text.
- Effects: WebFetch now reaches only listed domains, which the author feels lowers the risk of auto mode considerably, and the roles are clear, with Claude Code reading trusted resources and broad research in claude.ai.
- Remaining risk: injection through the file system, such as third-party OSS package code, files cloned from public repositories and imported issues, still exists.
- The article shows the settings, the design points, the test table and the denial message, but not the hook script itself.

#### [A] Anthropic — Claude Code docs: WebFetch behavior and WebFetch permission rules (as fetched on 2026-10-03)

<https://code.claude.com/docs/en/tools-reference>

- WebFetch takes a URL and a prompt, converts HTML to Markdown and, for most fetches, "runs the prompt against the content in a separate model call, and Claude receives the result of that call rather than the raw page".
- "In Manual and `acceptEdits` permission modes, WebFetch prompts before fetching, except for domains your permission rules already allow or deny and a built-in set of preapproved documentation domains that fetch without a prompt."
- "The `auto` and `bypassPermissions` permission modes skip the prompt, except for a domain an explicit `ask` rule matches."
- An explicit `WebFetch(domain:...)` rule in `deny`, `ask` or `allow` takes precedence over the preapproved set, so a preapproved domain can be blocked or made to prompt.
- When a URL redirects to a different host, WebFetch returns the original URL and the redirect target instead of following it, and Claude fetches the target with a second WebFetch call.
- WebFetch refuses `localhost` and dotless hostnames, caches each response for 15 minutes by default, sends a `User-Agent` beginning with `Claude-User`, and never reads the sandbox allowlist.
- `CLAUDE_CODE_DISABLE_WEB_FETCH=1` turns WebFetch off on v2.1.285 or later.
- WebSearch "returns result titles and URLs" and "doesn't fetch the result pages", and its permission rules take no specifier.
- The [permissions page](https://code.claude.com/docs/en/permissions) says WebFetch rules use a `domain:` prefix matched against the URL's hostname, case-insensitively and ignoring a trailing dot.
- `WebFetch(domain:*.example.com)` matches subdomains at any depth but not `example.com`, and a wildcard in any other position matches only the text between two dots (v2.1.172 or later).
- "Rules are evaluated in order: deny, then ask, then allow."
- "An allow rule can't carve an exception out of a deny rule", and "a matching ask rule prompts even when a more specific allow rule also matches the same call".
- The page suggests denying `curl` and `wget` and allowing domains with rules such as `WebFetch(domain:github.com)`, while noting that "using WebFetch alone doesn't prevent network access" when Bash is allowed.
- "A hook that exits with code 2 stops the tool call before permission rules are evaluated", and to run a tool without prompts except for a few calls, the docs suggest allowing the tool and registering a PreToolUse hook that rejects those calls.

#### [A] Grafana Labs (Unprompted on Medium) — Enter the arena: evaluating and improving Grafana Assistant Investigations against real incidents, by William Dumont (2026-07-15, background)

<https://medium.com/grafana-labs/enter-the-arena-evaluating-and-improving-grafana-assistant-investigations-against-real-incidents-d0a813404ad2>

- The first evaluation used synthetic telemetry, and "It passed, and kept passing, while still struggling on real incidents in the ways that mattered."
- Synthetic cases "get too simple and the errors are too classic."
- The team built an "arena" where different builds of the agent work the same real incident and are graded against each other, and in one week the score on its internal suite of difficult incidents moved from 52% to 69%, which the post also calls a 33% improvement.
- Cases come from real, already resolved production incidents, and the agents also get code access through the GitHub MCP server and the GitHub CLI.
- Each case has an entry prompt built from the firing alert and grading criteria extracted from the human-written analysis (blast radius, root cause, contributing factors), and "The incident report serves as ground truth."
- Every case has a time cutoff at the moment the incident began, and incident-management records with the resolution are excluded, so that an agent cannot "cheat".
- Grading works on individual claims: a criterion is "fully met, partially met, or missed", and the weighted fraction is the score.
- "Quality is the only quantity we optimize."
    - Duration, tool calls, model calls, token counts and dollar cost are recorded but kept out of the score, and are used only to choose between variants of equal quality.
- Most changes were "found by reading transcripts, then confirmed by the score rather than discovered through it", across thousands of investigations, and a change ships only when the pattern holds across many incidents.
- The team varied one factor at a time: tool sets (removing tools one by one), models and thinking budgets, prompts, and external agents connected through the Grafana MCP server, gcx or direct HTTP as an upper bound.
- "Interestingly, changing the underlying model was less of a contributing factor than either of these", meaning tools and prompts.
- Findings: a tool that reads the alert definition and its query; a query tool that was almost never called because its guide had been copied from another tool and described the wrong query language; a small, cheap model call that filters retrieved memory; prompts that ask the agent to state what it cannot conclude.
- "In several cases a smaller model at an appropriate effort level matched a larger one."
- Still hard: the agent tends to present something as the root cause even when the evidence does not justify a confident conclusion, and the suite keeps adding fresh incidents so the agent meets cases it was not tuned on.

### Notes

- The write-up is not an independent analysis: its author is a Staff Developer Advocate at Grafana Labs, and every other A source except Anthropic's also comes from Grafana Labs or its staff.
    - Outside Grafana, only SiliconANGLE's launch news (no analysis), the MicroFIRE deep dive with its own partial run and three GitHub contributions were found, and no coverage of the write-up itself appeared in the window.
    - The author's affiliation rests on Zenn's and GitHub's APIs, because the cached Zenn profile page is thin.
- Reading the graders as checks on the agent's steps rather than on its final answer overstates the sources.
    - They say the final answer alone is not enough and grade outcomes and grounded evidence (saved state, query shape, facts computed from the environment, cited trace IDs), while expressly not grading the path: Ekinci's "Unless policy requires a specific path", the grading README's "without forcing one exact wording or one exact solution path" and Anthropic's "grade what the agent produced, not the path it took".
    - In o11y-bench, 167 of 247 criteria judge the final response against a source of truth, 35 refer to the transcript or tool output, and 13 checks verify cited trace IDs, so the graders check grounded outcomes more than the steps or the final answer's wording.
- Pass^3 is defined two ways in the April announcement and its Japanese edition: "the average benchmark score across three runs", and in the same post "got it right all three times".
    - The leaderboard, the reporting code and Anthropic's definition all use the second.
    - A task passes only when every check and criterion passes, so the weights the write-up describes shape only the mean `score`, not the leaderboard's pass or fail, which the write-up does not mention.
- The local run report leaves trials with infrastructure failures, including non-zero agent exits, out of pass^k and pass@k, while the leaderboard says non-zero exits score 0, so a local report may read higher than the leaderboard for the same run (inference from the code and the page).
- "3 attempts by default" holds for `mise run bench:job` and `bench:suite`; the raw Harbor `job.yaml` sets `n_attempts: 1`.
- The grading README promises three check families and lists two, `grounding` and `state`; the code has five modes under those two types.
- The judge defaults to Claude Haiku 4.5 through the Anthropic SDK, so the judge model cannot be swapped for another vendor's without code changes, and the leaderboard's top places are all Claude models.
    - No source discusses whether a same-vendor judge favours them; Anthropic's build-eval guidance (topic 9 of 2026-10-01) recommends a judge other than the model under test, so this stays an open question.
- Sample sizes are small: by my calculation a 95% Wilson interval for 50 of 63 tasks runs from 67.8% to 87.5%, and for 43 of 63 (fifth place) from 56.0% to 78.4%, so the top five overlap (inference); PR #56 proposing such intervals has had no review since 08-24.
- Ekinci's post gives no category sizes: 92.3% and 94.9% equal 36 and 37 of 39, so the discover gain may be one trial out of 39 if that category has 13 scenarios (inference), which tempers the post's "three percentage point drop" rule for small categories.
- Grafana's own teams differ on method.
    - Ekinci tracks quality, cost and latency together and treats the tradeoff as the decision, while Dumont's arena optimises quality only and uses cost to break ties.
    - Dumont grades claims with partial credit, while o11y-bench asks YES or NO per criterion and needs all of them for a pass.
    - Dumont found that model changes mattered less than tools and prompts.
- The open repository reproduces the measurement only: Ekinci says the coding-agent improve loop (`LLM Spec Improve`) is internal, LLM Spec is written in Go, and turning production conversations into offline tasks is not yet automated.
- Parts of the MicroFIRE deep dive no longer match `main`: `SKIP_LLM_GRADING` appears nowhere in the repository, and 2 of the 11 investigation tasks now carry trace-ID checks, so the category is not graded by the rubric alone.
    - Its claim that the final answer is only auxiliary overstates the grading, since most criteria judge the final response.
- Issue #41's second complaint does not hold for the required Python version, because Python 3.14 allows `except` expressions without brackets ([What's new in Python 3.14, PEP 758](https://docs.python.org/3/whatsnew/3.14.html)); the `pyiceberg` build failure was not tested in this run.
- The Sigil-era names of Agent Observability retire at the end of October 2026, so a team on the old SDK packages, dashboards or RBAC names has a migration to make.
- The leaderboard's "Avg Cost" equals the total divided by 189 trials (63 tasks times 3), so it is a per-trial figure (inference from the arithmetic).
- Maurice Rochau's post, cited by the write-up, returned HTTP 403 to both the page cache and WebFetch.
- Compared with topic 9 of 2026-10-01 (Anthropic's `/claude-api build-eval` and `hillclimb`, and Hamel Husain's review), Grafana's loop is the same measure-change-remeasure cycle with a coding agent and a human gate.
    - o11y-bench puts all criteria in one judge call, whereas Hamel Husain argued for one evaluator per failure mode and for keeping code checks and judges apart.

### Ideas for practice and output

- Run two or three tasks of o11y-bench for one or two models (for example `promql-cache-refresh-lag-peak`, `dashboard-add-cache-lag-panels` and `traceql-cache-refresh-hotspot` with the default 3 attempts), then read `verifier/grading_details.json` and `agent/trajectory.json` to see which criterion failed and why.
    - The leaderboard's per-trial costs range from under a cent to about $0.81, and Python 3.14 plus Docker are required; issue #41 may bite during installation.
- Measure judge agreement before trusting the scores: regrade the same saved jobs with `GRADING_MODEL` set to a larger Claude model and count the criteria whose verdict flips, then have two people grade ten transcripts by hand, as the post's two-experts test suggests.
- Port the task shape to the team's own agent: ten to twenty tasks with a user-voiced `statement`, state `checks` for artifacts, and rubric criteria each paired with a `fact` query computed from the environment at grading time; run three attempts and report pass^3 and pass@3 per capability with Wilson intervals against a baseline.
- Compare tool interfaces on fixed data: run the default MCP agent and `GcxOpenCodeAgent` on the same tasks with `O11Y_SCENARIO_TIME_ISO` pinned, which repeats Grafana's own MCP-against-CLI comparison.
- Write a short team note that maps Ekinci's six starting steps and the four kinds of decay onto the team's current evals, and contrasts them with Anthropic's build-eval and hillclimb from 2026-10-01.
