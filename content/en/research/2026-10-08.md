#### [A] Anthropic — What's new in Claude Haiku 5.5 (as fetched on 2026-10-08)

<https://platform.claude.com/docs/en/models/haiku-5-5/whats-new-haiku-5-5>

- Built "for high-volume, latency-sensitive work such as classification, routing, extraction, and subagent tasks".
- Tokenizer: "the same input text produces approximately 30% more tokens on Claude Haiku 5.5 than on Claude Haiku 4.5", and "The exact increase depends on the content."
- Context and output: 1M tokens and 128k output, "up from 200k and 64k on Claude Haiku 4.5".
- Thinking tokens count toward `max_tokens`, "so a small limit can stop after a `thinking` block and before any text".
- New: adaptive thinking and effort, the larger context and output, the browser use tool ("Available on the Claude API and Google Cloud"), and safety classifiers that can decline a request (handle `stop_reason: "refusal"`; "Server-side fallback isn't available").
- Breaking: manual extended thinking, non-default sampling parameters and assistant prefill return errors; computer use needs `computer_toolset_20260801` on the Claude API and Google Cloud; changing earlier turns invalidates thinking blocks.
- Changed: responses can begin with thinking blocks ("Select content blocks by `type`, not by position"); thinking text is omitted by default; the same text counts as more tokens; thinking blocks work only in the producing account or a linked one.
- Thinking can still be turned off "with `thinking: {"type": "disabled"}` at `high` effort or below", but effort is "the better way to trade response quality against speed and cost".

#### [A] Anthropic — Claude Haiku 5.5 migration guide (as fetched on 2026-10-08)

<https://platform.claude.com/docs/en/models/haiku-5-5/migration-guide>

- Model IDs: Claude API `claude-haiku-4-5-20251001` or `claude-haiku-4-5` becomes `claude-haiku-5-5`; Amazon Bedrock `anthropic.claude-haiku-4-5` becomes `anthropic.claude-haiku-5-5`; Google Cloud `claude-haiku-4-5@20251001` becomes `claude-haiku-5-5`; Claude Platform on AWS and Microsoft Foundry use `claude-haiku-5-5`.
- "`claude-haiku-5-5` is a fixed model ID with no date suffix and no separate alias."
- Thinking: `{"type": "enabled", "budget_tokens": N}` "returns a 400 error"; the replacement is `"thinking": {"type": "adaptive"}` with `"output_config": {"effort": "medium"}`.
- Effort is the lever: "where Claude Haiku 4.5 ran without thinking, or with a small budget to save tokens, choose a lower effort level".
- By default each `thinking` block comes back "with an empty `thinking` field and only a `signature`"; `thinking: {"type": "adaptive", "display": "summarized"}` returns summaries.
- A forced `tool_choice` is accepted, "but the response starts with the tool call and has no `thinking` block".
- Sampling: `temperature` must be `1` and `top_p` `0.99`; "Any other `temperature` or `top_p` value returns a 400 error, including a `top_p` of `1`", as do any `top_k` and both parameters together.
- Prefill is rejected "even with thinking turned off"; replace it with structured outputs or tools, and "On Claude in Amazon Bedrock, which doesn't support structured outputs, use tools."
- Computer use: drop the `computer-use-2025-01-24` beta header, declare `{"type": "computer_toolset_20260801"}`, dispatch on `name` and `toolset_name`; zoom is on by default, and `fine-grained-tool-streaming-2025-05-14` alongside a toolset returns a 400 error.
- A thinking block sent back after a change to `system`, `tools` or earlier `messages` returns a 400 error, so "Keep conversations append-only."
    - On accounts created before August 31, 2026, 00:00 UTC, the error comes only with `thinking.block_binding.prefix_mismatch_behavior` set.
- "Priority Tier is not supported on Claude Haiku 5.5."
- Haiku 3.5 is retired on the Claude API and Bedrock and Haiku 3 on the Claude API; code from them also moves to `code_execution_20250825` or later and `text_editor_20250728`.

#### [A] Niko1221 — Strata docs: HOW_IT_WORKS.md and MODELS.md (as fetched on 2026-10-08)

<https://github.com/Niko1221/Strata/blob/main/docs/HOW_IT_WORKS.md> / <https://github.com/Niko1221/Strata/blob/main/docs/MODELS.md>

- The GPU holds "attention and DeltaNet mixers, the gated-residual weights, routers, shared experts, output head, the MTP draft layer, the KV cache (from 64K: only its most-read part, the rest streams from RAM), and an expert cache that fills the rest of VRAM with the most-used experts".
- "More VRAM matters more than a faster GPU: every extra GB holds ~700 more experts, and every expert on the GPU is one the CPU does not have to compute."
- RAM holds "all 24,576 experts, pinned", and the CPU computes the ones not on the GPU "in place", at the same time as the GPU (AVX-512 / AVX2 kernels, ggml's for the i-quants).
- On a PC with little RAM and a big card, a low-RAM mode keeps in RAM only what the GPU does not hold.
- The SSD holds "the 28.8 GB n-gram table, read a few rows per token through the OS cache".
- The same engine is compiled for NVIDIA (CUDA) and AMD (HIP).
- The model's own MTP layer drafts up to 3 tokens and one pass over all 48 layers checks them, at 2.4-3.2 tokens per pass on average.
- When the reply repeats the context, prompt lookup drafts up to 5 tokens, making "code edits 6-11% faster, other text unchanged".
- "Strata runs one model, Qwen3.8-Flash-Next, in several sizes (the same model, compressed more or less) and several versions (the original, a coding version, a fine-tune)."
- At a 128K context on the RTX 5070, answers run at 76 (Q2_0), 63 (IQ2_XS), 49 (IQ3_XXS), 46 (IQ3_S) and 43 (Coder, IQ1_M) tokens/s.
- A 4K prompt reads at 910-1,580 tokens/s, and "A 32K prompt takes about 15 seconds with Q2_0."
- RAM plus VRAM needed: Q2_0 37.6 GB ("fastest", "good"), IQ2_XS 39.2 GB ("better (recommended)"), IQ3_XXS 47.0 GB ("great") and IQ3_S 54.8 GB ("best: matches the full model on the published tests (original model only)").
- The download is 66-76 GB for the three smaller sizes, and the first start also fetches the MTP draft layer (~6 GB, +1 GB with images).
- A size fits when "RAM is at least the experts + about 10 GB", the experts being 34 GB for Q2_0, 35.5 for IQ2_XS, 43 for IQ3_XXS, 50 for IQ3_S and 23 for the Coder.
- The second shard, "a 29 GB lookup table", stays on the SSD.
- `START-HERE.bat --calibrate` tunes engine settings in about 5-10 minutes and made the Coder 7% faster on the measured PC (NVIDIA cards for now).
- The Coder keeps 256 of each layer's 512 experts, chosen on code (with agentic and image) data, at "91% of the full model's SWE-bench Verified score, 99% of LiveCodeBench, by its authors".
    - Its shard 1 is 29.6 GB, so it fits 32 GB of RAM and "runs 262K context on 64 GB".
    - Under issue #438, "Chinese answers came out wrong or looping where English was fine".
- Swift 1.5 runs at the same speed per token as the original, comes without IQ3_S and carries its own license.
- UD-IQ4_XS keeps "your RAM minus 24 GB" of its 59.5 GB of experts in RAM and needs 48 GB of RAM or more and engine 0.1.38 or newer.
- UD-Q4_K_XL is a 111 GB download whose 77 GB of experts do not fit in RAM, and it needs 48 GB of RAM, an NVMe SSD and one NVIDIA GPU (no images yet).
- Unsloth's UD-Q6_K_XL (169.2 GB, not in setup's menu) and OrcaRouter's Uncensored IQ3_XXS are manual setups.

#### [A] Strata — Running a 125-Billion-Parameter Model on a Normal PC, paper (September 2026)

<https://github.com/Niko1221/Strata/blob/main/docs/paper/Strata-Paper.pdf>

- The subtitle calls Strata "a CUDA and CPU inference engine that serves Qwen3.8-Flash-Next from one 12 GB graphics card, 64 GB of RAM and a six-core desktop processor".
- The extracted text names no author and no affiliation.
- The paper gives the model's smallest good-quality quantization as a 66 GB file, five and a half times the memory of a 12 GB card.
- "Strata is an inference engine written for this one model."
- On an RTX 5070 (12 GB), a Ryzen 5 7600 and 64 GB of DDR5 it reports 95 tokens/s at a 4K context with Q2_0, 45-95 tokens/s across all three quantizations from 1K to 262K, and prompt reading at 285-571 tokens/s.
- Running the rest from RAM on the CPU with a general-purpose engine such as llama.cpp "works but leaves most of the machine idle most of the time".
- Of the 48 layers, 36 use Gated DeltaNet and 12 use Qwen Sparse Attention, which has two key/value heads and attends to at most about 2,048 selected positions.
- Each layer ends in 512 experts of which the router picks 10, so a token touches 2% of the expert weights, and the 51-billion-parameter n-gram table is addressed by the last three token ids.
- The byte census of the Q2_0 file gives the routed experts 34.0 GB stored and 0.66 GB read per token, the mixers, attention, shared experts and routers 1.8 GB, the gated residual 1.3 GB, the output head 0.44 GB, the n-gram table 28.8 GB with at most 23 KB read per token, and the MTP layer 0.8 GB.
- The GPU-resident part is about 3.5 GB, and the test machine has PCIe 4.0 x16 (~26 GB/s) and 64 GB of DDR5 (~41-52 GB/s).
- For each layer the GPU writes the ten chosen expert ids into pinned host memory (a "doorbell"), and the CPU sends the cached experts to the GPU, copies a share of the misses over PCIe (55% for the i-quant files, 20% for Q2_0) and computes the rest.
- Strata fetches the MTP head's tensors (5 GB) from the BF16 checkpoint and keeps them in VRAM with a reduced output head over 40,525 likely tokens.
- "The result is exact: the text is identical, token for token, to plain greedy decoding, which we test with forced wrong drafts and rollbacks."
- A profile-filled expert cache serves 50% of the routed experts from 4,500 VRAM slots, and swapping in the conversation's own hot experts raises that to about 72%.
- Q2_0's time to first token is 2.7 s at 1K, 6.7 s at 4K, 55.3 s at 32K, 114.4 s at 64K, 236.7 s at 128K and 523.8 s at 262K, while the experts in VRAM fall from 4,517 to 1,588.
- At 4K a Q2_0 verify window takes 34.3 ms, of which 14.6 ms wait for the GPU, 13.4 ms for the CPU experts, 2.0 ms drafting and 4.3 ms other, at 3.23 tokens per round.
- Speculation with the MTP layer is "worth 1.6–1.8×", taking plain decoding at 4K from 47-57 tokens/s to 82-92.
- Against llama.cpp the mean KL divergence of the next-token distribution is 0.022, below the 0.058 by which llama.cpp's own CPU and GPU builds differ.
- On a DDR4 system the CPU half of a Q2_0 round takes about twice as long, and "a bigger GPU cache is the best compensation".
- The paper lists keeping the conversation's state between requests as future work, because "Today every request processes its whole prompt again".

### Notes

- Every speed figure in the README, the docs and the paper is the developer's own; the independent measurements are the PC Watch column (IQ2_XS 34-44 tok/s on an RTX 3060 with DDR4, IQ3_S 86.6-128.5 tok/s on a 48 GB-modified RTX 4090), the community RTX 5090 report (165.0-179.4 tok/s) and single users on Hacker News and Hackaday.
    - The RTX 3060 results fit the paper's statement that DDR4 roughly doubles the CPU half of a round.
- Prompt reading is the weak point for coding agents: the paper's TTFT for Q2_0 is 55.3 s at 32K, the README says the first message reads at about 1 minute per 30,000 tokens, and PC Watch measured about 25 s for 23k tokens on the RTX 3060.
    - The conversation cache and the system-prompt checkpoint in DETAILS.md are what make later agent turns read only the new part (Codex: about 96% reused, 1-2 s per turn on an RTX 5070).
- The paper's prompt speeds (285-571 tokens/s) predate the current README (1,160-2,650 tokens/s); DETAILS.md says engine 0.1.13 about doubled prompt speed, and later releases added more.
- The minimum RAM differs by source: 32 GB in the README, GIGAZINE and Hackaday (enough only for the Coder, or for Q2_0 and IQ2_XS with a 24 GB card in low-RAM mode), 48 GB as the practical floor in the PC Watch column, and 64 GB recommended by npaka and in the PC Watch news piece.
- Quality is the open question: low-bit quantizations (Q2_0, IQ2_XS), a Coder that is weaker on Chinese and other CJK text (#438, which matters for Japanese use), a looping IQ2_XS answer relayed by GIGAZINE, PC Watch finding IQ2_XS code a notch below IQ3_S, and one Hacker News user's vision test in which Strata was about three times worse than llama.cpp on the same weights.
    - Only PC Watch's small IQ3_S checks (46/48 code tests, clean Japanese, correct images and tool calls) point the other way, and nobody has published a larger eval of Strata against llama.cpp on the same file.
- No source shows a link between the Strata author and the Qwen team: the GitHub profile lists Ljubljana and no company, the paper names no author, and every source treats Strata as an independent project built on Qwen's open weights.
- The claim on Hacker News that the code is AI-generated is unverified; the docs themselves say several hardware paths are only compile-checked and that the Windows AMD fix in 0.1.40.3 was untested on such a card.
- The model's license matters for team use: Strata is MIT, but the weights and the ESP vector are under the Qwen Community License 1.0, which requires a separate license from Qwen for commercial use by a "Model as a Service" or "AI Work Assistant" (AI coding or office productivity product) business, while internal use that exposes nothing to third parties is exempt.
    - The Coder (Apache-2.0 per its card) and Swift 1.5 (Swift Open License 1.0) carry further licenses of their own.
- The reasoning levels do not line up: the model card lists xhigh (default), medium and low, while Strata exposes none, low, medium and high with high as the model's default; how Strata maps them onto the trained levels is not documented in what was read.
- GIGAZINE's background article differs from Qwen's own pages twice: it gives the training cost as one ninth of Qwen3.8-27B where the QwenLM README says one ninth of Qwen3.7-Plus, and it names the comparison column Claude-Opus-4.8 (Max) where the model card read on 2026-10-08 shows Claude-Opus-4.6 (Max).
- AINews says llama.cpp v0.6.0 "Adds" Qwen3.8-Flash-Next, but the QwenLM README already lists llama.cpp support (text and vision) and Hacker News users run Unsloth's GGUFs on llama.cpp, so what v0.6.0 adds for this model is unclear.
- The Hacker News title mentions an RTX 4090 at 100 T/s, a 24 GB card, while the project's headline claim is about 12 GB cards.
- The docs disagree on how the n-gram table is read: HOW_IT_WORKS.md and the paper say through the OS page cache, while DETAILS.md says the default `--ple-io direct` reads it unbuffered past the OS cache, with `--ple-io ram` for rotational disks (#605).
- The Qwen blog post (qwen.ai) did not render through the page cache or WebFetch, so the architecture facts here come from the model card and the QwenLM README.
- The Qwen3.8-Flash API price ($0.16 / $0.47 per 1M input / output tokens) comes from Qwen's post on X as embedded by GIGAZINE on 2026-08-27, and the current QwenCloud price was not checked.

### Ideas for practice and output

- Run a one-day spike on a spare desktop with a 12-24 GB NVIDIA card, 64 GB of RAM and an NVMe SSD: install IQ2_XS and IQ3_S, point Claude Code (`ANTHROPIC_BASE_URL`, `ANTHROPIC_MODEL`) and Codex CLI (`wire_api = "responses"`) at it, and record the first-prompt TTFT, decode tok/s and cache reuse on later turns.
- Score 10-20 of the team's own small coding tasks, including Japanese prompts and comments, on Strata IQ2_XS, IQ3_S and the Coder against the hosted model the team uses today, to see whether the quality loss reported for low-bit quants and CJK text matters for its work.
- Run the same GGUF on llama.cpp for the same tasks to separate engine effects from quantization effects, since the Hacker News vision test suggests the engine itself can cost quality.
- Before any use beyond personal experiments, review the Qwen Community License 1.0 with legal: an internal coding assistant served to colleagues may count as internal use, but anything offered to customers as a coding or office assistant may need a separate license from Qwen.
- Write a short security checklist for local model servers from Strata's own rules: keep `127.0.0.1`, set `--api-key` before `--host 0.0.0.0`, use 0.1.38 or later for the DNS-rebinding protection, leave the experimental speed projection off, and read `docs/AI_SETUP.md` before letting an agent run the installer.
- Compare the monthly cost of a local box (hardware amortization and power) with the team's token volume at the Qwen3.8-Flash API price relayed by GIGAZINE ($0.16 / $0.47 per 1M tokens), and write the result up as an internal note or a short Zenn article on when local 125B MoE serving pays off.

- "Based on Gemma 4, this sub-1B model maps text, code, images, video, and audio into a unified 768-dimensional space."
- Load sizes: "270M (text/code), 440M (text + vision), 570M (text + audio), or 740M (full multimodal), all projecting into the same compatible vector space."
- Code: it "Significantly outperforms EmbeddingGemma 1 on code search and technical retrieval, making it ideal for local codebase indexing and agentic code search."
- Under the hood: text and code use "An adapted Gemma 4 decoder with an 8,192-token context window"; the vision encoder (+170M) handles "images, visual documents (PDFs, slides, charts), and video frames"; the audio encoder (+300M) "directly ingests raw audio".

- Text uses task prompts through `prompt_name`, for example `SearchQuery` for queries and `Document` for documents.

#### [A] Google AI for Developers — EmbeddingGemma 2 model card (2026-10-06)

<https://ai.google.dev/gemma/docs/embeddinggemma/model_card_2>

- The page reads "Last updated 2026-10-06 UTC", names Google DeepMind as author, and labels the license Apache 2.0 with a link to the `gemma_4_license` page.
- "EmbeddingGemma 2 is an open multimodal embedding model built by Google DeepMind which maps text (incl. code), images, video, and audio inputs—and combinations thereof—into a single, unified 768-dimensional vector space."
- It "understands 100+ languages, and achieves a ~14% improvement on code tasks relative to its predecessor."
- The text backbone is 270M parameters (130M transformer + 140M embedder), with selectively loadable vision (170M) and audio (300M) encoders.
- MRL covers 128d, 256d, 512d and 768d, "enabling up to a 6x reduction in vector storage costs with minimal impact on quality."
- "Task-steered representations: Uses lightweight text instruction prefixes to optimize embeddings for different tasks".
- Architecture: 24 layers, model dimension 512, hidden dimension 2048, a 1024-token sliding window, vocabulary 262,144, 4 heads, KV-heads 2/1 (local/global), local:global 5:1, GQA/MQA, gated FFN with GELU, mean pooling, and a 512→768 projection.
- Input and output: text, images, video and audio; an 8,192-token context window; native output 768 dimensions; MRL truncation to 128, 256 and 512.
- Benchmarks at 768d, full-precision checkpoint, EmbeddingGemma 2 against EmbeddingGemma 1 where given:
    - MTEB (multilingual, v2), Mean(Task): 61.36 against 61.15.
    - MTEB (code, v1), Mean(Task), NDCG@10: 78.68 against 68.76.

    - MSEB (Retrieval), MRR@10: 69.54; MAEB, Mean(Task): 49.39.

    - 768d (1:1): 61.36 / 68.46 / 78.68 / 64.64 / 59.01 / 69.54 / 49.39.

    - 128d (1:6): 57.89 / 65.68 / 71.41 / 59.06 / 45.65 / 56.71 / 46.92.
- "model users can reduce storage requirements, with minimal quality impact down to 256d."
    - "128d is best suited to text-only workloads."
- Task prefixes apply to text only; "omitting it still works but reduces precision", and images, video and audio take no prefix.
    - `SearchQuery`: `task: search result | query: {query}`, with documents as `title: {title} | text: {content}` (or `title: none`).
    - `QuestionAnswering` and `FactChecking` use `task: question answering | query: {question}` and `task: fact checking | query: {claim}`.
    - `CodeRetrieval`: `task: code retrieval | query: {query}`, with documents as `title: {title or filename} | text: {code}`.
    - Symmetric tasks (`Classification`, `Clustering`, `SentenceSimilarity`) put the same prefix on every input.
    - `prompt_name="Document"` applies `title: none`, so titled documents must be formatted by hand.
- Effective sizes by `config_kwargs`: text only 270M, text and image 440M, text and audio 570M, full multimodal 740M; omitting encoders "differs among model libraries".
- MRL at runtime: "Re-normalize after truncating", because "Skipping this step degrades ranking quality silently—it produces plausible-looking scores rather than an error."
    - "Queries and documents must share a dimension."
    - "Quality is close to lossless down to 256 dimensions."
    - "128 dimensions degrades multimodal quality substantially and should be validated against your own workload before adoption."
- Precision: "Run inference in `bfloat16` or `float32`."
    - "Do not use `float16`."
    - "In `float16` the model returns NaN or silently degraded embeddings rather than raising an error, so the failure is easy to miss."
- Context budget, all modalities sharing 8,192 tokens: text 1 token per subword; image 280 tokens per image by default (~29 images); video 140 tokens per frame by default (~58 frames); audio 25 tokens per second (~327 seconds).

    - Video is sampled at 1 frame per second by default (configurable), and audio should be mono at 16 kHz.
- Training data has "a cutoff date of January 2025", and its web text spans "over 140 languages".
- "Unlike generative models, it does not undergo post-training alignment, safety tuning, or output-level moderation."
    - "Developers and deployers are responsible for evaluating and implementing application-level safeguards, like retrieval filtering and fairness testing".
    - Deployments must follow the Gemma Prohibited Use Policy.
- "while EmbeddingGemma 2 supports 100+ languages, the model may not exhibit equal performance across languages."
- Intended uses include "RAG over enterprise knowledge bases, code search from natural language queries, or spoken-query search over audio archives", classification, clustering, semantic similarity and fact verification.

- What operation taught them: the hard part is not writing but keeping what was written correct, because the sources are updated daily and the wiki starts going stale the moment it is written.
- Why none of the three can be trusted alone:
    - Design specs show the design intent, but they describe the design at the time of writing, with no guarantee that it matches current behaviour.
    - Help articles explain what customers see, but many patterns are not covered and revisions sometimes lag the implementation.
    - Code is the actual behaviour, but few people can read it and the implementation itself may be wrong.
- Handing the three to an LLM as they are solves nothing, because the LLM cannot decide which one is right when they conflict; the author judged that organising the context beforehand works better than a stronger model.
- Who gains from one reconciled place:
    - QA can write expected results against a spec that reflects both code and design, which is what finding deviations from the spec (bugs) requires, since code alone cannot show whether behaviour is as intended.
    - CS can tell quickly, without reading code, whether a reported behaviour is per spec or a defect.
    - Setting help articles next to the implementation exposes mistakes and outdated text in what customers are told.
- LLM Wiki is introduced as a knowledge-management pattern proposed by Andrej Karpathy: instead of people writing the wiki, an LLM reads the primary sources, writes the wiki, and grows it each time it answers a question.
- Page structure: one feature per page, with what the design spec, the help article and the code each say set side by side.
- Scale: around 100 pages per product, expected to pass 1,000 pages across Bakuraku's products.
- In Japan, trials of LLM Wiki are increasing, but cases run continuously and at scale by an organisation are still few, in the author's view.
- With personal knowledge such as papers and notes, sources are only added and past content is rarely rewritten; with an organisation's specs at this scale, help articles are revised and code ships regularly, so the sources themselves keep changing.
- The most recent release alone contained more than 2,000 pull requests.
- A wiki that is written and left returns outdated answers plausibly, so organisational use needs a mechanism that keeps following the changes in its sources.
- Device 1, regular updates (定期更新): changes land in the sources almost every day, and descriptions of new features and changed behaviour arrive through them, so what the wiki must reflect has to be found daily.
    - Most changes are refactoring or internal reorganisation that do not touch what wiki users want to know.
    - Having an LLM read every diff to decide whether to reflect it makes the cost proportional to the volume of diffs, most of it spent on changes irrelevant to users.
- The starting point of the judgement moved from "what changed in the source" to "does the answer to a user's question change", because the wiki's value lies in whether it answers users' questions correctly.
- The regular update re-fetches the three sources, diffs them against the previous run and groups the diffs by product; code diffs are further grouped by pull request.
    - Files changed in one pull request are parts of one change, so judging what a change means to users is easier per pull request than per file.
- For each grouped diff, the LLM writes one question a user would likely ask about the change (想定質問).
- When no question can be written, as with internal reorganisation, typo fixes or replaced screenshots, nothing is done, on the view that the wiki has nothing to say about it either; most diffs are dropped at this stage.
- When a question is written, the current wiki is made to answer it:
    - If the answer matches the updated sources, nothing is done.
    - If they disagree, that section is fixed.
    - If the wiki cannot answer, a section is added or a new page is created.
- A flowchart in the post shows the path: re-fetch the sources, group diffs by product and pull request, ask whether a likely question can be written, then compare the wiki's answer with the updated sources and do nothing, fix the section, or add a section or page.
- With this, the LLM reads in detail only the changes that could change an answer for users.
- Device 2, mechanical detection of degradation (劣化の機械的な検知): question-based selection leaves the decision to pick up a diff to the LLM, so when a source behind an existing page changes and the LLM judges that users' answers do not change, the page stays out of date.
    - Pages whose grounds changed must therefore be re-read with no LLM judgement in between.
- Each page lists every source it is based on and records a hash of each source's content; when a source changes, the hash no longer matches and the page is judged stale without any LLM judgement.
- Pages written from other wiki pages are tied the same way: fixing page A after a source update changes the hash of A's body, which then marks page B, written from A, as stale.
    - The judgement travels downstream one level at a time and repeats until no stale page remains, as a second diagram shows.
- Code is cited pinned to the version released to production, because help articles describe production behaviour and the reconciliation only holds on the same version.
    - Questions about behaviour in development or staging environments are answered by reading that environment's code directly, not the wiki.
- Detection is useless unless the comparison actually runs, so the hash comparison is implemented as a lint, and every wiki change must pass it before it is pushed.
    - If even one page judged stale remains, the lint fails and the push cannot proceed.
    - All wiki updates, the regular update included, go through this procedure, so a page whose sources changed is always re-read and fixed before it reaches the wiki.
- Device 3, protecting the wiki from many people's write-backs (多人数の書き戻しからwikiを守る仕組み): an LLM Wiki grows by writing answers back into it, but if users rewrite the wiki directly from their own agents, it drifts with each person's preferences and the habits of each agent.
    - The more users, the more the writing style and the judgement criteria diverge, and the wiki loses consistency.
- Write-back is therefore limited to a staging area (一時置き場): users' agents do not rewrite the wiki itself and leave their answers as they are in the staging area.
- The daily regular update reads the staging area and, following predefined rules (規約), decides whether to promote each answer to a feature page or delete it.
    - When an answer is promoted, an agent other than the one that wrote it checks it against the sources.
    - Content in the staging area is never used as grounds for the next answer, because grounding on unchecked answers would carry errors into later answers.
- The post's third diagram: a user's question, an answer from the wiki, the answer left in the staging area with the wiki untouched, a judgement by the regular update under the rules, then promotion to the matching feature page if it fits or deletion if it is wrong or weakly grounded.
- As a result, whoever asks with whatever agent, the wiki keeps being updated only along the predefined rules, keeping both the insight gained from answers and the wiki's consistency.
- Next steps: today's sources are design specs, help articles and code, and LayerX wants to add Slack discussions and the content of real customer inquiries, where the history of spec decisions and the points customers actually stumble on are recorded.
    - Unlike code and help articles, these have viewing permissions that differ by person, so gathering them into one wiki needs a mechanism that handles those differences.
- The closing summary lists three points: regular updates reflect only diffs whose likely user question gets a different answer; pages whose grounds changed are detected mechanically by hash and cannot be reflected until re-read; write-backs pass through a staging area and are promoted under the rules.
- The author's conclusion: a system in which an LLM writes knowledge is now easy to build, but running it in an organisation requires noticing that written knowledge has gone stale, deciding what not to write, and having the same rules govern updates whoever uses it.

#### [B] DevelopersIO (Classmethod) — What happens when you leave document maintenance to an LLM: a paper, by 森茂洋 (Hiroshi Morishige) (2026-05-08, in Japanese, background)

<https://dev.classmethod.jp/articles/llm-knowledge-base-document-corruption-revisit/>

- The author follows up his earlier post on Karpathy's "LLM Knowledge Base" pattern, which he had adopted, with the Microsoft Research paper above (arXiv:2604.15597v1).
- He reads the paper not as denial for its own sake but as a grounded finding: something that works in the short term showed non-negligible degradation when measured over long delegation.
- As he relays it, the three frontier models averaged over 52 domains corrupted 25% of a document after 20 interactions, and extended runs to 100 rounds did not stop the decline.
- Reconstruction Score at 20 interactions: Gemini 3.1 Pro 80.9%, Claude 4.6 Opus 73.1% and GPT 5.4 71.5%, against 94% to 97% for every model at 2 interactions.
- DELEGATE-52 covers 52 domains and 310 work environments, each with a real document of 2k to 5k tokens and 5 to 10 editing tasks, scored by round-trip (back-translation style) forward and backward edits with domain-specific parsers and weighted similarity.
- Six degradation factors he highlights:
    - Errors compound with rounds and do not converge.
    - Size and rounds interact: after 20 interactions 1k-token documents score 91.4%, 4k 79.0% and 10k 59.9%, and for GPT 5.4 each extra 1,000 tokens costs 0.7% at 2 rounds against 3.6% at 20.
    - Tool use makes it worse: with file read and write and code execution tools, the 4-model average ends 6 points lower, with input tokens 2.1 to 4.6 times larger.
    - Distractor documents cost 0.4% to 4% at first and 2% to 8% by 20 rounds, an effect that grows as a wiki grows.
    - Domains differ sharply: even the leading Gemini 3.1 Pro is "ready" (RS@20 ≥ 98%) in only 11 domains, while Python is ready for 17 of 19 models.
    - Frontier models rewrite content rather than delete it, which is hard to spot in a git diff.
- He argues an LLM cannot see its own degradation: lint or self-review run by an LLM is the same probabilistic engine checking probabilistically, with no ground truth inside, so recompilable raw sources and round-trip-style yardsticks belong outside the LLM.
- Implications for Karpathy's pattern: filing answers back into the wiki is exactly the multi-round editing the paper measured, and tool-based fixes such as lint got worse in the paper.
- Reservations: raw sources stay immutable, so a corrupted wiki can be discarded and recompiled; wikis on domains the paper rates "ready" (Python, infrastructure, AI) may fare better than the 52-domain average; and the authors acknowledge that each step was tested as an independent single turn, unlike real editing with git diff review.
- Mitigations he proposes without implementing them: a full rebuild from raw sources every N rounds (5 to 10 as a safe zone), a cap on filing-back rounds that forces a rebuild, and a round-trip-style regression check such as comparing answers to 10 recent queries from the current and a regenerated wiki.
- His conclusion: not to drop LLM knowledge bases, but to use them assuming they break, with reproducibility and monitoring built in.
