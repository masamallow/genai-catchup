#### [A] claude.dev Blog — How the Claude Code team does code review, by Addy Osmani, Morgan Westlee Lunt and Qing Wang (2026-10-15)

<https://claude.dev/blog/solving-code-review-at-anthropic/>

- Claude writes about 90% of Claude Code's own code, and from June to September merged pull requests more than doubled while the share that had to be reverted fell by more than 40%.
- The team calls "did a human read the code?" an imprecise proxy and aims for most PRs to merge with at most one human, who may be the author, with no rise in reverts or incidents.
- Before a PR, Claude is asked to show runnable evidence (tests, a build, a screenshot) and a fresh-context subagent reviews the diff, steered by a short `CLAUDE.md` and code owners' `REVIEW.md` files.
- On every PR several agents hunt bugs in parallel, a separate group votes on each finding, style-only findings are dropped, and the rest are posted inline as Important, Nit or Pre-existing.
- A PR cannot merge while any finding of the bug review or the separate security review is open; the author fixes it or resolves the thread with a reason, which is how false positives are cleared.
- A classifier picks each change's risk tier: low (docs, flagged additive changes) needs no human once checks pass, medium one, high two, and sensitive paths and CI workflow files always need a person.
- Only authors on a repository's trusted list get the lighter paths, an agent's approval never fills a human slot, and an approval covers one commit, so a later agent push needs a new one.
- The team has no circuit breakers yet that tighten approval when revert or incident rates move, and its engineers want them before more code merges with no human.
- Past incident and revert PRs, confirmed by engineers, form an eval the reviewer runs daily, and noise is tracked through authors' responses to comments and false alarms on known-clean PRs.
- After a CLI PR went through over fifty review rounds overnight, convergence changes such as a three-round cap raised one-round passes from 65% to 78% and cut mean reviews to pass from 2.08 to 1.32.

### Ideas for practice and output

- Write a `REVIEW.md` for one repository on the post's pattern (what failure looks like, a nit cap, paths to skip, file and line as evidence) and track how authors answer each finding for a few weeks.
- Turn the last few reverts or incident PRs into a small eval set and score the reviewer in use, whether Code Review, `/code-review` or a CI action, against it after every prompt or model change.
