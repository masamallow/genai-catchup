### Collected information

#### [A] OpenAI — Introducing dots (2026-09-29)

<https://openai.com/index/introducing-dots/>

- Dots are always-on agents powered by GPT-6 Astra; each has its own cloud computer, learns from feedback and can work toward the user's goals around the clock.
- Through the plugin ecosystem a dot can connect to more than 4,000 apps.
- A dot is reachable in ChatGPT, Slack and Teams, and by voice call; texting is coming later.
- Each dot works in its own cloud computer and browser, the user can open that computer to inspect the work, and connecting the user's own laptop is an optional permission.
- Inside OpenAI, dots start investigating bugs reported in Slack and turn new designs into working apps; an early tester's dot noticed a forgotten invoice, prepared it and sent it after his approval.
- When the user is not working with it, a dot does "proactive research" with tools restricted to read-only, so it cannot send messages, change app content or control a browser or computer.
- Security safeguards defend against malicious instructions, and a monitoring system can pause or stop a dot when it detects a safety concern.
- Dots start with built-in rules for when to act and when to ask; Custom Rules let users allow, require approval for or block specific actions, and Activity View shows background work.
- Actions that could affect accounts or share information go through auto-review against the user's instructions, Custom Rules and safety requirements; some tasks, such as changing a password, always stay with the user.
- For sign-in, dots can use saved passwords without exposing them to the model.
- Business, Enterprise and Edu content is not used for training by default, and OpenAI does not train directly on proactive research or a dot's notes to itself.
- Specialist dots get their own identity, credentials and system access for defined responsibilities, starting with enterprise pilots built on internal tests in procurement, invoice processing, email marketing, customer support and commercial contracting.
- OpenAI is working with Microsoft to manage specialist dots through Agent 365's governance and security controls.
- Rollout: Pro and Business Premium in eligible markets; Enterprise, Edu and Healthcare can try a beta when an admin enables it.
- The first dot is included in Pro and Business Premium, conversations with it do not count toward ChatGPT limits, and tasks it starts in Codex or ChatGPT Work count as usual; limits are extended for the first month.
- A dot is created in the desktop app or a desktop browser and can be messaged from mobile afterwards.

#### [A] OpenAI — Codex Cloud overview and cloud environments (as fetched on 2026-10-01)

<https://learn.chatgpt.com/docs/environments/cloud-environments.md>

- A cloud environment is the reusable setup that tasks use (repositories, dependencies, tools and access settings), and each task gets its own isolated workspace from the published environment and keeps working while the user's computer sleeps.
- Codex inspects the selected repositories, installs dependencies, tests the workflow and records an install script and a start skill; publishing captures the prepared filesystem for new tasks.

#### [A] OpenAI Developers — MCP Events build guide (as fetched on 2026-10-01)

<https://developers.openai.com/plugins/build/mcp-events>

- MCP Events lets ChatGPT subscribe to updates from an MCP server, such as new messages, content updates or status changes, and act on the user's instructions when a matching event arrives in the subscribed chat.
- Requirements: MCP 2.0 (protocol version `2026-07-28`), persistent subscription storage, outbound HTTPS to callback URLs and a server configured in the plugin.
- ChatGPT supports webhook delivery and callback verification from the draft, but not polling, streaming or the draft's `gap` and `terminated` control notifications.
- The server declares `"events": {}` in `server/discover` and implements `events/list` (definitions with `name`, `description`, `delivery`, `inputSchema` and `payloadSchema`), `events/subscribe` and `events/unsubscribe`.
- On subscribe, ChatGPT sends the event name, filter `arguments`, a callback URL and a `whsec_` secret (24 to 64 bytes) for Standard Webhooks HMAC signing; the server returns `id`, `refreshBefore`, `cursor` and `truncated`.
- Before activating delivery, the server verifies the callback with a signed request carrying a fresh, single-use challenge that the receiver must echo; failure returns `-32015` (`CallbackEndpointError`).
- Callbacks must use HTTPS, and the server must block private and local addresses, refuse redirects and validate the destination at connection time to defeat DNS rebinding.
- Events carry `eventId`, `name`, `timestamp`, `data` and `cursor`, one per request, with headers `webhook-id`, `webhook-timestamp`, `webhook-signature` and `X-MCP-Subscription-Id`, and at most 256 KiB.
- Retries keep the event ID with a fresh signature, `410` and `413` are not retried, events can arrive out of order, and write tools should be idempotent.
- The client refreshes before `refreshBefore` with the last cursor; replayable events resume from the cursor, and `truncated: true` means history was lost.
- Payloads should carry summaries with a read tool for the full record, user-authored text is data, and payloads must not carry instructions to the model.
- The testing checklist includes revoked access, invalid signatures, duplicates, bursts and feedback loops when an action changes data in the source app.

#### [A] MCP Triggers and Events WG — MCP Events design sketch, by Peter Alexander (draft dated 2026-02-19, merged to main 2026-09-08)

<https://github.com/modelcontextprotocol/experimental-ext-triggers-events/blob/main/docs/design-sketch-proposal.md>

- The draft defines three delivery modes, `poll` (`events/poll`), `push` (a long-lived `events/stream`) and `webhook`, with no mode mandatory.
- The three modes are kept despite about three times the surface because deployments differ: serverless servers cannot push, clients behind NAT cannot receive webhooks, and cost-sensitive clients should not poll.
- The subscription key is the principal, callback URL, event name and canonical-JSON arguments; webhook mode requires an authenticated principal.
- Standard Webhooks was adopted so that existing verifiers work unchanged, receivers should reject timestamps older than 5 minutes, and an ack timeout of about 5 seconds is common.
- Endpoint verification is mandatory through one of four paths: a challenge handshake, a server allowlist, prior out-of-band verification or a well-known receiver document.
- Delivery is at least once with no ordering or exactly-once guarantee, there is no flow control in v1, and receiving an event grants no authority to act.
- Open questions include how SDKs should expose events to agent frameworks and whether one subscription can cover several event names.

#### [A] GitHub Blog — Project HydraFusion: Frontier quality via multi-model orchestration (2026-09-04)

<https://github.blog/ai-and-ml/github-copilot/project-hydrafusion-frontier-quality-via-multi-model-orchestration/>

- HydraFusion is a research preview that builds an execution plan per task, choosing models from several providers to draft, critique and revise, or to cascade to stronger models; the user selects it like any other model.
- It treats workflow selection as an optimization problem, using capability signals for reasoning, code generation, debugging and tool use, and picks the least complex workflow expected to meet the quality bar.
- Single: one model solves the task; Cascade: an efficient model drafts and a quality gate accepts or escalates to a stronger model; Critique: an independent, read-only critic from a different model family reviews the draft and the drafting model revises once.
- Design principles: account for cost across every leg, bound each leg with timeouts and cancellation, run reviews in isolated tool-less contexts, apply no patch when a workflow is cancelled or fails validation, and validate model bindings before execution.
- Against Claude Opus 5 at medium reasoning, the best tuned configuration scored 4.9 points higher on TerminalBench 2.1 at 67% lower estimated cost, 1.5 points lower on DeepSWE at 36% lower cost, and 0.1 points lower on the internal CheckpointBench at 65% lower cost.
- The policy was built with beam search across the same three benchmarks, and two harness failures between 08-11 and 08-25 produced runs that were excluded.
- At launch it was in Copilot CLI's `/experimental` on all plans, billed by the tokens of the models it uses at their standard rates, and best suited to first-turn, single-prompt tasks handed over in autopilot mode.

#### [A] Anthropic (claude.dev blog) — Automating eval design and hillclimbing with Claude, by Lance Martin (2026-09-28)

<https://claude.dev/blog/automating-eval-design-and-hillclimbing/>

- The post introduces two commands of the claude-api skill in Claude Code: `/claude-api build-eval` builds an eval inside the codebase, and `/claude-api hillclimb` improves the application against it one change at a time, with held-out examples to catch overfitting.
- A good eval has four properties: tasks that mirror production, scores that rise with stronger models and more thinking, headroom below 100% for the best model at maximum effort, and low run-to-run variance.
- It argues against adversarial sampling, picking cases that today's model fails, because that measures one model's failure fingerprint instead of what is hard or valuable for the application.
- build-eval interviews the user and collects inputs in this order: production transcripts (after asking about retention and sensitive data), bug reports and tickets, 5 to 10 hand-written cases, and cases synthesized from the codebase.
- It shows every input on a page for approval, then proposes the cheapest grader that fits: a programmatic check where outputs are constrained, or an LLM judge with a rubric of checkable claims (not a 1-to-5 scale) on a model other than the one under test.
- It grades a few cases and asks whether the user would have scored any differently, then runs three checks: the grader twice on the same output, timeouts and cut-off answers, and a warning when the baseline already scores about 95% or more.
- hillclimb asks for a goal (performance, or cost at equal performance), splits cases at random into train and test, and checks that eval noise is smaller than the smallest improvement worth acting on.
- Each round proposes one root-cause change (prompt, skills, tool descriptions, model and effort, or harness code); a change that raises train but not test is reverted as overfitting, and any regression is reverted.
- After two or three stalled rounds it sorts the remaining failures by cause, and at the end it leaves the code at the best test-set version and reports the result with confidence intervals.
- On an internal support benchmark of 44 tickets (30 for search, 14 held out), the baseline was Opus 4.8 at high effort with 74.4% decision accuracy at 4.6 cents per ticket.
- Steps found by the hill-climb: a prompt audit plus Opus 5.5 at low effort (87.8%, 1.9 cents), Sonnet 5 at low effort (88.9%, about 1 cent), then routing rules and a refund-cap cross-reference (98.9% at about the same cost).
- On the 14 held-out tickets, the final setup scored 90.5% against 78.6% for the original at about a fifth of the cost.
- A second example raised Anthropic's own claude-api skill from 66% to about 88% on a documentation-derived eval, partly by adding a table that maps API shapes remembered from training to current ones.
